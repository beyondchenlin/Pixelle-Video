## 1. 结论

本次设计采用“双位置、同名称、不同语义”的方案：

- **IP 设计页**继续保留现有字段 **`世界观提示`**，语义不变，它表示这个 IP 形象长期适配的内容世界、题材边界和默认融入倾向。
- **生成页**新增一个同样显示为 **`世界观提示`** 的填写位置，它表示**本次文案**的世界设定、时代空间、叙事边界和 IP 融入要求。

前端界面上，这两个位置都继续叫“世界观提示”，不改名。  
后端和链路内部则必须明确区分：

- `IPProfile.world_hint`：长期、资产级、可复用的 IP 默认世界观提示
- `generation_world_hint`：本次生成请求级的世界观提示

推荐实现不是“只加一个文本框”就结束，而是：

1. 生成页增加 `世界观提示` 输入区；
2. 支持“根据文案生成”和“使用 IP 默认”两种辅助填充；
3. 即使用户不手动填写，后端也可以在正式生成前基于文案自动补全一个**本次世界观结构化画像**；
4. 该结构化结果同时进入：
   - 高级分镜规划
   - IP 使用规划
   - 最终图片提示词生成

这样可以解决你前面反复指出的根问题：  
**IP 不是孤立设计出来摆在那里，而是要在整条提示词生成链路里，根据本次文案的世界观合理融入。**

## 3. 备选方案比较

### 方案 A：只复用 IP 设计页的 `世界观提示`

做法：

- 不新增生成页字段
- 每次生成都直接读取 `IPProfile.world_hint`

优点：

- 改动最少

问题：

- 会把“长期 IP 默认倾向”和“本次文案世界观”混为一谈
- 用户一换文案，字段语义立刻失真
- IP 默认世界观无法表达本次剧情的具体时代、空间、氛围和叙事边界
- 后续图生图、场景变体、多文案复用都会出现语义污染

结论：**不采用。**

### 方案 B：生成页只加一个自由文本框，直接把文本原样拼进 prompt

做法：

- 生成页新增 `世界观提示`
- 文本原样透传到 storyboard 和 image prompt

优点：

- 用户能立即填写
- 前端理解成本低

问题：

- 只是新增了输入，不是新增了能力
- 文本会在不同链路层被重复拼接，容易造成提示词污染
- 大模型无法稳定区分哪些内容属于时代/空间，哪些属于叙事边界，哪些属于 IP 融入要求
- 难以和现有 `world_preset_id`、风格提示词、IP 固定身份做稳定协同

结论：**不建议作为正式方案。**

### 方案 C：生成页新增 `世界观提示`，内部转成结构化世界画像

做法：

- 生成页新增 `世界观提示`
- 允许用户手填，也允许“根据文案生成”或“使用 IP 默认”
- 后端把最终文本解析成结构化 `generation_world_profile`
- 分镜规划、IP 使用规划、最终提示词统一读取这个结构

优点：

- 界面名称和使用习惯简单
- 内部语义清晰，不污染现有字段
- 可以和现有高级分镜规划、IP 链路、风格提示词稳定组合
- 未来扩展图生图、图片复用、场景复写时仍然成立

问题：

- 需要新增一个小型服务层和合同层

结论：**采用方案 C。**

## 4. 产品语义定义

### 4.1 IP 设计页的 `世界观提示`

它描述的是：

- 这个 IP 长期适合什么样的内容世界
- 它不适合进入什么样的题材和角色语境
- 它默认更像“主角 / 向导 / 配角 / 象征物”中的哪一种
- 它进入场景时通常保持什么样的文化、审美、风格兼容性

它**不是**：

- 当前这篇文案正在发生的具体世界设定
- 本次每一帧都必须严格执行的场景描述

### 4.2 生成页的 `世界观提示`

它描述的是：

- 本次文案发生在什么样的世界
- 时代、地点、空间范围、社会语境是什么
- 画面整体气质和叙事边界是什么
- 这个 IP 在本次内容里应该以什么方式融入，而不是生硬替换原有主体

它**不是**：

- 风格提示词的替代品
- 世界预设库的替代品
- IP 固定身份锁定的替代品

## 5. 命名与字段边界

### 5.1 界面命名

前端显示统一保持：

- `世界观提示`

不改成“长期适用边界”“世界设定”“世界画像”等其它名称。

### 5.2 内部字段命名

为避免技术债，内部必须拆开：

- 保留：`IPProfile.world_hint`
- 新增：`generation_world_hint`
- 新增：`generation_world_profile`

推荐不要把新字段继续命名成第二个 `world_hint`，否则 API、合同、快照和测试层都会变得模糊。

### 5.3 快照与调试字段

在 `planning_snapshot` 里建议明确记录：

- `generation_world_hint`
- `generation_world_hint_source`
- `generation_world_profile`

其中 `generation_world_hint_source` 推荐值：

- `manual`
- `generated_from_script`
- `ip_default`
- `empty`

## 5.4 源头事实模型与职责边界

这是本次方案后续维护时最重要的边界，必须作为源头规则固定下来：

1. **IP 身份事实源**
   - `IPProfile.identity_lock`
   - `IPProfile.identity_anchors`
   - `IPProfile.semantic_boundary`
   - 这些字段定义“这个 IP 是谁”“哪些识别锚点不能丢”“哪些角色和主体不能被错误替换”。
   - 它们属于资产级、结构化、长期稳定的事实源，不允许被请求级世界观字段替代。

2. **IP 长期默认世界观**
   - `IPProfile.world_hint`
   - 这是资产级长期默认值，用于表达该 IP 长期适配的内容世界、默认题材边界和默认融入倾向。
   - 它可以作为生成页“使用 IP 默认”的回填来源，也可以作为 `ContentWorldPlanner` 的输入之一。
   - 它不能覆盖当前请求的 `generation_world_hint`，也不能充当身份锚点。

3. **请求级世界观输入**
   - `generation_world_hint`
   - 这是本次生成请求的世界观输入，决定当前文案所处世界、叙事边界和本次 IP 融入要求。
   - 它只属于请求级，不得写回 AssetBible，不得覆盖 `IPProfile.world_hint`。

4. **请求级结构化世界画像**
   - `generation_world_profile`
   - 这是 `ContentWorldPlanner` 对本次世界观进行解析、归一化和补全后的结构化结果。
   - 它是分镜规划、IP 融入规划和最终图片提示词共同读取的请求级中间合同。

5. **逐帧 IP 融入裁决**
   - `ip_adaptation`
   - 这是 `IPUsagePlanner` 基于分镜、世界观约束、身份锚点和保护主体生成的逐帧裁决结果。
   - 它是最终图片提示词阶段对“这一帧里 IP 以何种强度、何种方式出现”的事实来源。

后续任何扩展都必须遵守以下硬规则：

- 不允许用 `generation_world_hint` 替代 `identity_lock` / `identity_anchors`
- 不允许把 `generation_world_hint` 或 `generation_world_profile` 写回 AssetBible
- 不允许把 `IPProfile.world_hint` 当作逐帧图片提示词的唯一真实来源
- 不允许跳过 `ContentWorldPlanner` / `IPUsagePlanner` 直接把任意文本拼进最终 prompt

## 5.5 与 IP 工作台保存链路的关系

本方案已经依赖一个更底层的事实：IP 资产保存链路必须保留完整的 `ip_profiles` 集合，不能因为编辑一个形象而覆盖其他 sibling profiles。

当前主线已通过投影与 upsert 方式修复该问题：

- `web/utils/asset_bible_api.py::build_asset_bible_draft_payload_from_response`
- `web/utils/asset_bible_api.py::upsert_ip_profile_draft`
- `web/components/ip_design_workbench.py`

这条修复与“生成页世界观提示”不是同一个功能，但它是本方案可靠成立的前置条件之一。否则，请求侧世界观和 IP 身份事实源虽然设计正确，底层资产保存仍可能把其他 IP 事实源误删，导致后续生成拿到错误或残缺的 IP 画像。

## 6. 生成页的交互设计

### 6.1 放置位置

从当前代码结构看，最合理的位置不是 IP 设计页，也不是单独新开页面，而是：

- `web/components/storyboard_planning_controls.py`
- 挂在当前 **高级分镜规划** 区域内

原因：

1. 它首先服务于**本次文案**；
2. 它要先于 storyboard planner 生效；
3. 它又要继续传给 IP usage planner 和最终 image prompt；
4. 当前 `style_config -> storyboard_planning_controls -> output_preview -> API -> standard pipeline` 已是这类生成期参数的正式链路。

### 6.2 前端交互形态

推荐使用以下组合，而不是新建复杂模式页：

1. 一个 `世界观提示` 多行输入框
2. 两个辅助操作
   - `根据文案生成`
   - `使用 IP 默认`
3. 一段简短帮助文案，说明它作用于“本次文案”

推荐行为：

- 用户可直接手填
- 用户点“根据文案生成”时，基于当前文案、标题、世界预设、已启用 IP 的默认世界观，生成一版草稿回填到文本框
- 用户点“使用 IP 默认”时，把当前选中 IP 的 `IPProfile.world_hint` 回填到文本框
- 用户即使什么都不点，后端在正式生成时仍可根据文案自动补全一个结构化世界画像

这样可以同时满足：

- 有明确填写位置
- 有自动化能力
- 不强迫用户走额外流程

## 7. 结构化世界画像设计

生成页的 `世界观提示` 不应在后端只作为一大段裸文本存在，推荐转换成统一结构：

```json
{
  "summary": "这篇文案发生在什么样的内容世界",
  "time_space": "时代、地点、空间范围",
  "visual_environment": "主要视觉环境",
  "atmosphere": "整体氛围",
  "cultural_context": "文化、行业、题材语境",
  "story_constraints": "不能偏离的叙事边界",
  "ip_integration_guidance": "IP 在这个世界里应该如何融入"
}
```

推荐新增内部模型名：

- `ContentWorldProfile`

设计原则：

- 用户仍然只看一个“世界观提示”文本框
- 结构化只在后端内部和调试快照中存在
- 最终传给 LLM 的可以是结构化 JSON，也可以是基于结构化 JSON 生成的标准化文本片段

## 8. 与现有链路的职责分工

这次设计必须明确四类能力各做什么，避免互相污染。

### 8.1 `world_preset_id`

它负责：

- 高级分镜规划的宏观策略
- 预设世界模板
- 对镜头规划和内容模式的默认倾向

它不负责：

- 当前文案的具体世界事实

### 8.2 风格提示词 / 风格前缀

它负责：

- 画面材质
- 渲染语言
- 灯光、构图、笔触、摄影质感

它不负责：

- 决定 IP 是谁
- 决定当前故事世界是什么

### 8.3 `IPProfile.world_hint`

它负责：

- IP 的长期世界兼容性
- IP 默认适合如何出现

它不负责：

- 覆盖当前文案世界

### 8.4 `generation_world_hint`

它负责：

- 当前文案的世界设定
- 当前世界里的叙事边界
- 当前世界里 IP 的合理融入方式

## 9. 新的数据流设计

推荐的数据流如下：

```text
用户文案
  -> 生成页世界观提示（手填 / 根据文案生成 / 使用 IP 默认）
  -> generation_world_hint
  -> ContentWorldPlanner
  -> generation_world_profile
  -> Storyboard Planner
  -> IP Usage Planner
  -> Image Prompt Generation
  -> 最终图片提示词
```

正式展开后应为：

```text
content_input.text
  + content_input.title
  + storyboard.world_preset_id
  + ip_profile.world_hint (optional)
  + generation_world_hint (optional user override)
    -> ContentWorldPlanner
    -> generation_world_profile

generation_world_profile
  + world_preset
  + shot_preset
    -> StoryboardPlanner

storyboard_frame
  + generation_world_profile
  + ip_profile.identity_lock / anchors / semantic_boundary
    -> IPUsagePlanner

frame_context
  + generation_world_profile
  + ip_adaptation
  + resolved_style
    -> build_image_prompt_prompt(...)
```

## 9.1 当前已落地的数据流

当前 `dev` 上实际运行的数据流已经与上面的目标链路对齐：

```text
生成页 storyboard_generation_world_hint
  -> build_storyboard_control_payload(...)
  -> output_preview request builder
  -> VideoGenerateRequest / StoryboardControlsContract
  -> generate_styled_image_prompt_batch(...)
  -> ContentWorldPlanner.plan(...)
  -> generation_world_profile
  -> StoryboardPlanner
  -> IPUsagePlanner.plan_batch(...)
  -> ip_adaptation
  -> PromptContextEnvelope.plan_context / frame_contexts
  -> build_image_prompt_prompt(...)
  -> 最终图片提示词
```

这里必须明确两个事实：

- `generation_world_profile` 进入 `plan_context`
- `ip_adaptation` 进入逐帧 `frame_contexts`

也就是说，当前主线已经不是“IP 设计页有个世界观字段，但最终图片提示词没吃进去”的状态，而是已经具备“资产级身份事实 + 请求级世界观 + 逐帧融入裁决”三层协同。

## 10. IP 融入规则中的使用方式

本次新增的 `generation_world_hint` 不只是给 storyboard 用，它还必须进入 IP 融入裁决。

### 10.1 它决定“这一篇内容里的 IP 应该像什么”

例如：

- 同一个白兔 IP，在童话解释类内容中可以是引导者
- 在城市漫游内容中可以是陪伴式主视角角色
- 在宗教、历史人物、严肃纪实内容中，它可能只能作为低侵入背景角色，甚至不出现

### 10.2 它决定“IP 可变层”的边界

固定不变的仍然是：

- 物种
- 主体配色
- 核心识别锚点
- 不能替代的语义边界

可变的则依据当前世界观生成：

- 动作
- 表情
- 服装
- 道具
- 站位
- 与主场景的关系
- 出场强度

### 10.3 它帮助解决“不能硬贴 IP”的问题

你前面举过的关键例子是对的：

- 如果文案明确出现佛祖、宗教人物、历史人物、古建筑主体
- IP 不能粗暴替代这些主体

因此推荐在 `generation_world_profile.story_constraints` 和 `ip_integration_guidance` 中明确承载：

- 哪些主体不可被 IP 替代
- 当前题材更适合 `strong_identity / balanced_narrative / scene_integrated / low_intrusion / symbolic_only / absent` 中的哪一类

## 11. 最终提示词中的优先级规则

为避免风格、世界观、IP 三者互相污染，正式规则推荐如下：

1. **原文事实和受保护主体优先**
   - 文案中明确的人物、事件、建筑、宗教主体不能被覆盖
2. **IP 语义边界优先**
   - 不能把 IP 强行变成不该替代的角色
3. **IP 固定身份优先于风格变化**
   - 风格可改渲染方式，不能改掉核心识别锚点
4. **本次文案世界观决定可变层**
   - 决定服装、动作、道具、氛围、站位
5. **世界预设决定分镜策略**
   - 决定画面组织方式和规划倾向
6. **风格提示词决定最终视觉表现**
   - 决定材质、镜头语言、光影和美术气质

这条优先级就是避免你前面担心的两个问题：

- 风格提示词把 IP 识别度洗掉
- IP 逻辑反过来破坏原文世界和主体

## 11.1 图片提示词中的实际融入原则

对 Z-Image 链路，当前主线的实际原则应明确写死，避免后续维护者退回“最小改动拼文本”的坏模式：

1. 最终图片提示词阶段必须同时参考：
   - `generation_world_profile`
   - `ip_adaptation`
   - 分镜上下文
   - 已解析的风格上下文

2. `generation_world_profile` 负责告诉提示词生成器：
   - 这次文案发生在什么世界
   - 哪些主体不能被替换
   - IP 应该如何融入，而不是是否存在一个长期默认设定

3. `ip_adaptation` 负责告诉提示词生成器：
   - 本帧 IP 是否出现
   - 以何种 presence type 出现
   - 哪些身份锚点需要可见，哪些需要抑制

4. 最终图片提示词字符串中不得泄露内部字段名：
   - `generation_world_profile`
   - `story_constraints`
   - `ip_integration_guidance`
   - `ip_adaptation`
   - 以及任何 JSON key、参数名、调试字段名

这保证了“IP 已经进入图片提示词链路”，同时避免把内部合同直接暴露成脆弱的 prompt 文本。

## 12. 失败与降级策略

为了保证生成链路稳定，推荐以下降级规则：

### 12.1 世界观自动生成失败

如果自动生成 `generation_world_profile` 失败：

- 不中断整条生成链路
- 回退到：
  - 原文文本
  - `world_preset_id`
  - `IPProfile.world_hint`
  - 当前 style profile

同时在 `planning_snapshot` 标记：

- `generation_world_hint_source = "empty"`
- `generation_world_profile_generation_failed = true`

### 12.2 用户没有填写也没有点击生成

如果生成页 `世界观提示` 为空：

- 后端可以自动基于文案补全世界画像
- 但不把这个结果回写到 IP 设计资产

### 12.3 用户点击“使用 IP 默认”但当前没有可用 IP

前端直接提示：

- 当前未启用 IP
- 或当前 IP 未配置默认世界观提示

## 13. 测试要求

这次设计对应的后续实现，至少要覆盖这些层面：

1. **合同层**
   - 请求参数能接收 `generation_world_hint`
   - 空字符串、空白字符、过长输入能被规范化
2. **模型层**
   - `ContentWorldProfile` 序列化、反序列化稳定
3. **服务层**
   - 自动从文案生成结构化世界画像
   - 能正确合并 IP 默认世界观和当前文案
4. **分镜层**
   - storyboard planner 能看到 `generation_world_profile`
5. **IP 规划层**
   - `IPUsagePlanner` 能消费新的世界画像
6. **最终提示词层**
   - image prompt prompt 能拿到世界画像，不泄露内部字段名
7. **前端层**
   - 新输入框渲染
   - 两个辅助按钮行为
   - 请求透传
8. **回归层**
   - 未启用 IP 的标准生成不能被破坏
   - 未填写世界观提示时的旧链路仍能工作

## 14. 非目标

本轮不做：

- 新建独立 AI Chat 式 IP 创作页
- 重做 IP 设计工作台整体布局
- 重做世界预设库
- 改造图生图能力
- 在本轮把 `generation_world_profile` 暴露成用户可编辑 JSON

这些都可以后续扩展，但不应该混进这轮“生成页世界观提示”源头改造里。

## 15. 最终建议

最终建议是：

- **保留 IP 设计页现有 `世界观提示`**
- **在生成页新增一个同名的 `世界观提示` 输入位**
- **用户看到的都是“世界观提示”，内部字段严格拆分**
- **把生成页世界观提示转换为结构化世界画像，再喂给高级分镜规划、IP 使用规划和最终提示词生成**

这是当前代码结构下改动最集中、语义最清晰、后续扩展成本最低、也最不容易留下技术债的方案。

补充说明：

- 该方案已经在 `dev` / `origin/dev` 落地
- 后续文档维护重点不再是“是否要这样设计”，而是“是否持续遵守这套事实源边界”
- 后续若继续扩展世界观能力，应新增后续 spec / plan，不应回退到“只加字段、直接拼 prompt”的做法
