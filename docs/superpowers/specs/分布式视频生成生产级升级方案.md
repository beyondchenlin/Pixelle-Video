# 分布式视频生成生产级升级方案

## 背景

当前系统已经完成 Postgres + Redis 的分布式生成注册中心：

- PostgreSQL 保存任务状态、请求指纹、结果 metadata。
- Redis 保存提交锁和 worker 执行 lease。
- Worker 使用任务 claim、heartbeat、fencing token、orphan running recovery 避免重复生成和僵尸任务卡死。
- Docker Compose 单宿主机场景下，API、Web、Worker 共享 `./output` 本地目录。

这个方案已经适合单机 Docker / 单宿主机多容器 / 多 worker 进程。但如果目标是多机器横向扩容，当前还缺共享 artifact 后端和基础设施高可用策略。

## 目标

将当前方案升级为生产级多机器部署：

- 多台 API 节点可以读取同一份视频产物。
- 多台 Worker 节点可以写入同一份视频产物。
- 任务状态、锁、产物 metadata 保持一致。
- worker 崩溃、节点重启、Redis lease 过期后任务可恢复。
- 生成完成后，历史视频和最近视频不依赖某台机器的本地磁盘。

## 非目标

- 不在第一阶段替换为 Celery、Temporal 或其他完整任务系统。
- 不在第一阶段重构 PixelleVideoCore 的生成流水线。
- 不把本地开发模式强制改成对象存储；本地 `local` artifact backend 继续保留。

## 当前方案评估

### 已符合最佳实践的部分

- 使用 PostgreSQL `FOR UPDATE SKIP LOCKED` 做 pending task claim，适合多 worker 队列消费。
- 使用 Redis TTL lease，worker 定时 heartbeat，避免永久锁死。
- 使用 `owner_id + lease_token` 作为 fencing token，完成/失败写入前确认当前 worker 仍拥有任务。
- 使用 generation fingerprint 做同请求去重。
- completed 任务复用前检查 artifact 是否存在，避免返回坏结果。
- running orphan task 可以在 lease 丢失后被新 worker 接管。

### 仍不完整的部分

- artifact backend 只有 `local`，多机器部署时 API 节点未必能读到 worker 节点生成的文件。
- Redis 当前按单实例配置，适合单宿主机或受控内网，不是高可用锁服务。
- Docker Compose 是单宿主机部署形态，不等于多机器生产部署。
- 任务执行仍是自研轻量队列，后续复杂度升高时需要评估 Celery / Temporal / Arq。

## 推荐目标架构

```text
Browser
  |
  v
Web / Streamlit
  |
  v
FastAPI API replicas
  |
  +--> PostgreSQL HA: generation_tasks authoritative state
  |
  +--> Redis HA: submit locks, worker execution leases
  |
  +--> S3 / MinIO: generated videos, images, audio, previews

Worker replicas
  |
  +--> PostgreSQL claim pending/orphan running tasks
  |
  +--> Redis heartbeat + fencing lease
  |
  +--> S3 / MinIO persist final artifacts
```

## 关键升级项

### 1. 新增 S3 / MinIO ArtifactStore

新增 `S3ArtifactStore`，与当前 `LocalArtifactStore` 实现同一协议：

- `persist_video(task_id, source_path, duration) -> dict`
- `exists(storage_key) -> bool`
- 可选新增 `open_read(storage_key)` 或 `build_presigned_url(storage_key)`

推荐 metadata：

```json
{
  "storage_backend": "s3",
  "bucket": "pixelle-artifacts",
  "storage_key": "generation/task-id/final.mp4",
  "video_url": "/api/files/generation/task-id/final.mp4",
  "file_size": 1234567,
  "duration": 12.3,
  "content_type": "video/mp4"
}
```

配置项：

```env
PIXELLE_ARTIFACT_BACKEND=s3
PIXELLE_S3_ENDPOINT_URL=http://minio:9000
PIXELLE_S3_BUCKET=pixelle-artifacts
PIXELLE_S3_ACCESS_KEY=...
PIXELLE_S3_SECRET_KEY=...
PIXELLE_S3_REGION=us-east-1
PIXELLE_S3_FORCE_PATH_STYLE=true
PIXELLE_ARTIFACT_BASE_URL=/api/files
```

验收标准：

- Worker A 上传的视频，API B 可以通过 `/api/files/...` 读取。
- `recent_completed` 复用时通过对象存储 `HEAD` 判断文件存在。
- 删除本地 `output` 后，历史视频仍可访问。

### 2. 文件服务支持对象存储读取

当前 `/api/files/{file_path}` 只从本地 allowed roots 读取。升级后：

- `local` backend：继续走本地 `FileResponse`。
- `s3` backend：根据 `storage_key` 从对象存储流式读取，或返回 presigned URL。

建议优先实现 API 代理流式读取，保持前端 URL 不变：

```text
GET /api/files/generation/task-id/final.mp4
  -> ArtifactStore.open_read("generation/task-id/final.mp4")
  -> StreamingResponse
```

安全要求：

- storage key 必须 normalize。
- 禁止 `..`、绝对路径、空 key。
- 只允许访问配置 bucket/prefix 下的对象。

### 3. 任务结果统一使用 storage_key

当前部分历史系统仍偏向 `video_path` 本地路径。升级后：

- DB task result 以 `storage_key` 为主。
- `video_url` 为 API 可访问 URL。
- `video_path` 仅用于 local backend 兼容，不作为跨机器 contract。

迁移策略：

- 新任务写 `storage_backend/storage_key/video_url`。
- 旧任务如果只有 `video_path`，在读取历史时转换为 local artifact item。
- 历史页和最近视频组件优先使用 `video_url`，只有本地模式才直接用 `video_path`。

### 4. Redis 高可用与锁策略

当前 Redis 单实例适合 Docker Compose。生产建议：

- Redis Sentinel / Redis Cluster / 云 Redis。
- 开启持久化或使用托管 Redis。
- 配置合理的 lease TTL 和 heartbeat：
  - `PIXELLE_GENERATION_LEASE_TTL_SECONDS=120`
  - `PIXELLE_GENERATION_HEARTBEAT_SECONDS=30`
  - heartbeat 必须小于 TTL。

正确性原则：

- Redis lease 只表示临时执行权。
- PostgreSQL `owner_id + lease_token` 是最终写入 fencing。
- 完成/失败写入必须同时通过 DB token 与 Redis lease 校验。

### 5. PostgreSQL 生产配置

推荐：

- 托管 PostgreSQL 或主从 HA。
- `generation_tasks` 表定期 vacuum/analyze。
- 为 completed 历史做归档或 TTL 清理策略。
- 为 `status, created_at`、`generation_fingerprint, status`、pending claim 保留索引。

后续可新增：

- `lease_expires_at` 字段，降低 orphan running recovery 对 Redis 的依赖。
- `attempt_count`、`max_attempts`、`last_heartbeat_at` 字段，用于重试策略和可观测性。
- dead-letter 状态，例如 `exhausted`。

### 6. Worker 重试与幂等策略

建议补齐：

- `attempt_count`。
- `max_attempts`。
- `retryable_error` 分类。
- 指数退避。
- 永久失败进入 dead-letter。

关键原则：

- 同一 fingerprint 的 active task 仍只能有一个。
- artifact 上传必须幂等：同 task_id 的 `final.mp4` 重试覆盖或版本化，策略必须明确。
- 旧 worker 完成后如果 fencing 失败，不得覆盖新状态。

### 7. 可观测性与运维

新增指标：

- pending task count
- running task count
- orphan recovered count
- heartbeat failure count
- lease lost count
- task duration histogram
- artifact upload failure count
- duplicate request reuse count

新增日志字段：

- `task_id`
- `generation_fingerprint`
- `owner_id`
- `lease_token` hash
- `worker_id`
- `storage_backend`
- `storage_key`

## 分阶段实施计划

### 阶段 1：S3 / MinIO ArtifactStore

1. 新增 `S3ArtifactStore`。
2. `build_task_manager()` 支持 `PIXELLE_ARTIFACT_BACKEND=s3`。
3. `/api/files` 支持 S3 streaming。
4. 历史和最近视频优先使用 `video_url/storage_key`。
5. 增加 MinIO docker-compose profile。

验收：

- API 和 Worker 分别运行在不同容器且不共享 `./output` 时，视频可生成、可预览、可下载。

### 阶段 2：任务重试与 dead-letter

1. 数据库 migration 增加 `attempt_count/max_attempts/last_heartbeat_at`。
2. Worker claim 时递增 attempt。
3. 可重试失败回 pending，超过次数进入 failed/dead-letter。
4. UI 显示失败原因和重试次数。

验收：

- 模拟 worker 进程被杀，任务可被接管。
- 模拟生成错误，任务按策略重试并最终可观察。

### 阶段 3：生产部署模板

1. 新增 `docker-compose.prod.yml` 或 Helm chart。
2. Redis 使用 Sentinel/托管服务说明。
3. PostgreSQL 使用托管服务说明。
4. MinIO/S3 bucket 初始化脚本。
5. 健康检查和 readiness probe。

验收：

- 两个 API replica、两个 worker replica、一个 MinIO、一个 Postgres、一个 Redis 环境下通过端到端生成测试。

### 阶段 4：评估成熟队列系统

当任务类型增多、重试策略复杂、需要工作流编排时，评估：

- Celery：成熟 Python 队列，适合普通异步任务。
- Arq / RQ：轻量 Redis 队列。
- Temporal：适合长工作流、强恢复、复杂状态机。

迁移原则：

- 保留 generation fingerprint 和 artifact contract。
- 任务状态仍要能服务现有 UI。
- 不为了换队列牺牲视频生成幂等性。

## 风险与取舍

| 方案 | 优点 | 风险 |
| --- | --- | --- |
| 保持 Postgres + Redis 自研队列 | 与现有业务契合，改动可控 | 后续重试、调度、监控复杂度会上升 |
| 引入 Celery | 成熟、生态完整 | 需要适配现有 fingerprint/task UI/result 模型 |
| 引入 Temporal | 长工作流恢复能力强 | 引入成本和运维复杂度高 |
| S3/MinIO artifact | 多机器必需，解耦本地磁盘 | 需要处理权限、流式读取、对象清理 |

## 最终建议

短期最佳路径：

1. 保留当前 Postgres + Redis 任务协调方案。
2. 优先补 S3/MinIO artifact backend。
3. 增加 retry/dead-letter 和 observability。
4. 生产部署显式使用 Redis HA、PostgreSQL HA、对象存储。

不要继续在本地文件系统上叠加多机器能力。本地 `output` 只能作为开发和单宿主机 Docker 模式，不能作为生产横向扩容基础。
