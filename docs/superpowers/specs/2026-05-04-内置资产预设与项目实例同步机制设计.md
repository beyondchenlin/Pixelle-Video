# 内置资产预设与项目实例同步机制设计

## 1. 结论

当前不能把 `output/_platform/assets/assets.json` 提交到 GitHub。该文件属于运行态数据，包含用户当前机器上的项目实例、临时状态和生成链路副产物，不应成为团队共享资产源。

正确方案是建立一套统一的资产生命周期：

1. **内置预设层**：随代码发布，Git 管理，只读。
2. **项目实例层**：用户从内置预设导入或自己创建，可编辑，保存在本地持久化目录。
3. **运行产物层**：生成结果、日志、缓存和中间状态，保存在 `output/`，不作为知识资产源。

这套机制要覆盖 AssetBible/IP，并和现有模板库、风格提示词前缀库、高级分镜预设保持同一生命周期语义。模板、风格前缀、分镜预设不需要被强行塞进一个大而全的通用抽象，但必须遵守相同的来源、实例化、版本、升级和覆盖规则。

## 2. 背景

现有仓库里已经存在几种不同成熟度的资产机制：

- 模板库已经有 `templates/` 内置模板和 `data/templates/` 用户覆盖机制。
- 图片提示词前缀库已经有代码内置项和 `config.yaml` 用户库。
- 高级分镜世界预设与镜头预设已经是代码内置库。
- AssetBible/IP 目前主要保存到 `output/_platform/assets/assets.json`，缺少代码随包发布的内置预设层。

因此用户部署后能获得模板、风格前缀、分镜预设，但不能天然获得团队沉淀的正式 IP/AssetBible。把 `output/` 提交到 GitHub 可以短期看见数据，但会把运行态和产品资产混在一起，后续会形成不可控技术债。

## 3. 目标

本设计要实现以下目标：

1. 团队精选的 AssetBible/IP 可以随代码发布，用户部署后即可浏览和导入。
2. 用户导入内置 IP 后得到当前项目自己的可编辑副本，不直接修改内置源。
3. 生成链路引用项目实例快照，不直接引用会随版本升级变化的内置预设。
4. 内置预设升级时，系统能识别项目实例基于哪个旧版本，并提供显式升级或合并入口。
5. `output/` 继续只承担运行产物职责，不再作为正式知识资产源。
6. 模板、风格前缀、分镜预设、AssetBible/IP 在 UI 和 API 上呈现统一的来源与同步语义。

## 4. 非目标

本设计不包含以下内容：

1. 不把 `output/` 纳入 Git 管理。
2. 不把所有预设类型强行重构成单一超级模型。
3. 不在生成时静默覆盖用户已经编辑过的项目实例。
4. 不把 SceneCast、PromptPlan、生成 artifact 设计成全局内置预设。它们属于项目过程数据或生成结果。
5. 不引入运行时猜测逻辑从 `style_hint` 自动推导 IP 身份锚点。

## 5. 分层模型

### 5.1 内置预设层

内置预设层由 Git 管理，随代码发布，默认只读。

推荐路径：

```text
resources/presets/
  asset_bibles/
    zhengding_guide_bible.json
  prompt_prefixes/
    prompt_prefix_library.json
  storyboard/
    storyboard_preset_library.json
```

第一阶段只要求新增 `resources/presets/asset_bibles/`。风格前缀和分镜预设已经有代码内置实现，后续可以逐步外置到同一目录结构，但不是本次机制落地的前置条件。

### 5.2 项目实例层

项目实例层保存用户导入或创建后的可编辑副本。该层不进 Git，默认放在 `data/` 下。

推荐路径：

```text
data/platform/
  assets/
    assets.json
```

当前 dev 平台仓储仍使用 `output/_platform/assets/assets.json`。新机制落地时应把 AssetBible 的正式持久化根从 `output/_platform/assets` 迁移到 `data/platform/assets` 或等价的可配置持久化目录。`output/_platform/assets` 只能作为兼容读取来源，不能继续作为主写入位置。

### 5.3 运行产物层

运行产物层继续使用 `output/`。

包括：

- 生成结果目录
- metadata
- storyboard 临时输出
- prompt trace
- artifact 结果
- 失败日志

运行产物层不得作为团队共享资产源，也不得要求提交到 GitHub。

## 6. 统一来源语义

所有可复用资产都应具备可解释来源。

建议统一使用以下来源类型：

- `builtin`：随代码发布的只读内置预设。
- `user`：用户在本地创建或编辑的项目实例。
- `imported`：从内置预设导入后形成的项目实例。
- `generated`：AI 辅助生成后被用户保存的项目实例。

当前模板系统使用 `system/user`，提示词前缀使用 `builtin/manual/llm`。不要求立即重命名既有字段，但 UI 与服务层应把这些来源映射到统一语义：

| 领域 | 现有来源 | 统一语义 |
| --- | --- | --- |
| 模板 | `system` | `builtin` |
| 模板 | `user` | `user` |
| 风格前缀 | `builtin` | `builtin` |
| 风格前缀 | `manual` | `user` |
| 风格前缀 | `llm` | `generated` |
| 分镜预设 | 代码内置 | `builtin` |
| AssetBible/IP | 新增内置预设 | `builtin` |
| AssetBible/IP | 项目保存数据 | `user` 或 `imported` |

## 7. AssetBible 内置预设契约

### 7.1 文件形状

每个内置 AssetBible 预设使用一个 JSON 文件。文件必须包含预设元数据和完整 AssetBible payload。

```json
{
  "preset_id": "builtin_asset_bible_zhengding_guide",
  "revision": "2026-05-04.1",
  "source": "builtin",
  "display_name": "正定向导兔",
  "description": "面向正定古城文旅短视频的陪伴式导游 IP。",
  "tags": ["文旅", "正定", "导游IP", "卡通角色"],
  "preview_asset_path": "resources/presets/asset_bibles/previews/zhengding_guide.png",
  "asset_bible": {
    "asset_bible_id": "zhengding_guide_bible",
    "workspace_id": "__builtin__",
    "project_id": "__builtin__",
    "ip_profiles": [],
    "character_profiles": [],
    "scene_assets": [],
    "prop_assets": [],
    "style_profiles": [],
    "metadata": {}
  }
}
```

`asset_bible` 内部必须符合 `pixelle_video.models.asset_bible.AssetBible` 的正式结构。内置文件中的 `workspace_id` 和 `project_id` 使用保留值 `__builtin__`，导入项目时由服务替换为真实 workspace/project。

## 8. 项目实例契约

项目实例是用户可编辑的 AssetBible。它的主体仍然是正式 `AssetBible` payload，但 metadata 中必须记录来源。

导入内置预设后，项目实例应写入：

```json
{
  "metadata": {
    "source_kind": "imported",
    "origin_preset_id": "builtin_asset_bible_zhengding_guide",
    "origin_revision": "2026-05-04.1",
    "imported_at": "2026-05-04T00:00:00Z",
    "customized": false
  }
}
```

用户编辑保存后，服务应把 `metadata.customized` 置为 `true`，并保留 `origin_preset_id` 与 `origin_revision`。这能支持后续提示“该项目实例基于旧版内置预设，但已经被用户修改过”。

## 9. 导入与同步生命周期

### 9.1 浏览

用户打开 IP/AssetBible 选择器时，UI 应显示两组：

1. 当前项目资产
2. 内置资产库

内置资产库只读，不直接进入生成链路。

### 9.2 导入

用户选择内置 AssetBible 后，调用导入接口：

```text
POST /api/projects/{project_id}/asset-bible/import-from-preset
```

请求参数：

```json
{
  "workspace_id": "workspace_1",
  "preset_id": "builtin_asset_bible_zhengding_guide",
  "asset_bible_id": "zhengding_guide_bible",
  "conflict_policy": "fail"
}
```

导入服务必须：

1. 读取内置预设。
2. 校验预设 payload。
3. 替换 `workspace_id` 和 `project_id`。
4. 写入来源 metadata。
5. 保存到项目实例仓储。
6. 返回项目实例 AssetBible。

如果目标 `asset_bible_id` 已存在，默认 `conflict_policy="fail"`，不能静默覆盖。后续可以支持 `duplicate` 生成新 ID，或 `replace` 显式替换。

### 9.3 编辑

用户编辑项目实例时，只修改项目实例，不修改内置预设文件。

保存时使用现有项目级 AssetBible API：

```text
PUT /api/projects/{project_id}/asset-bible/{asset_bible_id}
```

### 9.4 生成

正式生成只允许引用项目实例：

- `ip_enabled=true`
- `ip_asset_bible_id=<project instance id>`
- `ip_profile_id=<profile id>`

生成链路不得直接使用 `preset_id`。如果 UI 允许用户从内置库选择，必须先导入，再把导入后的 `asset_bible_id` 写入生成配置。

### 9.5 升级

当内置预设 revision 升级，项目实例不自动覆盖。UI 应显示状态：

- `up_to_date`：项目实例的 `origin_revision` 等于当前内置 revision。
- `upstream_updated`：内置 revision 更新，项目实例未同步。
- `customized_upstream_updated`：内置 revision 更新，且项目实例已被用户编辑。
- `detached`：项目实例没有来源，属于纯用户资产。

第一阶段只需要能识别状态并提示。自动三方合并可以后续实现。

## 10. API 设计

### 10.1 内置 AssetBible 预设列表

```text
GET /api/presets/asset-bibles
```

响应：

```json
{
  "items": [
    {
      "preset_id": "builtin_asset_bible_zhengding_guide",
      "revision": "2026-05-04.1",
      "display_name": "正定向导兔",
      "description": "面向正定古城文旅短视频的陪伴式导游 IP。",
      "tags": ["文旅", "正定", "导游IP", "卡通角色"],
      "preview_asset_path": "resources/presets/asset_bibles/previews/zhengding_guide.png"
    }
  ]
}
```

### 10.2 内置 AssetBible 预设详情

```text
GET /api/presets/asset-bibles/{preset_id}
```

响应包含完整预设元数据与 `asset_bible` payload。

### 10.3 导入到项目

```text
POST /api/projects/{project_id}/asset-bible/import-from-preset
```

该接口返回现有 `AssetBibleResponse` 形状，方便 UI 直接把导入结果加入当前项目资产列表。

## 11. UI 设计

### 11.1 IP 设计工作台

IP 设计工作台应增加“内置资产库”入口：

- 展示内置 AssetBible 卡片
- 查看详情
- 导入到当前项目
- 导入后跳转到项目实例编辑状态

项目实例列表中应展示来源状态：

- 内置导入
- 用户自建
- 上游有更新
- 已自定义

### 11.2 生成页 IP 选择

生成页只展示可生成的项目实例。若用户从内置库直接选中一个 IP，UI 应引导先导入，不能把 builtin preset 直接作为生成参数传入。

### 11.3 风格前缀与分镜预设

风格前缀库和分镜预设本阶段不需要重构存储，但 UI 文案应逐步统一：

- 内置
- 用户
- AI 生成
- 当前项目

这可以降低用户理解成本，避免“模板库、风格库、IP 库各说各话”。

## 12. 迁移策略

### 12.1 当前本地数据

当前存在的 `output/_platform/assets/assets.json` 不能直接提交。它应作为本地迁移来源。

实施时提供迁移命令或 UI 操作：

```text
pixelle asset-bible migrate-output-assets --workspace-id workspace_1 --project-id project_1
```

迁移行为：

1. 读取 `output/_platform/assets/assets.json`。
2. 校验每个 AssetBible。
3. 写入新的项目实例仓储。
4. 保留原文件，不删除。
5. 输出迁移报告。

### 12.2 仓储默认根迁移

平台依赖构建时，AssetBible 仓储应从 `output/_platform/assets` 改为 `data/platform/assets` 或配置项指定的持久化根。

为了兼容旧本地环境，读取路径可以短期支持：

1. 主路径：`data/platform/assets`
2. 兼容路径：`output/_platform/assets`

写入只能写主路径，避免继续扩大旧债。

## 13. 验证要求

实施完成后至少要有以下验证：

1. 内置 AssetBible JSON 能被加载并通过 `AssetBible.from_dict` 校验。
2. 正定向导兔内置预设的 `identity_lock + identity_anchors` 无重复项。
3. 导入内置预设后，项目实例的 workspace/project 被正确替换。
4. 导入不会修改内置预设文件。
5. 目标 `asset_bible_id` 冲突时默认失败。
6. 生成页不能直接把 builtin preset id 作为 `ip_asset_bible_id` 使用。
7. 原有项目级 AssetBible API 仍能保存和读取用户编辑后的项目实例。
8. `output/` 没有被加入 Git 跟踪。

## 14. 分阶段实施

### 阶段一：AssetBible 内置预设与导入

实现：

- 内置 AssetBible 预设模型
- 文件加载器
- 预设列表/详情 API
- 导入到项目 API
- 正定向导兔内置预设 JSON
- 项目实例来源 metadata
- 基础 UI 入口

### 阶段二：项目实例持久化根迁移

实现：

- AssetBible 仓储主路径迁移到 `data/platform/assets`
- `output/_platform/assets` 兼容读取
- 本地迁移命令或 UI 迁移入口
- 迁移报告

### 阶段三：来源状态与升级提示

实现：

- 识别 `up_to_date`
- 识别 `upstream_updated`
- 识别 `customized_upstream_updated`
- UI 展示上游版本状态
- 明确提示用户手动导入新版本或保留当前项目实例

### 阶段四：统一资产库体验

实现：

- 风格前缀库来源文案统一
- 分镜预设来源文案统一
- 模板库来源文案统一
- 后续可选地把提示词前缀和分镜预设外置到 `resources/presets/`

## 15. 设计决策

1. **生成绑定项目实例，不绑定 builtin**  
   避免代码升级导致旧项目生成结果漂移。

2. **内置预设只读**  
   用户编辑必须先导入或复制，避免误以为修改了团队默认资产。

3. **`output/` 不再承担资产源职责**  
   运行产物和知识资产必须分开。

4. **各领域保留独立模型**  
   不为统一而统一。模板、风格前缀、分镜、AssetBible 的业务结构不同，只统一生命周期和来源语义。

5. **升级显式化**  
   内置预设变更后，只提示，不静默覆盖用户项目实例。

## 16. 成功标准

本机制落地后，新部署用户应能直接看到团队发布的“正定向导兔”等内置 IP 资产，并能导入到自己的项目中编辑和生成。团队可以通过 Git 提交内置预设文件来发布精选资产，用户运行数据仍留在本地持久化目录，`output/` 继续只保存生成结果和运行痕迹。
