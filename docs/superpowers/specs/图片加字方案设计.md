# 图片加字方案设计 v3 - 平台级文字层架构

## 1. 背景与版本结论

Pixelle 的目标不是只做一个“把几个字贴到图片上”的小功能，而是继续演进成一个大的内容创作平台。  
因此 v3 不再以“最小改动”为主导，而是以“平台原语优先、分阶段落地”为主导。

本方案把“图片加字”升级为平台级 **Text Layer** 能力：

1. 字幕、重点词、角标、标题、模板文字、模型原生画字提示，都属于文字层能力。
2. 不同渲染方式只是后端：HyperFrames / HTML / ASS / 模型原生文字 / Python fallback。
3. 所有后端必须消费同一套语义规划与时间线契约，不能各自维护一套平行时间线。
4. `RenderManifest` 和 `TemplateRenderContext` 是平台级渲染契约，新增文字能力必须接入这条主线。
5. `TextOverlayPlan` 只负责语义规划，不负责成为最终时间线事实来源。

v3 的核心结论：

> Pixelle 应该新增统一的 `TextTrack / TextCue` 平台模型，并把图片加字作为第一个消费场景落地。  
> HTML、ASS、模型原生画字都不再直接从零解析文本，而是从同一个文字层契约中派生。

## 2. 已有平台基础

当前项目里已经有几条与平台化方向一致的基础：

1. 主创作链路已经清晰  
   `Quick Create -> Standard Pipeline -> 文案 -> 图像提示词 -> TTS -> 分镜资产 -> 最终合成`

2. HyperFrames-first 方向已经在设计文档中确立  
   `docs/superpowers/specs/2026-04-21-pixelle-hyperframes-rendering-architecture-design.md`

3. compiled HyperFrames 已经要求 canonical timeline  
   `docs/superpowers/specs/2026-04-22-pixelle-hyperframes-compiled-project-design.md`

4. `RenderManifest` 已经承载视觉、音频、字幕等最终渲染信息  
   `pixelle_video/models/render_package.py`

5. `TemplateRenderContext` 已经被定义为 compiled HyperFrames 的唯一任务输入契约  
   `pixelle_video/models/template_render_context.py`

6. `TimingPlan / SentenceUnit / AlignmentService` 已经提供句级和块级时间线基础  
   `pixelle_video/services/timing_planner.py`  
   `pixelle_video/services/alignment_service.py`

7. 观测性文档已经要求创作链路可追踪、可诊断、可复盘  
   `docs/superpowers/specs/2026-04-24-log-persistence-and-ai-creation-observability-design.md`

8. 内容创作平台总纲已经定义平台级创作契约  
   `docs/superpowers/specs/内容创作平台整体规划设计.md`

   其中 `CreationPackage` 是平台内部的创作资产模型，`RenderManifest v2` 是渲染执行模型。文字层必须挂在这个总契约下，不能只挂在 `StandardPipeline` 的临时上下文里。

这些基础说明：图片加字不应该另起一套小系统，而应该补齐平台文字层。

## 3. 设计原则

### 3.1 平台原语优先

不要把需求建模成“图片加字开关”。  
应该建模成：

1. 文本语义从哪里来
2. 文本属于哪条轨道
3. 文本在什么时间出现
4. 文本在什么布局槽位出现
5. 文本应该由哪个 renderer 消费
6. 文本渲染结果如何被调试、复现、对比

### 3.2 单一时间线事实来源

所有字幕和重点词都必须最终落到 canonical timeline。  
允许第一阶段用规则映射生成时间，但规则映射后的结果也必须编译成统一 `TextCue`，而不是留在某个 renderer 内部。

### 3.3 语义规划与渲染契约分离

`TextOverlayPlan` 是规划结果，回答“哪些词重要、建议放在哪里、属于什么角色”。  
`TextCue` 是渲染契约，回答“具体文本在全局时间线的几秒到几秒出现、用哪个轨道、哪个布局槽位、哪个样式”。

### 3.4 Renderer 可替换

同一批文字 cue 可以被多个 renderer 消费：

1. HyperFrames / HTML：主力精美渲染
2. ASS：legacy 最终视频层烧录与字幕兼容
3. 模型原生文字：作为图像生成 prompt hint
4. Python 绘图：只做 fallback 或离线工具，不作为主路线

### 3.5 可观测、可复现、可 A/B

每次生成都应该能回答：

1. 哪些原文被抽成重点词
2. 哪些重点词进入了 prompt
3. 哪些重点词进入了稳定叠字
4. 每个 cue 的时间、位置、样式从哪里来
5. 最终用了哪个 renderer
6. 哪个 renderer 更快、更稳定、效果更好

## 4. 核心数据模型

### 4.1 TextRenderingPolicy

统一管理“模型是否允许在图中生成文字”的策略，避免多个布尔字段互相冲突。

建议字段：

```python
@dataclass(frozen=True)
class TextRenderingPolicy:
    version: str = "text_rendering_policy.v1"
    image_text_mode: str
    enabled_targets: tuple[str, ...]
    density: str
    max_items_per_frame: int
    allow_native_text_in_image: bool
    suppress_unplanned_embedded_text: bool
```

`image_text_mode` 建议取值：

1. `suppress`：禁止模型自行画字，适合稳定后期叠字。
2. `native_hint`：允许模型按提示词画部分文字。
3. `programmatic_only`：只允许 HTML / ASS / HyperFrames 文字层。
4. `hybrid`：模型原生文字和程序文字层都开启，用于实验对比。

### 4.2 TextOverlayPlan

语义规划层，不是最终时间线。

建议职责：

1. 从 narration / prompt source / storyboard 中抽取关键词、短句、标签。
2. 给每个候选文本标注角色：`keyword`、`headline`、`subtitle_phrase`、`corner_label`、`callout`。
3. 给出建议槽位：`center`、`lower_third`、`top_left`、`corner_badge`。
4. 给出 renderer 目标建议：`native_prompt`、`html`、`ass`、`hyperframes`。
5. 给出重要性、置信度、来源 span。

它可以作为调试产物落盘：

```text
text_overlay_plan.json
```

但它不能成为最终渲染事实来源。

### 4.3 TextTrack

平台级文字轨道。

建议字段：

```python
@dataclass(frozen=True)
class TextTrack:
    version: str = "text_track.v1"
    id: str
    kind: str
    name: str
    enabled: bool = True
    renderer_targets: tuple[str, ...] = ()
    style_profile: str | None = None
    layer: int = 0
```

`kind` 建议取值：

1. `caption`：字幕轨
2. `overlay`：重点词 / 重点短句轨
3. `template`：模板固定文字轨
4. `native_hint`：模型原生画字提示轨
5. `debug`：调试轨

### 4.4 TextCue

平台级文字 cue，是最终渲染契约。

建议字段：

```python
JSONValue = str | int | float | bool | None | list["JSONValue"] | dict[str, "JSONValue"]

@dataclass(frozen=True)
class TextCue:
    version: str = "text_cue.v1"
    id: str
    track_id: str
    text: str
    start: float
    end: float
    role: str
    frame_indices: tuple[int, ...] = ()
    slot: str | None = None
    layout: Mapping[str, JSONValue] = field(default_factory=dict)
    style_profile: str | None = None
    layer: int = 0
    priority: int = 0
    language: str | None = None
    source: Mapping[str, JSONValue] = field(default_factory=dict)
```

实现时必须在 `__post_init__` 或 `from_dict(...)` 中对 `layout` 和 `source` 做 canonical copy / immutable wrapper，避免 frozen dataclass 内部仍持有可变 dict，影响缓存、复跑和 A/B 对比。

`CaptionCue` 不应被强行扩展成所有文字类型的容器。  
推荐做法是：

1. 保留现有 `CaptionCue` 兼容旧字幕逻辑。
2. 新增 `TextTrack / TextCue`。
3. 在迁移期把 `CaptionCue` 映射成 `TextTrack(kind="caption") + TextCue(role="subtitle")`。
4. 等 HyperFrames 路线稳定后，再考虑是否合并旧 caption 模型。

### 4.5 RenderManifest 扩展

`RenderManifest` 应新增文字层字段：

```python
text_tracks: List[TextTrack]
text_cues: List[TextCue]
```

保留：

```python
caption_cues: List[CaptionCue]
```

用于兼容现有 compiled HyperFrames 字幕逻辑。

长期目标是：

```text
CaptionCue -> TextTrack(kind="caption") + TextCue(role="subtitle")
OverlayText -> TextTrack(kind="overlay") + TextCue(role="keyword" | "callout")
TemplateText -> TextTrack(kind="template") + TextCue(role="template_slot")
NativeTextHint -> TextTrack(kind="native_hint") + TextCue(role="native_hint")
```

也就是说，`kind` 只属于 `TextTrack`，`role` 只属于 `TextCue`。实现和文档都不再把轨道类型写进 cue 构造参数。

### 4.6 与内容创作平台总契约的关系

文字层必须遵守平台总纲中的边界：

```text
CreationRequest
  -> CreationRun
  -> CreationPackage
  -> RenderManifest v2
  -> TemplateRenderContext / renderer adapters
```

推荐归属：

1. `TextRenderingPolicy` 属于 `CreationRequest` 的派生策略。
2. `TextOverlayPlan` 属于 `CreationPackage`，和 `content_plan / storyboard_plan / prompt_plan / audio_plan` 同级。
3. `TextTrack / TextCue` 属于 `RenderManifest v2`，是渲染执行事实。
4. `TemplateRenderContext` 只消费已经编译后的文字层，不重新规划文字。
5. `StandardPipeline` 只是当前 legacy 入口和过渡适配层，不能成为文字层契约 owner。

代码 owner 建议与总纲保持一致：

```text
pixelle_video/models/text_overlay.py        # TextOverlayPlan / TextRenderingPolicy
pixelle_video/models/render_package.py      # TextTrack / TextCue / RenderManifest v2
pixelle_video/models/template_render_context.py
```

## 5. 平台级数据流

推荐主链路：

```text
用户输入 / 脚本 / 主题
  -> CreationRequest
  -> CreationRun
  -> CreationPackage
  -> 内容生成与分镜规划
  -> TimingPlan / SentenceUnit
  -> TextOverlayPlanner 写入 CreationPackage.text_overlay_plan
  -> TextCueCompiler 编译 CreationPackage -> RenderManifest v2
  -> RenderManifest v2 写入 text_tracks / text_cues
  -> TemplateRenderContext 暴露给 HyperFrames / HTML
  -> ASS exporter / renderer adapters
  -> 最终视频、调试产物、观测性摘要
```

### 5.1 pre-image-generation projection

模型原生画字不能等到 `RenderManifest` 之后再适配。  
当前标准链路会在 `plan_visuals` 阶段调用 `generate_styled_image_prompt_batch(...)` 生成图像 prompt，因此 native prompt 必须在出图 prompt 生成前完成投影。

推荐前置链路：

```text
CreationPackage.text_overlay_plan
  -> NativePromptProjection
  -> native_prompt_hints
  -> generate_styled_image_prompt_batch(...)
  -> StyledImagePromptBatch
```

规则：

1. `NativePromptProjection` 只消费 `TextOverlayPlan` 中 role 为 `model_native_hint` 或 renderer target 包含 `native_prompt` 的候选文本。
2. 如果当前阶段还没有完整 `TextCue` 时间线，也可以先用 narration / storyboard frame / prompt source 生成受控数量的 native hints。
3. 如果 native hints 不能在 prompt batch 生成前得到，就必须禁用本次 native prompt 注入，不能在出图后补一个无效 adapter。
4. native prompt 注入结果必须回写到调试产物和观测性摘要中，记录注入了哪些文本、数量多少、来自哪段原文。

### 5.2 render-time compilation

稳定叠字、字幕、ASS、HyperFrames 都走渲染期编译：

```text
CreationPackage.text_overlay_plan
  + TimingPlan / SentenceUnit
  + Storyboard
  -> TextCueCompiler
  -> RenderManifest v2.text_tracks / text_cues
```

这个阶段负责把语义规划变成 canonical timeline 上的 `TextTrack / TextCue`。

### 5.3 TextOverlayPlanner

新增轻量服务：

```text
pixelle_video/services/text_overlay_planner.py
```

职责：

1. 输入 narration、storyboard frames、style profile、用户文字层配置。
2. 输出 `TextOverlayPlan`。
3. 不依赖具体 renderer。
4. 不直接修改 `StyledImagePromptBatch`。

### 5.4 TextCueCompiler

新增轻量服务：

```text
pixelle_video/services/text_cue_compiler.py
```

职责：

1. 输入 `TextOverlayPlan`、`TimingPlan`、`Storyboard`。
2. 输出 `TextTrack / TextCue`。
3. 统一处理 frame-relative、sentence-relative、word-level alignment 三类时间来源。
4. 给不同 renderer 打目标标签，但不执行渲染。

### 5.5 Renderer Adapters

每个 renderer 只做适配：

1. `HyperFramesTextAdapter`：把 `TextCue` 写入 `TemplateRenderContext`。
2. `AssTextAdapter`：把 `TextCue` 导出为 `master.ass`。
3. `HtmlFrameTextAdapter`：给 legacy HTML frame overlay 使用。
4. `PythonTextAdapter`：只作为 fallback 或 debug。

这样 renderer 可以替换，文字层数据不需要重算。

## 6. API 与 UI 设计

### 6.1 API 不再铺满顶层布尔字段

不推荐新增大量顶层字段：

```text
enable_html_text_overlay
enable_ass_text_overlay
enable_ass_subtitle_track
enable_ass_overlay_track
enable_model_native_text_rendering
...
```

这些字段会在平台扩展时快速失控。

推荐新增一个嵌套对象：

```python
class TextLayerRequest(BaseModel):
    enabled: bool = False
    mode: Literal["suppress", "programmatic_only", "native_hint", "hybrid"] = "programmatic_only"
    renderer_targets: list[Literal["hyperframes", "html", "ass", "native_prompt"]] = Field(default_factory=list)
    caption_enabled: bool = True
    overlay_enabled: bool = False
    density: Literal["low", "medium", "high"] = "medium"
    max_items_per_frame: int = 2
    style_preset: str = "default"
    debug_artifacts: bool = False
```

现有 `forbid_embedded_text_in_image` 可以保留兼容，但内部应统一转换成 `TextRenderingPolicy`。

### 6.2 UI 命名

UI 不应叫“图片加字”一个孤立功能。  
建议命名为：

```text
文字层
```

UI 分组：

1. 总开关：启用文字层
2. 输出目标：稳定叠字 / 模型原生文字 / 字幕 / 调试对比
3. 文字密度：少 / 中 / 多
4. 轨道：
   - 字幕轨
   - 重点词轨
   - 模板文字轨
   - 模型原生提示轨
5. 渲染方式：
   - HyperFrames / HTML
   - ASS
   - Native prompt
6. 调试产物：
   - `text_overlay_plan.json`
   - `render_manifest.json`
   - `master.ass`
   - `subtitle_only.ass`
   - `overlay_only.ass`

### 6.3 UI 实现边界

`web/components/style_config.py` 已经很大，后续不建议继续把文字层 UI 堆进去。  
推荐新增：

```text
web/components/text_layer_config.py
```

它只负责收集文字层配置，再由现有 Quick Create payload builder 合并到请求里。

## 7. 各渲染路线定位

### 7.1 HyperFrames / HTML

定位：主力精美文字渲染路线。

原因：

1. 最适合模板化、动画、布局、字体、响应式适配。
2. 能直接消费 `TemplateRenderContext`。
3. 与平台的 compiled HyperFrames 方向一致。
4. 后续支持复杂动效、品牌模板、编辑器预览更自然。

要求：

1. `TemplateRenderContext` 增加 `text_tracks` 和 `text_cues`。
2. 模板不能绕过契约读取散落字段。
3. 每个模板需要声明自己支持哪些 slot 和 style preset。

### 7.2 ASS

定位：legacy 最终视频层稳定烧录路线，也是字幕兼容路线。

ASS 不应成为平台主时间线，只应是 `TextCue` 的导出格式。

推荐产物：

```text
master.ass
subtitle_only.ass
overlay_only.ass
```

主产物是 `master.ass`，内部包含两类逻辑轨：

1. 字幕轨：低位、连续、可读性优先。
2. 重点词轨：不同位置、短时间出现、视觉强调优先。

接入点：

1. legacy 标准链路先完成 segment concat 和 BGM。
2. 然后执行 ASS burn-in。
3. 最后再复制到用户指定 output path。

也就是：

```text
concat_videos(...)
  -> burn_ass_subtitles(...)
  -> copy to user output
```

不能在复制后再烧录，否则任务产物和用户产物会不一致。

### 7.3 模型原生画字

定位：实验性增强路线，不是确定性排版路线。

它应该消费 `TextTrack(kind="native_hint")` 或 `TextCue(role="native_hint")`，再由 prompt adapter 合并进正向 prompt。

原则：

1. 只有 `TextRenderingPolicy.image_text_mode` 允许时，才放松 no-text 约束。
2. native hint 的文本数量必须受 `density` 和 `max_items_per_frame` 控制。
3. 模型原生文字的输出不保证位置和一致性，因此不能替代稳定文字层。
4. 需要保留 A/B 实验能力，用同一批 cue 对比 native prompt、HTML、ASS 的效果和耗时。

### 7.4 Python 直接绘字

定位：fallback 和工具能力，不作为主路线。

适合：

1. 纯图片导出。
2. 无浏览器环境的降级路径。
3. 简单水印、角标、debug 标注。

不适合：

1. 精美排版。
2. 复杂动画。
3. 多语言字体 fallback。
4. 长视频时间线文字。

## 8. 时间线策略

### 8.1 第一阶段：frame-relative

第一阶段可以基于分镜帧时长做规则映射：

```text
frame.start + 20% duration -> frame.start + 65% duration
```

适合重点词、角标、短句。

### 8.2 第二阶段：sentence-relative

如果已有 `SentenceUnit` 或 `CaptionCue`，则把重点短句绑定到句级时间。

适合：

1. 字幕轨
2. 与旁白同步的重点词
3. 语义片段强调

### 8.3 第三阶段：word-level alignment

当 forced alignment 或 TTS word timestamp 可用时，再升级为词级时间。

这不是 v3 的首个落地前置条件。  
平台契约先支持 `source` 和 `confidence` 字段，未来可以自然升级。

## 9. 观测性与产物

每个任务建议产出：

```text
text_overlay_plan.json
render_manifest.json
text_tracks.json
master.ass
subtitle_only.ass
overlay_only.ass
```

其中：

1. `text_overlay_plan.json`：解释为什么选这些词。
2. `render_manifest.json`：最终渲染事实来源。
3. `text_tracks.json`：可选调试导出，便于单独比较文字层。
4. `master.ass`：legacy 最终烧录输入。
5. `subtitle_only.ass`：字幕 A/B 和 debug。
6. `overlay_only.ass`：重点词 A/B 和 debug。

观测性摘要应记录：

1. text planner 耗时
2. cue compiler 耗时
3. 各 renderer 耗时
4. cue 数量
5. native prompt 文本数量
6. ASS burn-in 耗时
7. 最终启用的 renderer targets

## 10. 与现有代码的关系

### 10.1 不修改 StyledImagePromptBatch 职责

`StyledImagePromptBatch` 保持 prompt 返回契约。  
不要把完整 `TextOverlayPlan` 或时间线数据挂进去。

正确做法：

```text
generate_styled_image_prompt_batch(...)
  -> StyledImagePromptBatch

TextOverlayPlanner(...)
  -> TextOverlayPlan

TextCueCompiler(...)
  -> TextTrack / TextCue
```

### 10.2 Prompt 生成只消费 native hint

模型原生文字需要 prompt 参与，但 prompt 生成不拥有整个文字层。

推荐流程：

```text
TextOverlayPlan(role="model_native_hint")
  -> NativePromptProjection
  -> prompt positive rules
  -> generate_styled_image_prompt_batch(...)
```

渲染期仍然可以把 native hint 记录成：

```text
TextTrack(kind="native_hint") + TextCue(role="native_hint")
```

这份记录用于审计、复跑和 A/B 对比，不是 prompt 注入的实际执行点。实际注入点必须发生在图像 prompt batch 生成之前。

### 10.3 TemplateRenderContext 必须扩展

HyperFrames 和 HTML 模板不能从 `template_params` 里临时找任意字段。  
应该在 `TemplateRenderContext` 明确增加：

```python
text_tracks: List[TextTrack]
text_cues: List[TextCue]
```

模板字段清单也要同步声明支持的 slot、role、style preset。

### 10.4 HyperFramesProjectService 导出链路

扩展 `TemplateRenderContext` 只是其中一步。compiled HyperFrames 路线还必须同步规定整个导出链路：

1. `RenderManifest.to_dict/from_dict` 必须序列化 `text_tracks/text_cues`，旧 manifest 缺字段时默认空列表。
2. `_normalize_manifest_timeline(...)` 必须校验 text cue 的 `start/end` 不越界，并按 canonical timeline 归一化。
3. `_materialize_project_assets(...)` 不能丢弃 text tracks/cues；文字层里的 asset refs 后续也要走统一 materialize。
4. `build_template_render_context(...)` 必须把归一化后的 `text_tracks/text_cues` 放进 context。
5. `_write_diagnostic_payloads(...)` 必须把文字层写入诊断产物，至少保证 `render_manifest.json` 和 `text_tracks.json` 可复跑。
6. compiled project 的 `context`、manifest payload、debug payload 三者必须来自同一份 normalized manifest。

这样才能避免“视频能渲染，但 debug artifact 或复跑 manifest 丢失文字层”的问题。

### 10.5 VideoService 增加 ASS burn-in

建议新增：

```python
VideoService.burn_ass_subtitles(
    input_video: str,
    ass_file: str,
    output: str,
) -> str
```

要求：

1. Windows 路径、空格、中文路径必须测试。
2. 输入输出不能是同一个文件。
3. FFmpeg filter 字符串必须统一转义。
4. burn-in 后更新 `storyboard.final_video_path` 和 `ctx.final_video_path`。

## 14. 最终推荐口径

对外产品口径：

> Pixelle 的“文字层”可以把字幕、重点词、标签、标题、模型原生文字提示统一编排到同一条创作时间线中。用户可以选择稳定叠字、模型原生画字，或同时开启进行对比。

对内工程口径：

> 不做孤立的图片加字功能。先补平台文字层契约，再让图片加字、字幕、重点词、模板文字、模型原生 prompt hint 都成为 `TextTrack / TextCue` 的不同角色。

推荐优先级：

1. 先对齐内容创作平台总契约：`CreationPackage -> RenderManifest v2`。
2. 再做平台文字层契约：`TextTrack / TextCue / TextRenderingPolicy`。
3. 再做 planner/compiler 与 pre-image `NativePromptProjection`。
4. 先接 HyperFrames / HTML 主路线，并补齐 diagnostic payload。
5. 再接 ASS legacy burn-in。
6. 最后做模型原生文字 A/B 实验。

## 15. v3 结论

图片加字是入口，不是终点。  
真正要建设的是 Pixelle 的平台级文字层。

v3 推荐方案可以同时满足：

1. 大内容创作平台的长期扩展。
2. 字幕、重点词、模板文字、模型原生画字的统一编排。
3. HyperFrames-first 的架构方向。
4. legacy 标准链路的可用性。
5. 可观测、可复现、可 A/B 的工程治理。

下一步不建议直接写 renderer。  
应该先实现平台契约和测试，把 `TextTrack / TextCue` 立住，再把各 renderer 作为适配层逐步接入。
