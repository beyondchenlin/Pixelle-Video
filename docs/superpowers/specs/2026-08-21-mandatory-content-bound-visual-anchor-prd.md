# Pixelle 文案与强制视觉锚点联合场景生成 PRD（产品需求文档）

> 文档日期：2026-08-21
>
> 需求状态：规格已确认，实施中
>
> 适用范围：文案生成分镜图片、分镜图片生成视频的前置画面生成链路
>
> 基线版本：`dev` 分支提交 `308e9244`
>
> 核心结论：视觉锚点必须出现在每一张图中，但它的大小、位置、景别和参与方式必须由当前文案决定。

## 1. 文档关系

本文档是“文案内容 + 强制视觉锚点如何共同生成合理图片”的唯一产品事实源。

本文档覆盖 `2026-08-20-series-visual-signature-entity-control-prd.md` 中以下旧规则：

- “视觉锚点可以缺席”；
- 按固定角色限制画面占比；
- 默认站在边缘、处于中景、被动观察；
- 只保证身份、位置和融合，不保证视觉锚点参与文案表达；
- 成图检查可以跳过但任务仍然成功；
- 生成最终提示词时再次调用大语言模型自由改写。

旧文档中的身份快照、身份哈希、持久化、追踪记录和模型能力适配继续有效。发生冲突时，以本文档为准。

## 2. 背景与问题

Pixelle 已经能把固定角色身份写入提示词，但当前主链路没有真正解决“角色为什么在这里”。实际表现是：

1. 文案先形成一个内容画面，随后系统再把视觉锚点塞进画面；
2. 多数分镜退化为“角色站在旁边观察”；
3. 位置由帧编号哈希决定，深度固定为中景，和文案语义无关；
4. 当上游没有提取内容主体时，系统仍允许生成；
5. 身份和控制描述占据大部分提示词，挤压真正的文案画面；
6. 内部枚举值进入最终提示词，产生乱码和无意义文字；
7. 最终大语言模型重写链路耗时高、失败后大量回退；
8. 成图检查关闭时，系统仍把“视觉锚点缺失、身份错误、内容错误”的结果标记为成功。

一次十六帧真实任务暴露了上述问题：十六帧的内容主体均为空，十六帧全部退化成被动观察角色，十五帧最终提示词被硬截断，十五帧最终大语言模型组装失败并回退，且成图检查全部跳过。乔布斯只是这次故障中的文案人物，不是产品设计对象；本方案必须对任意文案成立。

### 2.1 当前代码复现证据

本文档基线上的问题由以下生产代码和自动化测试共同证明，不以事故口述作为唯一依据：

- `visual_story_engine.py` 主动移除身份配置并输出无锚点融合的中性计划；
- `visual_prompt_composer.py` 先形成纯内容提示词，再在末尾调用投影服务追加锚点；
- `series_visual_signature_projection_policy.py` 允许空的内容必要主体通过；
- `visual_entity_placement_planner.py` 使用帧标识哈希选择左右位置，并固定使用中景和被动观察回退；
- `final_visual_prompt_compiler.py` 使用字符串切片缩短受保护内容，并输出内部枚举值；
- `series_visual_signature_rendered_output_gate.py` 将“检查通过”和“检查跳过”都视为接受；
- `frame_processor.py` 的重试只更换种子，不根据检查失败原因修复合同或提示词；
- `tests/services/test_series_visual_signature_projection_service.py`、`tests/services/test_series_visual_signature_contract_builder.py`、`tests/test_standard_pipeline_storyboard_generation.py` 和 `tests/services/test_final_visual_prompt_llm_assembler.py` 固化了上述旧行为。

真实十六帧事故样本在进入固定回归集前必须补齐任务标识、逐帧原文、最终提示词、图片、工作流、模型版本、种子、检测结果和时间戳。材料不完整时不得用该事故样本宣称回归通过；当前阶段以可重复执行的代码路径和自动化测试作为基线证据。

## 3. 第一性原理

一张合理的文案配图同时回答四个问题：

1. 文案在说什么；
2. 画面中什么东西承载这个意思；
3. 视觉锚点在做什么，它为什么必须在场；
4. 内容主体、视觉锚点和环境之间是什么物理关系。

因此，正确生成方式不是：

`内容画面 + 后插入视觉锚点`

而是：

`文案主张 + 内容主体 + 视觉锚点身份 + 视觉锚点职责 + 空间关系 = 一个联合场景`

视觉锚点的身份是全系列不变量；动作、大小、位置、景别、遮挡和道具关系是逐帧变量。只固定身份，不固定构图。

## 4. 产品目标

### 4.1 核心目标

对每一段文案，生成一张同时满足以下条件的图片：

- 视觉锚点清晰可见且身份正确；
- 文案的核心含义没有被改写、遗漏或反转；
- 文案中的必要人物、物体、地点、事件或抽象视觉载体没有被视觉锚点替代；
- 视觉锚点以一种能帮助表达文案的方式参与场景；
- 视觉锚点的大小和位置符合当前画面，而不是固定模板；
- 视觉锚点与地面、道具、人物、光线和透视关系成立；
- 结果通过出图前合同与提示词门禁后才能发起图片生成并进入后续视频链路。

### 4.2 成功指标

成功指标分成“确定性合同门禁”“固定验收集人工发布门禁”和“生产运行指标”三层。确定性门禁必须在每次执行中满足；成图质量的百分之百只表示固定验收集的人工发布门禁，不表示对所有未来生成结果作永久保证。

| 指标 | 上线门槛 |
|---|---:|
| 每帧视觉锚点可见率 | 100% |
| 单实例正确率 | 100% |
| 内容必要主体保留率 | 100% |
| 文案含义反转率 | 0% |
| 内部枚举泄漏率 | 0% |
| 空主体合同进入图片生成率 | 0% |
| 出图后看图大模型调用次数 | 0 次 |
| 最终提示词硬截断率 | 0% |
| 最终阶段大语言模型二次组装调用 | 0 次 |

生产运行指标使用真实完成生成的帧作为分母；合同失败、生成失败、人工复核和历史只读任务分别计数，不得从分母中静默剔除。生产阈值在固定验收集和内部灰度产生基线数据后固化到发布清单，本文档不以无数据的阈值替代真实基线。

## 5. 非目标

本期不处理以下内容：

- 通过训练新模型解决角色一致性；
- 同一画面生成多个视觉锚点分身；
- 让视觉锚点替代历史人物、产品、动物或事件主体；
- 依赖负向提示词保证强制业务规则；
- 为某一篇文章、某一种角色或某一种画风写专用模板；
- 在本期重构无关的视频剪辑、字幕和配音链路。

## 6. 用户故事

1. 作为创作者，我输入任何文案并选择视觉锚点后，每张图都能看到该锚点。
2. 作为创作者，我不需要手工指定锚点左、右、大、小，系统会按文案自动安排。
3. 作为创作者，我看到的图必须仍然在讲原文，而不是只展示锚点。
4. 作为运营人员，我能查看每帧锚点为什么出现、做了什么、和谁发生关系。
5. 作为开发人员，我能从结构化合同和追踪记录定位是语义规划、提示词编译还是图片生成失败。

### 6.1 用户操作流程

1. 用户选择一个已有视觉锚点身份档案；没有身份档案时不能开启强制模式。
2. 用户输入文案并生成分镜；系统自动完成逐帧联合场景规划。
3. 分镜预览展示图片，同时展示一句人话说明，例如“锚点正在拉动压力阀，用来表现控制风险”。
4. 用户可以重新生成单帧，但默认不要求用户填写大小和位置。
5. 高级设置允许用户明确指定某帧的大小、位置或动作；用户指定值优先，但仍必须通过内容主体和空间合理性校验。
6. 出图前门禁失败时，界面显示具体的合同或提示词问题，不显示内部枚举和技术堆栈。

### 6.2 页面状态

| 状态 | 用户看到的结果 |
|---|---|
| 规划中 | 正在理解文案并安排视觉锚点的作用 |
| 合同不完整 | 明确指出缺少内容主体、动作目标或身份档案 |
| 图片生成中 | 显示当前帧和生成进度 |
| 完成 | 单次生成的图片进入视频生成 |
| 失败 | 显示出图前门禁或图片生成失败的具体原因 |

## 7. 强制产品规则

### 7.1 必须出现

- 开启“强制视觉锚点”后，每帧恰好出现一个可识别实例；`absent` 不是合法状态。
- 锚点可以只占局部细节，也可以成为全画面主体；合法画面占比范围为 `0 < ratio <= 1`。
- 锚点可以位于左、中、右、前景、中景、背景或全画面，但位置必须由联合场景语义决定。
- 锚点不得被主体、边框、烟雾、文字或裁切遮到不可识别。

### 7.2 必须参与内容表达

锚点至少承担一种内容绑定职责：

| 参与机制 | 适合内容 | 合理表现 |
|---|---|---|
| 动作执行者 | 教程、流程、操作 | 执行文案中的关键动作 |
| 读者代理 | 选择、思考、体验 | 代替观众面对问题或结果 |
| 观察入口 | 尺度、远景、发现 | 提供视点、方向或尺度参照 |
| 系统组件 | 结构、机制、产品 | 成为系统中有功能的一部分 |
| 冲突参与者 | 对比、阻力、风险 | 与障碍或对立因素发生关系 |
| 尺度参照 | 数据、体量、距离 | 用身体或道具帮助理解大小 |
| 解释引导者 | 知识、分解、因果 | 指向、拆解或连接关键对象 |
| 转化媒介 | 变化、成长、抽象概念 | 让变化通过锚点或其操作发生 |

“站在旁边看”只有在观察本身提供视角、方向、尺度或发现过程时才合法。无语义作用的陪站、摆拍、贴纸化和角落吉祥物全部判定失败。

### 7.3 必须保护原文内容

- 每帧必须有至少一个 `required_subjects` 内容必要主体；为空时禁止生成图片。
- 具体文案的必要主体是原文中的人物、物体、地点、产品或事件。
- 抽象文案的必要主体是能够承载含义的可视化结构，例如岔路、压力表、逐级台阶、转化装置、破裂与修复过程。
- 视觉锚点只能参与必要主体，不能吞掉或替换必要主体。
- 提示词生成前必须执行“语义删除测试”：删除视觉锚点后，原文主体仍存在；删除视觉锚点的动作和关系后，画面表达应明显变弱。两项必须同时成立。

语义删除测试按锚点与原文主体的关系执行：

- 当锚点不是原文主体时，`content_survives_without_anchor` 必须为真，证明锚点没有替代原文主体；
- 当锚点本身就是原文明确描述的主体时，不执行“移除实体”测试，改为执行 `content_survives_without_brand_identity`：移除品牌化身份特征后，原文主体、动作和事件仍成立；
- 两种情况都必须满足 `anchor_contribution_is_meaningful`：移除锚点的动作、目标和关系后，画面表达明显变弱；
- 三项结论必须保存证据文本和所采用的测试模式，不允许以通用默认句补齐。

## 8. 通用联合场景生成流程

### 8.1 主流程

1. **提取文案事实**：得到不可改写的核心主张、必要主体、动作、因果、情绪和禁忌。
2. **建立视觉命题**：把不可直接拍摄的抽象概念转成可见对象、空间或变化过程。
3. **选择参与机制**：从八种机制中选择最能增强表达的一种，不按文章人物类型写死。
4. **生成语义动作**：为视觉锚点生成具体动词、动作目标和结果，禁止使用空泛的“出现”“陪伴”“观察”。
5. **设计同一场景**：一次性确定内容主体、锚点、环境、构图、景深、支撑、接触、遮挡、光影和透视。
6. **执行结构校验**：任何必填事实缺失、冲突或超预算时先修复合同，不进入图片生成。
7. **确定性编译提示词**：程序把已通过校验的合同压缩成自然语言，不再次让大语言模型自由改写。
8. **生成图片并检查**：检查视觉锚点、内容主体和交互关系；失败时携带明确修复原因重试同一帧。

### 8.2 内容类型路由

| 文案类型 | 首选画面载体 | 首选锚点职责 | 示例，不是模板 |
|---|---|---|---|
| 人物故事 | 人物、地点、关键事件 | 见证、引导、尺度参照 | 锚点递出关键物件，但不替代原人物 |
| 抽象观点 | 隐喻物体、空间变化 | 读者代理、转化媒介 | 锚点跨过正在闭合的岔路 |
| 教程流程 | 工具、步骤、输入输出 | 动作执行者 | 锚点操作流程中的关键一步 |
| 产品说明 | 产品、部件、使用场景 | 系统组件、解释引导者 | 锚点连接产品的两个功能节点 |
| 冲突对比 | 两组对象、障碍、拉力 | 冲突参与者 | 锚点抵住与主张相反的力量 |
| 数据尺度 | 数量阵列、距离、体量 | 尺度参照 | 锚点站在巨量对象旁提供比例 |
| 情绪叙事 | 表情、距离、色光、环境 | 读者代理 | 锚点承受或释放文案中的情绪 |
| 自然与空间 | 地貌、天气、生态关系 | 观察入口、尺度参照 | 锚点用视线和姿态引导远景 |
| 严肃敏感内容 | 克制的象征和事实主体 | 解释引导者、读者代理 | 不卖萌，不稀释事实，不做滑稽动作 |

路由只提供候选机制，最终选择必须由当前帧的核心主张、必要主体和相邻分镜共同决定。

## 9. 单帧规范合同

新增 `pixelle_video/models/mandatory_content_bound_visual_anchor.py`，其中的 `MandatoryContentBoundVisualAnchorContract` 是强制模式单帧唯一聚合事实源。它引用现有身份合同、结构化内容主体、`ContentBoundIPPresencePlan`、`VisualEntityPlacement` 和 `VisualEntitySceneFusion`，不复制这些对象已经拥有的事实。

生产链路只能从该模型文件导入联合合同。不得在服务层、请求模型或追踪模型中再定义同名映射结构。合同使用严格构造：缺失字段直接失败，不提供会伪造语义完整性的通用默认值。

### 9.1 必填字段

| 字段 | 含义 | 校验规则 |
|---|---|---|
| `frame_id` | 分镜标识 | 非空且全任务唯一 |
| `content_claim` | 本帧不可改写的文案主张 | 非空 |
| `required_subjects` | 必须保留的结构化内容主体 | 至少一项；复用 `SubjectAnchor`，保留主体标识、原文短语、证据、重要性、视觉存在和丢失策略 |
| `visual_thesis` | 画面如何表达主张 | 非空、可视化 |
| `participation_plan` | 锚点的参与机制、动作和目标 | 八种机制之一 |
| `identity_contract` | 固定身份特征和快照哈希 | 必须可追踪 |
| `placement` | 水平、纵深、景别、画面占比 | 由语义产生，不得哈希随机 |
| `scene_fusion` | 支撑、接触、遮挡、光影、透视 | 与场景对象一致 |
| `semantic_necessity` | 锚点为什么必须在场 | 非空，禁止套话 |
| `semantic_removal_test` | 内容保留与锚点增益结论 | 包含测试模式、内容保留结论、锚点增益结论和两段证据；适用结论均通过 |
| `final_scene_description` | 可直接编译的自然场景描述 | 不含内部枚举 |
| `forbidden_compositions` | 本帧禁止的错误构图 | 至少包含替代主体和贴纸化 |

### 9.2 参与计划必须输出

- 参与机制；
- 具体动作动词；
- 动作目标；
- 动作产生的视觉结果；
- 与原文主体的关系；
- 与相邻分镜不同的表达点；
- 严肃内容的克制策略；
- 禁止形式。

`ContentBoundIPPresencePlan` 必须新增并严格要求：`action_result`、`semantic_necessity`、`adjacent_frame_difference`、`serious_content_strategy` 和 `forbidden_forms`。规划器必须显式接收 `required_subjects`、前一帧摘要和后一帧摘要；未提供相邻帧时保存边界状态，不生成虚假差异描述。

### 9.3 位置与融合必须输出

- 水平位置：左、中、右或跨画面；
- 纵深位置：前景、中景、背景或全画面；
- 景别：细节、近景、中景、全景或超远景；
- 建议画面占比：大于零且不大于一；
- 可见范围：全身、半身、头像、局部但可识别；
- 支撑关系：站、坐、悬挂、握持、嵌入或其他明确支撑；
- 接触关系：与哪个对象接触、如何接触；
- 遮挡关系：谁在前、谁在后、允许遮挡多少；
- 光影关系：主光方向、接触阴影、反射或环境色；
- 透视关系：锚点尺寸和地平线必须服从场景透视。

### 9.4 大小规则

取消“某角色最多占画面百分之十六、二十、二十八或四十五”的固定上限。大小只由三件事决定：

1. 锚点承担的语义职责；
2. 内容必要主体需要的可见空间；
3. 当前镜头想表达的情绪和尺度。

全画面特写是合法的，但文案内容必须通过锚点正在执行的动作、持有的对象、环境变化或画外关系继续存在。小尺寸也是合法的，但必须仍能识别身份。

### 9.5 主体事实来源与冲突优先级

内容必要主体只从结构化文章理解和逐帧内容合同产生，优先级依次为：用户逐帧明确覆盖、逐帧文章理解证据、文章级主体证据、可审计的抽象视觉载体。投影服务不得把多个字符串来源无差别合并。

- 同一主体通过稳定主体标识去重，显示名称和别名只用于编译提示词；
- 每个主体必须保留原文证据；抽象载体必须保留它承载的原文主张；
- 用户覆盖不能删除丢失策略为 `must_keep` 的主体，除非显式关闭强制模式并重新创建任务；
- 锚点与原文主体同一实体时保存 `anchor_subject_overlap=true`，不得复制成两个实例；
- 主体来源冲突时按上述优先级选择，并在追踪记录中保存被覆盖值和原因。

## 10. 提示词规范

### 10.1 编译原则

- 最终提示词是自然语言画面描述，不是字段清单；
- 只允许一次语义规划，最终阶段不再调用大语言模型重写；
- 程序只压缩、排序和连接已验证事实，不创造新事实；
- 业务硬约束全部写入正向提示词；当前快速版图片模型不能依赖负向提示词保证规则；
- 保护内容、身份、动作目标、空间关系的句子禁止截断；超预算时回到合同压缩，不截掉句尾；
- 禁止输出 `silent_witness`、`midground` 等内部枚举和值对象名称。

### 10.2 固定顺序

最终正向提示词按四段编译：

1. **文案主画面**：场景、必要主体、关键动作、含义；
2. **视觉锚点参与**：身份特征、具体动作、动作目标、语义作用；
3. **空间与融合**：位置、景别、占比、支撑、接触、遮挡、光影和透视；
4. **视觉风格**：画风、镜头、色彩、材质和文字策略。

### 10.3 长度与占比

- 目标长度：二百五十至六百个字符；
- 硬上限：八百个字符；
- 文案主画面不得少于总长度的百分之三十五；
- 身份与实例控制不得超过总长度的百分之三十；
- 空间、融合和风格使用剩余预算；
- 任何保护字段因预算无法完整写入时，合同校验失败，不进入图片生成。

字符预算按以下唯一口径执行：

1. 所有段落先执行统一码规范组合形式归一化并折叠连续空白；
2. 以实际发送给图片模型的最终正向提示词为计数对象，按语言运行时的字符长度计数；
3. 负向提示词、调试字段和追踪元数据不计入正向提示词预算；
4. 文案主画面占比以第一段字符数除以总字符数计算；身份占比只计算不可变身份特征和单实例约束，不包含锚点动作；
5. 超预算时按“可选风格修饰、非必要镜头修饰、可合并融合修饰”的顺序删除完整短语，禁止字符串切片和省略号截断；
6. 删除完整短语后仍超过八百字符，或比例门禁仍不满足时，合同编译失败并返回分项预算，不进入图片生成。

### 10.4 合格提示词的最小结构示例

> 雨夜车站里，末班车即将关门，一只戴深色圆框眼镜的斑点狗从右侧前景奔向车门，前爪护住被风吹散的车票并把其中一张递给落在后方的旅客。狗是半身近景，旅客和车门保持完整可见；爪子压住车票，脚下有湿地接触阴影，身体受站台顶灯照亮，远处列车灯形成透视线。电影感写实插画，冷蓝环境光，不出现画面文字。

该示例只说明结构：内容主体、锚点动作、目标、位置和物理关系在同一句场景中成立，不作为固定模板。

## 11. 单次生成与源头质量门禁

自 2026-08-23 起，本节覆盖旧版“成图检查与三次定向修复”规则。生产链路不再调用看图大模型判断生成结果，也不再根据判断结果修补提示词或重复生成。

### 11.1 出图前强制检查

每一帧在首次出图前必须通过以下确定性检查：

- 分镜标识稳定、唯一且覆盖完整；
- 最终正向提示词、负向提示词与提示词计划完全一致；
- 最终提示词合同版本正确且结构完整；
- 身份资料、身份哈希与逐帧合同一致；
- 文案主体、视觉锚点、动作、目标、支撑、接触、遮挡、光影、透视和禁用项已经写入最终合同与提示词。

任一检查失败时，任务必须在出图前失败并指出具体合同或提示词问题，不得消耗图片生成资源。

### 11.2 单次生成规则

- 每帧只允许发起一次图片生成请求；
- 不调用看图大模型做出图后质量判断；
- 不自动修改提示词，不更换随机种子，不自动重复生成；
- 允许在出图后执行文件、哈希、随机种子、工作流绑定等确定性完整性审计，这类审计不得调用大模型，也不得触发重复生成；
- 画面质量问题必须回到文案理解、联合合同或最终提示词事实源修复，再由用户明确发起新的生成任务。

该规则把成本和质量控制集中在首次出图前，避免用重复生成掩盖提示词或合同缺陷。

## 14. 验收标准

### 14.1 合同层

- 任意帧 `required_subjects` 为空，投影服务抛出明确错误；
- 任意帧锚点状态为缺席，合同校验失败；
- 动作动词、动作目标、语义必要性、位置或融合字段缺失，合同校验失败；
- 画面占比在大于零且不大于一范围内通过，不再按角色设置上限；
- 位置不能由帧编号、随机数或哈希直接决定；
- 删除测试的两项结论必须为真。

### 14.2 提示词层

- 每条提示词都能找到全部内容必要主体、身份最低特征、动作和目标；
- 不出现内部枚举、结构字段名和调试文字；
- 不超过八百字符；
- 文案主画面占比达到百分之三十五；
- 不通过字符串硬截断满足长度；
- 相同输入合同重复编译得到相同提示词。

### 14.3 成图层

- 固定验收集中的每张成图均有一个可识别视觉锚点；
- 所有必要主体可见，且未被锚点冒充或替换；
- 锚点动作、目标和场景关系与合同一致；
- 锚点允许任意合理大小和位置，不因大或小单独判错；
- 没有明显漂浮、穿插、重复、贴纸化和透视冲突；
- 检查服务关闭或异常时，任务不得完成。

## 15. 测试方案

### 15.1 单元测试

- 八种参与机制的选择与字段完整性；
- 内容必要主体为空、被替换和重复时的失败；
- 任意合法画面占比通过，越界占比失败；
- 语义位置取代哈希位置；
- 自然语言编译顺序、预算和确定性；
- 内部枚举泄漏拦截；
- 出图后看图检查保持关闭；
- 每帧图片生成请求次数固定为一次。

### 15.2 集成测试

使用九类文案，每类至少八帧，共七十二帧：人物故事、抽象观点、教程流程、产品说明、冲突对比、数据尺度、情绪叙事、自然空间、严肃内容。

每类必须覆盖：

- 小、中、大、全画面四种尺度；
- 左、中、右和跨画面位置；
- 前景、中景、背景；
- 视觉锚点与人物、物体、环境和抽象结构的交互；
- 无具体名词时的抽象视觉载体生成；
- 相邻分镜构图去重复。

固定七十二帧验收集保存在 `tests/fixtures/mandatory_content_bound_visual_anchor/`，包含九类文案各八帧的原始文案、结构化主体真值、允许的锚点职责、禁止替代项和人工验收清单。每次发布固定图片工作流版本、图片模型版本、提示词合同版本、编译器版本和种子集合；任一输入版本变化都创建新的验收批次，不覆盖历史结果。

### 15.3 回归测试

- 现有身份快照和哈希保持稳定；
- 旧合同可正常读取；
- 未启用强制模式的路径不受影响；
- 快速版图片模型的正向提示词包含全部业务硬约束；
- 真实十六帧故障样本重新运行后，不再出现空主体、全员被动观察、硬截断和绕过出图前门禁。

### 15.4 自动化与人工验收边界

- 合同非空、字段完整、版本、字符预算、占比、内部枚举、确定性和失败阻断全部由自动化测试判定；
- 成图中的主体、动作、融合和内容主张由固定验收集的人工真值复核，不在生产生成链路增加看图模型调用；
- 人工验收失败时回到文案理解、联合合同或最终提示词修复，禁止用重复生成掩盖源头缺陷；
- 七十二帧发布门禁要求全部通过；生产指标按第 4.2 节口径观测并在内部灰度后固化阈值；
- 十六帧事故样本只有在第 2.1 节列出的复现材料完整后才进入强制回归集。

## 16. 监控与追踪

每帧记录以下数据：

- 文案主张和必要主体；
- 参与机制、动作、目标和语义必要性；
- 位置、大小、景别和融合关系；
- 身份快照哈希；
- 最终提示词各段字符数和占比；
- 图片模型、工作流、种子和生成耗时；
- 出图前门禁各项结果；
- 单次生成状态和失败原因。

任务级汇总必须展示：锚点可见率、主体保留率、语义失败率、硬截断率、单帧生成次数和单帧总耗时。

所有比率同时保存分子、分母和排除项。锚点可见率和主体保留率使用固定验收集的人工结果为分母；被出图前门禁阻断的帧单独计入失败总数。人工复核只能追加审计事件，不能改写原始生成记录。

严肃内容使用确定性分类结果进入克制策略：医疗伤害、事故灾害、死亡哀悼、法律惩罚、暴力冲突和公共安全事实至少纳入严肃类别。默认禁止卖萌、庆祝、夸张滑稽动作和用锚点遮盖受影响主体。用户覆盖必须记录理由，且不能绕过主体保护、单实例和成图检查。

- 强制内容必要主体非空；
- 把现有 `ContentBoundIPPlanner` 接入 `VisualPromptComposer` 的实际生产链路；
- 取消缺席状态和角色面积上限。

完成标志：每帧在生成前都有完整的“文案主体 + 锚点职责 + 动作目标 + 空间关系”。

### 阶段二：重写确定性提示词编译

- 移除最终大语言模型二次组装；
- 实现四段自然语言编译和预算；
- 清理内部枚举泄漏；
- 禁止保护事实硬截断。

完成标志：相同合同稳定生成不超过八百字符的自然提示词。

### 阶段三：出图前门禁和单次生成

- 完善合同、提示词来源和身份哈希检查；
- 固定每帧一次图片生成；
- 移除出图后看图判断和自动修复；
- 完整保存追踪数据。

完成标志：只有视觉锚点、内容主体和交互关系全部写入并通过出图前门禁的提示词才能发起图片生成。

### 阶段四：全量回归与灰度

- 跑完七十二帧通用验收集；
- 重跑历史故障样本；
- 先对内部任务启用，再对新建强制锚点任务全量启用；
- 旧任务保持只读兼容。

完成标志：所有必须级指标达到上线门槛。

## 18. 风险与处理

| 风险 | 处理方式 |
|---|---|
| 锚点身份描述过长挤压内容 | 身份只保留最低可识别特征并限制为总长度百分之三十 |
| 抽象文案没有具体主体 | 先生成可审计的抽象视觉载体，再进入联合场景规划 |
| 锚点尺寸过小无法识别 | 在合同和正向提示词中明确最低可识别身份特征，不只写面积 |
| 锚点过大遮住内容 | 在合同中保护必要主体可见性；全画面时要求内容通过动作和环境继续存在 |
| 严肃内容被角色可爱化 | 使用克制策略，禁止卖萌、庆祝和滑稽动作 |
| 图片模型忽略复杂指令 | 缩短提示词、把硬约束放在正向描述，并从合同和编译器源头改进 |
| 人工验收发现画面问题 | 保留原图和源头记录，修复合同或提示词后由用户发起新任务 |
| 连续分镜动作重复 | 规划时读取相邻两帧的机制、动作、位置和尺度并执行去重 |

## 19. 外部方案借鉴

以下项目只用于验证架构方向，不直接复制代码：

- [StoryForge](https://github.com/Oldcircle/storyforge)：把角色卡、场景资料、导演规划和确定性渲染计划分层，证明“模型负责创意，程序负责一致性”的方向正确；
- [Story2Board](https://github.com/DavidDinkevich/Story2Board)：强调跨分镜身份一致性与逐格构图控制必须同时存在；
- [StoryDiffusion](https://github.com/HVision-NKU/StoryDiffusion)：提供连续图像角色一致性的模型侧参考，但不能替代本文档的内容绑定规划；
- [VibeFrame](https://github.com/vericontext/vibeframe)：采用书面需求、生成计划、资产生成、成本与失败恢复的分层流水线，可借鉴可追踪执行方式；
- [IP-Adapter](https://github.com/tencent-ailab/IP-Adapter)：提供参考图身份注入能力，属于后续增强，不解决锚点为何出现在场景中的语义问题；
- [Z-Image](https://github.com/Tongyi-MAI/Z-Image)：当前图片模型的官方实现；快速版不应依赖负向提示词承载业务硬约束。

借鉴结论只有三条：

1. 角色身份与单帧构图必须分开管理；
2. 创意规划必须输出结构化合同，程序负责守住事实；
3. 参考图能增强身份一致性，但不能替代“文案与锚点共同成景”的语义规划。

## 20. 完成定义

本需求只有在以下条件全部满足时才算完成：

- 本文档中的十二项功能需求全部实现，其中所有“必须”项通过自动化测试；
- 七十二帧通用验收集全部完成人工验收；
- 真实故障样本不再出现空主体、被动陪站、角色替代主体、枚举泄漏、提示词硬截断和绕过出图前门禁；
- 每帧都能从追踪记录回答：“原文说什么、锚点为什么在、锚点做什么、锚点和谁发生关系、为什么放在这里、最终提示词如何表达”；
- 未通过出图前门禁的帧不能发起图片生成。

最终产品规则可以用一句话概括：**视觉锚点必须每帧出现，但画面不是围着锚点硬编；系统必须先理解文案，再让视觉锚点以最合适的动作、大小和位置参与同一个场景。**
