# Pixelle 文案与强制视觉锚点联合场景生成 PRD（产品需求文档）

> 文档日期：2026-08-21
>
> 需求状态：待实现
>
> 适用范围：文案生成分镜图片、分镜图片生成视频的前置画面生成链路
>
> 基线版本：`dev` 分支提交 `4b2c6e70`
>
> 核心结论：视觉锚点必须出现在每一张图中，但它的大小、位置、景别和参与方式必须由当前文案决定。

## 1. 文档关系

本文档是“文案内容 + 强制视觉锚点如何共同生成合理图片”的唯一产品事实源。

本文档覆盖 `2026-08-20-series-visual-signature-entity-control-prd.md` 中以下旧规则：

- “视觉锚点可以缺席”；
- 按固定角色限制画面占比；
- 默认站在边缘、处于中景、被动观察；
- 只保证身份、位置和融合，不保证视觉锚点参与文案表达；
- 成图检查可以跳过但任务仍然成功；
- 生成最终提示词时再次调用大语言模型自由改写。

旧文档中的身份快照、身份哈希、持久化、追踪记录和模型能力适配继续有效。发生冲突时，以本文档为准。

## 2. 背景与问题

Pixelle 已经能把固定角色身份写入提示词，但当前主链路没有真正解决“角色为什么在这里”。实际表现是：

1. 文案先形成一个内容画面，随后系统再把视觉锚点塞进画面；
2. 多数分镜退化为“角色站在旁边观察”；
3. 位置由帧编号哈希决定，深度固定为中景，和文案语义无关；
4. 当上游没有提取内容主体时，系统仍允许生成；
5. 身份和控制描述占据大部分提示词，挤压真正的文案画面；
6. 内部枚举值进入最终提示词，产生乱码和无意义文字；
7. 最终大语言模型重写链路耗时高、失败后大量回退；
8. 成图检查关闭时，系统仍把“视觉锚点缺失、身份错误、内容错误”的结果标记为成功。

一次十六帧真实任务暴露了上述问题：十六帧的内容主体均为空，十六帧全部退化成被动观察角色，十五帧最终提示词被硬截断，十五帧最终大语言模型组装失败并回退，且成图检查全部跳过。乔布斯只是这次故障中的文案人物，不是产品设计对象；本方案必须对任意文案成立。

## 3. 第一性原理

一张合理的文案配图同时回答四个问题：

1. 文案在说什么；
2. 画面中什么东西承载这个意思；
3. 视觉锚点在做什么，它为什么必须在场；
4. 内容主体、视觉锚点和环境之间是什么物理关系。

因此，正确生成方式不是：

`内容画面 + 后插入视觉锚点`

而是：

`文案主张 + 内容主体 + 视觉锚点身份 + 视觉锚点职责 + 空间关系 = 一个联合场景`

视觉锚点的身份是全系列不变量；动作、大小、位置、景别、遮挡和道具关系是逐帧变量。只固定身份，不固定构图。

## 4. 产品目标

### 4.1 核心目标

对每一段文案，生成一张同时满足以下条件的图片：

- 视觉锚点清晰可见且身份正确；
- 文案的核心含义没有被改写、遗漏或反转；
- 文案中的必要人物、物体、地点、事件或抽象视觉载体没有被视觉锚点替代；
- 视觉锚点以一种能帮助表达文案的方式参与场景；
- 视觉锚点的大小和位置符合当前画面，而不是固定模板；
- 视觉锚点与地面、道具、人物、光线和透视关系成立；
- 结果通过成图检查后才能进入视频生成。

### 4.2 成功指标

| 指标 | 上线门槛 |
|---|---:|
| 每帧视觉锚点可见率 | 100% |
| 单实例正确率 | 100% |
| 内容必要主体保留率 | 100% |
| 文案含义反转率 | 0% |
| 内部枚举泄漏率 | 0% |
| 空主体合同进入图片生成率 | 0% |
| 成图检查跳过后仍标记成功率 | 0% |
| 最终提示词硬截断率 | 0% |
| 最终阶段大语言模型二次组装调用 | 0 次 |

## 5. 非目标

本期不处理以下内容：

- 通过训练新模型解决角色一致性；
- 同一画面生成多个视觉锚点分身；
- 让视觉锚点替代历史人物、产品、动物或事件主体；
- 依赖负向提示词保证强制业务规则；
- 为某一篇文章、某一种角色或某一种画风写专用模板；
- 在本期重构无关的视频剪辑、字幕和配音链路。

## 6. 用户故事

1. 作为创作者，我输入任何文案并选择视觉锚点后，每张图都能看到该锚点。
2. 作为创作者，我不需要手工指定锚点左、右、大、小，系统会按文案自动安排。
3. 作为创作者，我看到的图必须仍然在讲原文，而不是只展示锚点。
4. 作为运营人员，我能查看每帧锚点为什么出现、做了什么、和谁发生关系。
5. 作为开发人员，我能从结构化合同和追踪记录定位是语义规划、提示词编译还是图片生成失败。

### 6.1 用户操作流程

1. 用户选择一个已有视觉锚点身份档案；没有身份档案时不能开启强制模式。
2. 用户输入文案并生成分镜；系统自动完成逐帧联合场景规划。
3. 分镜预览展示图片，同时展示一句人话说明，例如“锚点正在拉动压力阀，用来表现控制风险”。
4. 用户可以重新生成单帧，但默认不要求用户填写大小和位置。
5. 高级设置允许用户明确指定某帧的大小、位置或动作；用户指定值优先，但仍必须通过内容主体和空间合理性校验。
6. 成图检查失败时，界面显示具体原因和已使用的修复次数，不显示内部枚举和技术堆栈。

### 6.2 页面状态

| 状态 | 用户看到的结果 |
|---|---|
| 规划中 | 正在理解文案并安排视觉锚点的作用 |
| 合同不完整 | 明确指出缺少内容主体、动作目标或身份档案 |
| 图片生成中 | 显示当前帧和生成进度 |
| 自动修复中 | 显示具体修复项和次数 |
| 通过 | 图片可进入视频生成 |
| 失败 | 图片保留供查看，但禁止进入视频生成 |

## 7. 强制产品规则

### 7.1 必须出现

- 开启“强制视觉锚点”后，每帧恰好出现一个可识别实例；`absent` 不是合法状态。
- 锚点可以只占局部细节，也可以成为全画面主体；合法画面占比范围为 `0 < ratio <= 1`。
- 锚点可以位于左、中、右、前景、中景、背景或全画面，但位置必须由联合场景语义决定。
- 锚点不得被主体、边框、烟雾、文字或裁切遮到不可识别。

### 7.2 必须参与内容表达

锚点至少承担一种内容绑定职责：

| 参与机制 | 适合内容 | 合理表现 |
|---|---|---|
| 动作执行者 | 教程、流程、操作 | 执行文案中的关键动作 |
| 读者代理 | 选择、思考、体验 | 代替观众面对问题或结果 |
| 观察入口 | 尺度、远景、发现 | 提供视点、方向或尺度参照 |
| 系统组件 | 结构、机制、产品 | 成为系统中有功能的一部分 |
| 冲突参与者 | 对比、阻力、风险 | 与障碍或对立因素发生关系 |
| 尺度参照 | 数据、体量、距离 | 用身体或道具帮助理解大小 |
| 解释引导者 | 知识、分解、因果 | 指向、拆解或连接关键对象 |
| 转化媒介 | 变化、成长、抽象概念 | 让变化通过锚点或其操作发生 |

“站在旁边看”只有在观察本身提供视角、方向、尺度或发现过程时才合法。无语义作用的陪站、摆拍、贴纸化和角落吉祥物全部判定失败。

### 7.3 必须保护原文内容

- 每帧必须有至少一个 `required_subjects` 内容必要主体；为空时禁止生成图片。
- 具体文案的必要主体是原文中的人物、物体、地点、产品或事件。
- 抽象文案的必要主体是能够承载含义的可视化结构，例如岔路、压力表、逐级台阶、转化装置、破裂与修复过程。
- 视觉锚点只能参与必要主体，不能吞掉或替换必要主体。
- 提示词生成前必须执行“语义删除测试”：删除视觉锚点后，原文主体仍存在；删除视觉锚点的动作和关系后，画面表达应明显变弱。两项必须同时成立。

## 8. 通用联合场景生成流程

### 8.1 主流程

1. **提取文案事实**：得到不可改写的核心主张、必要主体、动作、因果、情绪和禁忌。
2. **建立视觉命题**：把不可直接拍摄的抽象概念转成可见对象、空间或变化过程。
3. **选择参与机制**：从八种机制中选择最能增强表达的一种，不按文章人物类型写死。
4. **生成语义动作**：为视觉锚点生成具体动词、动作目标和结果，禁止使用空泛的“出现”“陪伴”“观察”。
5. **设计同一场景**：一次性确定内容主体、锚点、环境、构图、景深、支撑、接触、遮挡、光影和透视。
6. **执行结构校验**：任何必填事实缺失、冲突或超预算时先修复合同，不进入图片生成。
7. **确定性编译提示词**：程序把已通过校验的合同压缩成自然语言，不再次让大语言模型自由改写。
8. **生成图片并检查**：检查视觉锚点、内容主体和交互关系；失败时携带明确修复原因重试同一帧。

### 8.2 内容类型路由

| 文案类型 | 首选画面载体 | 首选锚点职责 | 示例，不是模板 |
|---|---|---|---|
| 人物故事 | 人物、地点、关键事件 | 见证、引导、尺度参照 | 锚点递出关键物件，但不替代原人物 |
| 抽象观点 | 隐喻物体、空间变化 | 读者代理、转化媒介 | 锚点跨过正在闭合的岔路 |
| 教程流程 | 工具、步骤、输入输出 | 动作执行者 | 锚点操作流程中的关键一步 |
| 产品说明 | 产品、部件、使用场景 | 系统组件、解释引导者 | 锚点连接产品的两个功能节点 |
| 冲突对比 | 两组对象、障碍、拉力 | 冲突参与者 | 锚点抵住与主张相反的力量 |
| 数据尺度 | 数量阵列、距离、体量 | 尺度参照 | 锚点站在巨量对象旁提供比例 |
| 情绪叙事 | 表情、距离、色光、环境 | 读者代理 | 锚点承受或释放文案中的情绪 |
| 自然与空间 | 地貌、天气、生态关系 | 观察入口、尺度参照 | 锚点用视线和姿态引导远景 |
| 严肃敏感内容 | 克制的象征和事实主体 | 解释引导者、读者代理 | 不卖萌，不稀释事实，不做滑稽动作 |

路由只提供候选机制，最终选择必须由当前帧的核心主张、必要主体和相邻分镜共同决定。

## 9. 单帧规范合同

新增 `MandatoryContentBoundVisualAnchorContract` 作为单帧唯一事实源。它组合现有身份合同、`ContentBoundIPPresencePlan`、`VisualEntityPlacement` 和 `VisualEntitySceneFusion`，不复制这些对象已经拥有的事实。

### 9.1 必填字段

| 字段 | 含义 | 校验规则 |
|---|---|---|
| `frame_id` | 分镜标识 | 非空且全任务唯一 |
| `content_claim` | 本帧不可改写的文案主张 | 非空 |
| `required_subjects` | 必须保留的内容主体 | 至少一项 |
| `visual_thesis` | 画面如何表达主张 | 非空、可视化 |
| `participation_plan` | 锚点的参与机制、动作和目标 | 八种机制之一 |
| `identity_contract` | 固定身份特征和快照哈希 | 必须可追踪 |
| `placement` | 水平、纵深、景别、画面占比 | 由语义产生，不得哈希随机 |
| `scene_fusion` | 支撑、接触、遮挡、光影、透视 | 与场景对象一致 |
| `semantic_necessity` | 锚点为什么必须在场 | 非空，禁止套话 |
| `semantic_removal_test` | 内容保留与锚点增益结论 | 两项均通过 |
| `final_scene_description` | 可直接编译的自然场景描述 | 不含内部枚举 |
| `forbidden_compositions` | 本帧禁止的错误构图 | 至少包含替代主体和贴纸化 |

### 9.2 参与计划必须输出

- 参与机制；
- 具体动作动词；
- 动作目标；
- 动作产生的视觉结果；
- 与原文主体的关系；
- 与相邻分镜不同的表达点；
- 严肃内容的克制策略；
- 禁止形式。

### 9.3 位置与融合必须输出

- 水平位置：左、中、右或跨画面；
- 纵深位置：前景、中景、背景或全画面；
- 景别：细节、近景、中景、全景或超远景；
- 建议画面占比：大于零且不大于一；
- 可见范围：全身、半身、头像、局部但可识别；
- 支撑关系：站、坐、悬挂、握持、嵌入或其他明确支撑；
- 接触关系：与哪个对象接触、如何接触；
- 遮挡关系：谁在前、谁在后、允许遮挡多少；
- 光影关系：主光方向、接触阴影、反射或环境色；
- 透视关系：锚点尺寸和地平线必须服从场景透视。

### 9.4 大小规则

取消“某角色最多占画面百分之十六、二十、二十八或四十五”的固定上限。大小只由三件事决定：

1. 锚点承担的语义职责；
2. 内容必要主体需要的可见空间；
3. 当前镜头想表达的情绪和尺度。

全画面特写是合法的，但文案内容必须通过锚点正在执行的动作、持有的对象、环境变化或画外关系继续存在。小尺寸也是合法的，但必须仍能识别身份。

## 10. 提示词规范

### 10.1 编译原则

- 最终提示词是自然语言画面描述，不是字段清单；
- 只允许一次语义规划，最终阶段不再调用大语言模型重写；
- 程序只压缩、排序和连接已验证事实，不创造新事实；
- 业务硬约束全部写入正向提示词；当前快速版图片模型不能依赖负向提示词保证规则；
- 保护内容、身份、动作目标、空间关系的句子禁止截断；超预算时回到合同压缩，不截掉句尾；
- 禁止输出 `silent_witness`、`midground` 等内部枚举和值对象名称。

### 10.2 固定顺序

最终正向提示词按四段编译：

1. **文案主画面**：场景、必要主体、关键动作、含义；
2. **视觉锚点参与**：身份特征、具体动作、动作目标、语义作用；
3. **空间与融合**：位置、景别、占比、支撑、接触、遮挡、光影和透视；
4. **视觉风格**：画风、镜头、色彩、材质和文字策略。

### 10.3 长度与占比

- 目标长度：二百五十至六百个字符；
- 硬上限：八百个字符；
- 文案主画面不得少于总长度的百分之三十五；
- 身份与实例控制不得超过总长度的百分之三十；
- 空间、融合和风格使用剩余预算；
- 任何保护字段因预算无法完整写入时，合同校验失败，不进入图片生成。

### 10.4 合格提示词的最小结构示例

> 雨夜车站里，末班车即将关门，一只戴深色圆框眼镜的斑点狗从右侧前景奔向车门，前爪护住被风吹散的车票并把其中一张递给落在后方的旅客。狗是半身近景，旅客和车门保持完整可见；爪子压住车票，脚下有湿地接触阴影，身体受站台顶灯照亮，远处列车灯形成透视线。电影感写实插画，冷蓝环境光，不出现画面文字。

该示例只说明结构：内容主体、锚点动作、目标、位置和物理关系在同一句场景中成立，不作为固定模板。

## 11. 成图检查与修复

### 11.1 强制检查项

图片生成后逐帧检查：

- 是否存在且只存在一个视觉锚点；
- 身份特征是否达到配置的最低可识别数量；
- 所有内容必要主体是否存在；
- 锚点是否真的执行约定动作并指向约定目标；
- 锚点是否替换了原文人物或主体；
- 锚点大小、位置、支撑、接触、遮挡、光影和透视是否合理；
- 是否出现断肢、漂浮、重复身体、贴纸边缘或无关文字；
- 画面含义是否与文案主张一致。

### 11.2 失败处理

- 每帧最多生成一次初稿和两次修复稿；
- 修复提示只描述检测到的具体失败，例如“锚点缺失”“原人物被替换”“没有接触阴影”，不得整体重写文案；
- 第三次仍失败时，该帧和整项任务明确失败，保留所有提示词、图片和检测结果；
- 强制模式下，成图检查不可用时禁止把任务标记为成功；
- 不允许用“检查已跳过”作为成功结果。

| `pixelle_video/services/series_visual_signature_rendered_output_gate.py` | 强制检查锚点、内容主体、动作关系和空间合理性；检查不可用时关闭成功通道 |

### 12.2 唯一事实源

- 身份事实由身份合同拥有；
- 文案事实由内容合同拥有；
- 锚点的语义参与由 `ContentBoundIPPresencePlan` 拥有；
- 空间位置由 `VisualEntityPlacement` 拥有；
- 物理与视觉融合由 `VisualEntitySceneFusion` 拥有；
- 新联合合同只组合并校验上述对象，不在多个模型中重复保存同一事实。

### 12.3 兼容策略

- 旧记录继续可读，不回写、不批量迁移；
- 旧版 `final_visual_prompt_contract.v4_5` 继续只读兼容；新强制模式统一生成 `final_visual_prompt_contract.v4_6`；
- 新版合同必须包含 `MandatoryContentBoundVisualAnchorContract`，不存在时禁止走新版生成链路；
- 旧角色枚举仅用于读取和展示，不再驱动位置、大小和提示词；
- 未开启强制模式的历史行为不在本期改动范围；
- 新任务若缺少身份合同或内容必要主体，创建阶段直接失败。

## 14. 验收标准

### 14.1 合同层

- 任意帧 `required_subjects` 为空，投影服务抛出明确错误；
- 任意帧锚点状态为缺席，合同校验失败；
- 动作动词、动作目标、语义必要性、位置或融合字段缺失，合同校验失败；
- 画面占比在大于零且不大于一范围内通过，不再按角色设置上限；
- 位置不能由帧编号、随机数或哈希直接决定；
- 删除测试的两项结论必须为真。

### 14.2 提示词层

- 每条提示词都能找到全部内容必要主体、身份最低特征、动作和目标；
- 不出现内部枚举、结构字段名和调试文字；
- 不超过八百字符；
- 文案主画面占比达到百分之三十五；
- 不通过字符串硬截断满足长度；
- 相同输入合同重复编译得到相同提示词。

### 14.3 成图层

- 固定验收集中的每张成图均有一个可识别视觉锚点；
- 所有必要主体可见，且未被锚点冒充或替换；
- 锚点动作、目标和场景关系与合同一致；
- 锚点允许任意合理大小和位置，不因大或小单独判错；
- 没有明显漂浮、穿插、重复、贴纸化和透视冲突；
- 检查服务关闭或异常时，任务不得完成。

## 15. 测试方案

### 15.1 单元测试

- 八种参与机制的选择与字段完整性；
- 内容必要主体为空、被替换和重复时的失败；
- 任意合法画面占比通过，越界占比失败；
- 语义位置取代哈希位置；
- 自然语言编译顺序、预算和确定性；
- 内部枚举泄漏拦截；
- 成图检查关闭时关闭成功通道；
- 两次定向修复后停止。

### 15.2 集成测试

使用九类文案，每类至少八帧，共七十二帧：人物故事、抽象观点、教程流程、产品说明、冲突对比、数据尺度、情绪叙事、自然空间、严肃内容。

每类必须覆盖：

- 小、中、大、全画面四种尺度；
- 左、中、右和跨画面位置；
- 前景、中景、背景；
- 视觉锚点与人物、物体、环境和抽象结构的交互；
- 无具体名词时的抽象视觉载体生成；
- 相邻分镜构图去重复。

### 15.3 回归测试

- 现有身份快照和哈希保持稳定；
- 旧合同可正常读取；
- 未启用强制模式的路径不受影响；
- 快速版图片模型的正向提示词包含全部业务硬约束；
- 真实十六帧故障样本重新运行后，不再出现空主体、全员被动观察、硬截断和跳过检查成功。

## 16. 监控与追踪

每帧记录以下数据：

- 文案主张和必要主体；
- 参与机制、动作、目标和语义必要性；
- 位置、大小、景别和融合关系；
- 身份快照哈希；
- 最终提示词各段字符数和占比；
- 图片模型、工作流、种子和生成耗时；
- 成图检查各项结果；
- 修复次数、失败原因和最终状态。

任务级汇总必须展示：锚点可见率、主体保留率、语义失败率、修复率、硬截断率、检查跳过率和单帧总耗时。

## 17. 实施顺序

### 阶段一：修通合同主链路

- 新增联合场景合同；
- 强制内容必要主体非空；
- 把现有 `ContentBoundIPPlanner` 接入 `VisualPromptComposer` 的实际生产链路；
- 取消缺席状态和角色面积上限。

完成标志：每帧在生成前都有完整的“文案主体 + 锚点职责 + 动作目标 + 空间关系”。

### 阶段二：重写确定性提示词编译

- 移除最终大语言模型二次组装；
- 实现四段自然语言编译和预算；
- 清理内部枚举泄漏；
- 禁止保护事实硬截断。

完成标志：相同合同稳定生成不超过八百字符的自然提示词。

### 阶段三：强制成图检查和修复

- 扩展成图检查项；
- 接入最多两次定向修复；
- 检查不可用时任务失败；
- 完整保存追踪数据。

完成标志：只有视觉锚点、内容主体和交互关系全部通过的图片才能进入视频生成。

### 阶段四：全量回归与灰度

- 跑完七十二帧通用验收集；
- 重跑历史故障样本；
- 先对内部任务启用，再对新建强制锚点任务全量启用；
- 旧任务保持只读兼容。

完成标志：所有必须级指标达到上线门槛。

## 18. 风险与处理

| 风险 | 处理方式 |
|---|---|
| 锚点身份描述过长挤压内容 | 身份只保留最低可识别特征并限制为总长度百分之三十 |
| 抽象文案没有具体主体 | 先生成可审计的抽象视觉载体，再进入联合场景规划 |
| 锚点尺寸过小无法识别 | 成图检查按身份最低特征判断，不只看面积 |
| 锚点过大遮住内容 | 检查必要主体可见性；全画面时要求内容通过动作和环境继续存在 |
| 严肃内容被角色可爱化 | 使用克制策略，禁止卖萌、庆祝和滑稽动作 |
| 图片模型忽略复杂指令 | 缩短提示词、把硬约束放在正向描述、失败后定向修复 |
| 成图检查误判 | 保存证据和分项结果，允许离线复核，不允许静默放行 |
| 连续分镜动作重复 | 规划时读取相邻两帧的机制、动作、位置和尺度并执行去重 |

## 19. 外部方案借鉴

以下项目只用于验证架构方向，不直接复制代码：

- [StoryForge](https://github.com/Oldcircle/storyforge)：把角色卡、场景资料、导演规划和确定性渲染计划分层，证明“模型负责创意，程序负责一致性”的方向正确；
- [Story2Board](https://github.com/DavidDinkevich/Story2Board)：强调跨分镜身份一致性与逐格构图控制必须同时存在；
- [StoryDiffusion](https://github.com/HVision-NKU/StoryDiffusion)：提供连续图像角色一致性的模型侧参考，但不能替代本文档的内容绑定规划；
- [VibeFrame](https://github.com/vericontext/vibeframe)：采用书面需求、生成计划、资产生成、成本与失败恢复的分层流水线，可借鉴可追踪执行方式；
- [IP-Adapter](https://github.com/tencent-ailab/IP-Adapter)：提供参考图身份注入能力，属于后续增强，不解决锚点为何出现在场景中的语义问题；
- [Z-Image](https://github.com/Tongyi-MAI/Z-Image)：当前图片模型的官方实现；快速版不应依赖负向提示词承载业务硬约束。

借鉴结论只有三条：

1. 角色身份与单帧构图必须分开管理；
2. 创意规划必须输出结构化合同，程序负责守住事实；
3. 参考图能增强身份一致性，但不能替代“文案与锚点共同成景”的语义规划。

## 20. 完成定义

本需求只有在以下条件全部满足时才算完成：

- 本文档中的十二项功能需求全部实现，其中所有“必须”项通过自动化测试；
- 七十二帧通用验收集全部完成成图检查；
- 真实故障样本不再出现空主体、被动陪站、角色替代主体、枚举泄漏、提示词硬截断和检查跳过成功；
- 每帧都能从追踪记录回答：“原文说什么、锚点为什么在、锚点做什么、锚点和谁发生关系、为什么放在这里、成图是否兑现”；
- 未通过成图检查的帧不能进入视频生成。

最终产品规则可以用一句话概括：**视觉锚点必须每帧出现，但画面不是围着锚点硬编；系统必须先理解文案，再让视觉锚点以最合适的动作、大小和位置参与同一个场景。**
