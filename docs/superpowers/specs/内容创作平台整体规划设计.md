# 内容创作平台整体规划设计

## 1. 定位

Pixelle 不应继续被设计成“视频生成脚本集合”，而应被设计成一个大的 AI 内容创作平台。

平台的核心目标是：

- 从一个主题、一段文案、一组素材或一个角色出发，生成可发布的视频内容。
- 让文案、分镜、风格、提示词、声音、图片、视频、字幕、重点文字、模板和成片都成为可追踪、可编辑、可复跑的创作资产。
- 让不同入口共享同一套平台能力，而不是每个入口各自维护一条孤立链路。
- 让生成速度、质量、稳定性和后续编辑能力同时提升，而不是只追求一次性出片。

因此后续开发原则不是“最小改动优先”，而是：

**平台原语优先，分阶段落地；兼容现有链路，但新增能力必须进入统一契约。**

## 2. 当前基础

项目已经有一些正确的底座：

- `LinearVideoPipeline / PipelineContext` 已经把标准生成链路拆成生命周期阶段。
- `StandardPipeline` 已经覆盖 `文案 -> 视觉规划 -> TTS/媒体 -> 成片合成` 主链路。
- `RenderManifest / SentenceUnit / CaptionCue / VisualClip` 已经开始形成渲染包契约。
- `TemplateRenderContext` 已经明确 compiled HyperFrames 模板的任务输入契约。
- HyperFrames compiled path 已经具备长期统一渲染的雏形。
- 日志持久化和 AI Creation observability 已经有设计文档。
- 图片加字方案已经明确不应把文字层硬塞进 prompt 返回对象，而应独立建模为 `TextOverlayPlan`。

这些说明项目方向是对的，但还缺少一份总规划来约束后续所有功能。

## 3. 核心问题

当前最大的风险不是某一个功能慢，而是平台边界还不够稳：

1. UI、API、pipeline、provider、渲染层之间仍存在参数直传和局部判断。
2. `StandardPipeline` 承担了过多职责，既做业务编排，又做 backend 选择、TTS 策略、HyperFrames 构建、metadata 落盘。
3. 文案、分镜、提示词、字幕、文字层、音频策略还没有统一创作包模型。
4. legacy 渲染、HyperFrames、HTML、ASS、模型原生画字容易各自形成数据模型。
5. 日志和 metadata 还不足以完整回答“慢在哪里、失败在哪里、能否局部复跑”。
6. History 当前更像结果列表，还不是创作工作台。

如果继续用局部补丁推进，后续会出现多个时间线、多个文字层模型、多个任务状态模型，维护成本会很快上升。

## 4. 总体架构

推荐采用七层平台架构。

```text
入口层
  Quick Create / Custom Media / Digital Human / Image to Video / Action Transfer / API

创作请求层
  CreationRequest / CreationSession / CreationMode / UserIntent

创作规划层
  ContentPlan / StoryboardPlan / StylePlan / PromptPlan / AudioPlan / TextOverlayPlan / RenderPlan

资产生产层
  LLM / Qwen / TTS / ComfyUI / RunningHub / Local Processing / Cache / Provider Telemetry

统一时间线层
  Canonical Timeline / RenderManifest / Tracks / Cues / AssetRefs

渲染执行层
  HyperFrames compiled primary / legacy ffmpeg fallback / ASS burn-in / HTML frame overlay / model-native text

工作台与可观测层
  History / Run Detail / Logs / Stage Metrics / Partial Rerun / Versioned Artifacts
```

这七层不是要求马上大重写，而是要求后续所有设计都能落到这些边界里。

## 5. 平台原语

### 5.1 CreationRequest

统一所有入口的输入。

它应该表达：

- 用户输入来源：主题、文案、素材、图片、视频、角色、动作参考。
- 生成目标：短视频、图片序列、数字人、图生视频、动作迁移。
- 质量策略：快速出片、标准质量、精修质量。
- 输出规格：比例、时长、语言、模板、声音、字幕、文字层、渲染 backend。
- 复跑策略：全量生成、只重跑文案、只重跑 TTS、只重跑媒体、只重渲染。

UI 和 API 都应该生成 `CreationRequest`，而不是各自拼接 pipeline 参数。

### 5.2 CreationRun

每次生成都是一次 run。

它应该记录：

- `run_id`
- `request_id`
- `task_id`
- 输入快照
- planning 结果
- asset 结果
- timeline 结果
- render 结果
- observability summary
- 失败和重试信息

History 应该展示 `CreationRun`，而不是只展示最终视频文件。

### 5.3 CreationPackage

这是从规划到渲染之间的核心创作包。

建议包含：

- `content_plan`
- `storyboard_plan`
- `style_plan`
- `prompt_plan`
- `audio_plan`
- `text_overlay_plan`
- `asset_manifest`
- `render_plan`
- `observability_refs`

`CreationPackage` 是平台内部的创作资产模型；`RenderManifest` 是渲染执行模型。

### 5.4 RenderManifest v2

长期方向是把 `RenderManifest` 扩展成统一时间线的唯一渲染输入。

建议包含：

- `visual_tracks`
- `audio_tracks`
- `caption_tracks`
- `overlay_text_tracks`
- `effect_tracks`
- `template_slots`
- `asset_refs`
- `timeline`
- `render_backend`

重要原则：

- 字幕、重点词、模板文字都属于 timeline track，不应散落在 HTML 全局变量、ASS 临时文件或 prompt 结果里。
- HTML、ASS、HyperFrames、模型原生画字只是 renderer/backend，不是数据模型源头。
- `TemplateRenderContext` 只能消费编译后的上下文，不能成为旁路参数入口。

## 6. 关键设计决策

### 6.1 HyperFrames 是长期主线

HyperFrames compiled path 应该成为长期主渲染路线，因为它天然适合统一时间线、模板、字幕、文字层和可视化编排。

legacy ffmpeg 拼接继续保留，但定位是：

- 兼容旧模板
- fallback
- 对比性能
- 某些简单场景的稳定出口

新能力优先接入 HyperFrames compiled path，再按必要性兼容 legacy。

### 6.2 文字层必须平台化

图片加字不是单独功能，而是 Text Layer 能力。

建议统一为：

- `CaptionTrack`：正常字幕
- `OverlayTextTrack`：重点词、短句、标题卡、画面强调文字
- `TemplateTextSlot`：模板固定槽位文字
- `ModelNativeTextHint`：给图像/视频模型的原生画字提示

这些都从同一份 `TextOverlayPlan` 或后续 `TextTrackPlan` 编译而来。

### 6.3 速度优化先依赖观测性

速度优化必须先能量化。

每次 run 至少应知道：

- 总耗时
- AI Creation 耗时
- LLM 调用次数
- 每次 LLM 的 stage、model、prompt_chars、schema_chars、latency_ms
- Qwen fallback 是否重复拼 schema
- storyboard planning 耗时
- prompt batch 耗时
- TTS 提交、排队、执行、下载耗时
- media 提交、排队、执行、下载耗时
- final render 耗时
- cache hit/miss

没有这些数据时，不应盲目调整媒体并发或重构渲染。

### 6.4 工作台比结果页更重要

平台最终不应只有“生成结果历史”。

History 应升级为创作工作台：

- 看每次 run 的阶段耗时
- 看每个分镜的文案、提示词、素材、声音、字幕、文字层
- 局部重跑某个阶段
- 复制一次 run 做变体
- 比较两次 run 的质量和耗时
- 保留调试产物和渲染包

这会把 Pixelle 从生成工具推进到创作平台。

## 7. 优化路线

用户明确要求速度、架构、体验都要做，所以这里不做三选一，而是分成五条并行主线。

### 主线 A：可观测性和任务档案

目标：让每次生成可诊断、可复盘、可比较。

工作内容：

- 落地全局 JSONL 日志和 task-scoped 日志。
- `Quick Create -> AI Creation` 输出结构化阶段事件。
- `metadata.json` 增加 observability summary。
- History 展示慢阶段、LLM 次数、总耗时、失败原因。
- 任务目录保留 `runtime.jsonl`、`ai_creation.jsonl`、`render_manifest.json`、关键 planning artifacts。

验收：

- 任意一次 Quick Create 完成后，只看任务目录即可判断最慢阶段。
- 不打开控制台也能知道 Qwen 调用了几次、每次多久。
- 用户可以从 History 看到“卡住体感”到底发生在哪一步。

### 主线 B：LLM 与规划链路减负

目标：让文案、标题、视觉规划、分镜、提示词更快且更稳。

工作内容：

- 去掉 Qwen fallback 下重复 schema 拼接。
- 给 LLMService 统一 stage telemetry。
- 对 style resolution 做跨任务持久缓存和命中率统计。
- 对 storyboard planning、prompt batch 引入可控缓存。
- 拆分 prompt builder 和 schema 注入职责。
- 只在依赖关系允许时并行 LLM 调用，避免为了并行牺牲质量。
- 增加快速模式：先出片，再精修。

验收：

- 默认 Quick Create 首次生成减少稳定等待点，或同请求数下总 LLM 耗时下降。
- 相同输入二次生成能看到缓存命中。
- prompt/schema 体积可观测。
- 快速模式和标准模式质量策略明确，不互相污染。

### 主线 C：统一时间线和渲染契约

目标：建立平台长期扩展的核心骨架。

工作内容：

- 明确 `CreationPackage -> RenderManifest` 编译流程。
- 扩展 `RenderManifest` 支持 text overlay tracks。
- 不再让 renderer 各自维护时间线。
- `TextOverlayPlan` 独立建模，不挂在 prompt 返回契约里。
- `TemplateRenderContext` 只作为 compiled template 的任务输入。
- HyperFrames compiled path 优先消费统一 manifest。

验收：

- 字幕、重点词、模板文字可以在同一 timeline 下解释。
- HTML / ASS / HyperFrames / 模型原生画字都消费同一份上游计划。
- 新增文字层或效果层时，不需要改多个平行时间系统。

### 主线 D：媒体、TTS 和渲染性能

目标：在有观测数据后优化真正瓶颈。

工作内容：

- 拆分 TTS 和媒体外部 workflow 的提交、排队、执行、下载耗时。
- 保留 `master_track` 和 `per_frame` 两种音频策略。
- `master_track` 优化全片吞吐，`per_frame` 保留局部文案重试速度。
- 对生成媒体做资产级缓存和复用。
- HyperFrames 扩覆盖，减少 legacy 多段拼接和重复编码。
- legacy 只在数据证明有价值时做定向优化。

验收：

- 能判断慢在供应商排队、远端执行、本地处理还是最终渲染。
- 改一个分镜文案时，能局部复跑而不是全链路重做。
- HyperFrames path 覆盖的模板逐步增加，且 fallback 原因可见。

### 主线 E：创作工作台体验

目标：让用户从“一次性生成”进入“持续创作和精修”。

工作内容：

- History 升级为 run detail。
- 每个分镜展示文案、提示词、图片/视频、音频、字幕、文字层。
- 支持复制 run、局部复跑、切换声音/风格/模板。
- 支持查看和对比不同 run 的耗时与质量。
- 支持调试产物下载：manifest、ASS、HTML context、logs。

验收：

- 用户不需要重新输入全部内容即可改局部并复跑。
- 用户能理解系统为什么慢、为什么失败、为什么用了 fallback。
- 创作过程本身成为可沉淀资产。

## 8. 阶段落地

### 阶段 0：冻结总契约

目标：避免后续继续发散。

产物：

- 本规划文档确认。
- 明确 `CreationRequest / CreationPackage / RenderManifest v2 / TextOverlayPlan / ObservabilitySummary` 的边界。
- 明确 legacy 与 HyperFrames 的长期定位。

### 阶段 1：可观测性先落地

目标：先让所有优化有数据支撑。

范围：

- 日志持久化
- AI Creation stage events
- metadata observability
- History 基础展示

### 阶段 2：LLM 链路优化

目标：解决当前 Quick Create 体感慢的主要来源。

范围：

- Qwen schema 去重
- prompt size telemetry
- style/storyboard/prompt cache
- 快速模式
- 安全并行

### 阶段 3：时间线和文字层平台化

目标：把图片加字、字幕、重点词、模板文字纳入统一契约。

范围：

- `TextOverlayPlan`
- `RenderManifest` text tracks
- HyperFrames compiled 消费文字层
- ASS/HTML/model-native backend 适配

### 阶段 4：工作台化

目标：把 History 变成创作工作台。

范围：

- run detail
- per-frame asset inspection
- partial rerun
- run duplicate
- artifact comparison

### 阶段 5：扩大平台入口

目标：让其他入口也进入统一平台内核。

范围：

- Custom Media
- Digital Human
- Image to Video
- Action Transfer
- API batch creation

这些入口不应重写成同一条 pipeline，而应统一到同一套 request、planning、timeline、observability 契约。

## 9. 不建议做的事

以下事情会留下长期技术债：

- 为图片加字单独做一套时间线。
- 把 overlay 语义硬塞进 `CaptionCue.style_profile`。
- 把 renderer-specific 参数从 UI 一路透传到底。
- 在 HTML 模板里绕过 `TemplateRenderContext` 读取全局变量。
- 在 ASS、HTML、HyperFrames 各自维护 cue 数据。
- 在没有 telemetry 前盲目调大媒体并发。
- 直接把所有 pipeline 合并成一个大框架。
- 立即废弃 legacy。
- 只用日志文本，不把 summary 落到 metadata。
- 把快速模式改成标准模式默认行为，牺牲质量上限。

## 10. 推荐的近期拆分

本规划确认后，建议拆成 5 个实施计划：

1. `日志持久化与创作链路可观测性实施计划`
2. `Qwen 与 AI 创作链路减负实施计划`
3. `统一时间线与 RenderManifest v2 实施计划`
4. `TextOverlayPlan 与文字层平台化实施计划`
5. `创作工作台与局部复跑实施计划`

每个计划都应独立验收，但必须遵守本规划的边界。

## 11. 总结

Pixelle 的正确方向不是只把某个功能做出来，而是把每个功能沉淀成平台能力。

短期看，先补可观测性和 LLM 减负，可以立刻改善 Quick Create 的速度体感。

中期看，统一时间线、`RenderManifest v2` 和 `TextOverlayPlan` 会决定后续字幕、文字层、模板、转场、局部复跑能不能稳定扩展。

长期看，History 必须升级成创作工作台，让用户能持续编辑、比较、复跑和沉淀创作资产。

最终目标是：

**Pixelle 成为一个以统一创作包和统一时间线为内核的 AI 内容创作平台，而不是一组彼此靠参数连接的视频生成脚本。**
