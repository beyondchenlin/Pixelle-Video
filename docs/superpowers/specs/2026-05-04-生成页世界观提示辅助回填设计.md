# 生成页世界观提示辅助回填设计

日期：2026-05-04

## 0. 范围与前提

本文只覆盖“生成页世界观提示”的下一阶段增强：为现有 `世界观提示` 输入框补上两个辅助回填入口：

- `根据文案生成`
- `使用 IP 默认`

它建立在当前 `dev` 已落地的主链路之上：

- `generation_world_hint`
- `ContentWorldPlanner`
- `generation_world_profile`
- storyboard planner / IP usage planner / image prompt generation 消费链路

本轮**不重做**已有主链路，不回退到旧方案，不把请求级世界观写回 `AssetBible`。

## 1. 目标

本轮目标只有四个：

1. 用户在生成页能直接点击按钮，把“世界观提示”快速填入当前文本框。
2. `根据文案生成` 必须复用现有 `ContentWorldPlanner` 语义，不允许前端本地瞎拼一段文本冒充世界观规划。
3. `使用 IP 默认` 只能使用当前已选 IP 的 `IPProfile.world_hint`，并且只做前端回填，不进入 API 请求。
4. 正式生成时的请求合同、后端主链路、`AssetBible` 事实源边界保持不变。

- 当前没有一个“只生成世界观草稿、不触发正式生成”的标准 API。

## 3. 备选方案

### 方案 A：前端本地拼接草稿文本

做法：

- 直接在前端读取 `content_context`、`world_preset_id`、`ip_profile_world_hint`
- 用规则拼一段自然语言，回填到文本框

优点：

- 改动少
- 没有新增 API

问题：

- 复刻了一份“世界观归纳逻辑”，和 `ContentWorldPlanner` 分叉
- 无法保证和正式生成链路的世界观语义一致
- 后续维护容易演变成前端临时规则堆积

结论：**不采用。**

### 方案 B：新增世界观草稿接口，复用 `ContentWorldPlanner`，再把结构化结果确定性转成可编辑草稿文本

做法：

- 新增 `POST /api/content/world-hint-draft`
- 后端复用 `ContentWorldPlanner`
- 对 `ContentWorldProfile` 做确定性文本渲染，返回一段用户可编辑的世界观提示草稿
- 前端按钮只负责请求、回填、提示

优点：

- 和正式生成链路共享同一套世界观理解源头
- 不引入第二条隐性 prompt 规划链路
- 文本框里仍然是用户可编辑文本，不暴露 JSON
- 后续其他入口如果需要世界观草稿，也可复用这个接口

问题：

- 需要补一个轻量 API 和前端请求 helper
- 需要明确 `ContentWorldProfile -> 文本草稿` 的渲染规则

结论：**采用方案 B。**

### 方案 C：复用正式生成或图片提示词预览接口来间接拿草稿

做法：

- 通过正式内容生成链路、预览链路或图片提示词链路侧向拿回一段世界观文本

优点：

- 表面上少一个接口

问题：

- 语义不纯，接口职责错误
- 容易混入无关参数、性能成本和副作用
- 用户点击“根据文案生成”不应触发正式规划或图片提示词阶段

结论：**不采用。**

## 4. 采用方案

### 4.1 总体原则

本轮采用：

- **前端显式按钮**
- **后端轻量草稿接口**
- **复用现有 `ContentWorldPlanner`**
- **正式生成合同零侵入**

也就是说：

1. 正式生成仍然只认 `generation_world_hint`
2. 按钮只是帮助用户填这个字段
3. 字段一旦填入，之后仍由现有正式链路消费

### 4.2 用户交互

在生成页现有 `世界观提示` 输入框附近增加两个辅助按钮：

1. `根据文案生成`
2. `使用 IP 默认`

行为定义：

- 用户可继续手填，按钮不是必选流程
- 点击按钮即表示允许覆盖当前文本框内容
- 不做自动 merge，不做隐藏拼接，不保留第二份影子字段
- 回填后文本框仍然是普通可编辑文本

### 4.3 `使用 IP 默认`

它的语义非常严格：

- 只读取当前已选 IP 的 `IPProfile.world_hint`
- 只把该文本回填到当前 `storyboard_generation_world_hint`
- 不发 API
- 不写回 `AssetBible`

异常情况：

- 未启用 IP：前端 warning
- 当前 IP 没有 `world_hint`：前端 warning

### 4.4 `根据文案生成`

它的语义也必须严格：

- 输入来源：
  - `content_context.text`
  - `content_context.title`（可选）
  - 当前 `world_preset_id`（可选）
  - 当前已选 IP 的 `IPProfile.world_hint`（可选，仅作兼容参考）
- 处理方式：
  - 调用新增 `POST /api/content/world-hint-draft`
  - 后端复用 `ContentWorldPlanner`
  - 再将 `ContentWorldProfile` 渲染成可编辑自然语言草稿
- 输出结果：
  - 覆盖回填到 `storyboard_generation_world_hint`

这个接口只用于生成**草稿文本**，不产出正式图片提示词，不触发 storyboard/image/video 正式阶段。

## 5. 后端设计

### 5.1 新增接口

新增接口：

- `POST /api/content/world-hint-draft`

请求字段：

- `source_text: str`
- `title: str | None`
- `world_preset_id: str | None`
- `storyboard_prompt_language: "zh_CN" | "en_US"`
- `ip_default_world_hint: str | None`

响应字段：

- `world_hint_draft: str`
- `generation_world_profile: dict`
- `hint_source: str`

注意：

- `hint_source` 只是调试和可观测信息，不是正式生成请求字段
- 返回 `generation_world_profile` 仅供前端或调试复用，不要求当前 UI 展示

### 5.2 复用 `ContentWorldPlanner`

新接口内部不引入第二套 LLM 世界观抽取逻辑，而是：

1. 把 `title` 与 `source_text` 规范化成一个草稿输入文本
2. 根据 `world_preset_id` 查询 `world_preset`
3. 调用 `ContentWorldPlanner.plan(...)`
4. 拿到 `ContentWorldProfile`
5. 用确定性规则渲染成 `world_hint_draft`

### 5.3 草稿文本渲染规则

新增一个小的后端纯 helper，负责把 `ContentWorldProfile` 渲染成文本草稿。

要求：

- 只输出用户可编辑自然语言
- 不输出 JSON
- 不输出字段名
- 不输出 markdown fence
- 不输出 hex 颜色
- 缺失字段自动跳过

中文建议形态：

- 一段 2 到 6 个短句构成的自然语言草稿
- 包含：
  - 当前内容世界概括
  - 时代/空间
  - 主要视觉环境
  - 故事边界
  - IP 融入方式

英语路径同理，但使用英文自然语言句式。

## 6. 前端设计

### 6.1 不改变正式 payload

本轮不新增任何正式生成请求字段。

保持：

- 正式生成时只发 `generation_world_hint`
- 不发送 `ip_profile_world_hint`
- 不发送“按钮来源”

### 6.2 先补纯 helper，再接 UI

为了解决 `style_config` 当前渲染顺序问题，本轮不强制重排整块 UI，而是新增一个纯 helper：

- 根据 `session_state`
- 根据已加载的 `asset_bibles`
- 解析当前选中 IP profile 的摘要信息

这样高级分镜控件在渲染前，就能拿到当前 IP 默认世界观，而不依赖 IP 控件先渲染完。

### 6.3 `style_config` 数据流

`render_style_config(...)` 中：

1. 统一加载一次 `asset_bibles`
2. 调用新 helper 解析当前已选 IP profile 摘要
3. 把 `content_context` 与 `ip_profile_world_hint` 传给高级分镜控件
4. 同一份 `asset_bibles` 再传给 IP 控件渲染

这样可以减少重复加载，也能保证按钮逻辑和 IP 选择逻辑读取的是同一个事实源。

### 6.4 高级分镜控件行为

`render_storyboard_advanced_controls(...)` 新增：

- `content_context`
- `ip_profile_world_hint`
- `world_hint_draft_generator`（可注入，便于测试）

其中：

- `使用 IP 默认`
  - 直接读取 `ip_profile_world_hint`
  - 成功后写入 `ui.session_state["storyboard_generation_world_hint"]`
  - `safe_rerun()`
- `根据文案生成`
  - 校验 `content_context.text`
  - 调用 `world_hint_draft_generator(...)`
  - 成功后写入 `ui.session_state["storyboard_generation_world_hint"]`
  - `safe_rerun()`

## 7. 边界与禁止事项

以下规则必须继续成立：

1. 不允许把 `generation_world_hint` 或其辅助生成结果写回 `AssetBible`
2. 不允许把 `ip_profile_world_hint` 发到 API
3. 不允许让辅助按钮直接修改 `generation_world_profile`
4. 不允许绕过 `ContentWorldPlanner` 在前端本地构造正式世界观语义
5. 不允许把“根据文案生成”扩展成新的聊天页或复杂工作台

## 8. 错误处理与降级

### 8.1 `使用 IP 默认`

- 未启用 IP：前端 warning
- 当前 profile 没有 `world_hint`：前端 warning

### 8.2 `根据文案生成`

- `source_text` 为空：前端 warning，不发请求
- 后端接口 422：前端提示输入不完整
- 网络或 HTTP 异常：前端 error

### 8.3 LLM 失败

后端不把 LLM 失败直接上抛为“功能不可用”，而是沿用 `ContentWorldPlanner` 当前 fallback 机制：

- 返回 fallback `ContentWorldProfile`
- 仍然渲染一版 `world_hint_draft`
- `hint_source = "fallback"`

也就是说，多数情况下按钮应该返回“可编辑草稿”，而不是完全失败。

## 9. 测试要求

至少覆盖：

1. 纯 helper
   - 当前选中 IP profile 摘要解析
   - `ContentWorldProfile -> world_hint_draft` 文本渲染
2. API
   - 新请求 schema 校验
   - endpoint 复用 `ContentWorldPlanner`
   - fallback 时仍返回草稿文本
3. 前端 UI
   - `使用 IP 默认` 能回填文本框
   - `根据文案生成` 能调用 generator 并回填
   - 空文案 / 无 IP 默认世界观时有提示
4. 回归
   - 正式生成请求仍只发 `generation_world_hint`
   - `ip_profile_world_hint` 仍不进入 API

## 10. 非目标

本轮不做：

- 新建 AI Chat IP 设计入口
- 把 `generation_world_profile` 暴露成用户可编辑 JSON
- 保存世界观草稿历史
- 自动把 IP 默认世界观同步到生成页
- 改写正式生成链路的合同字段

## 11. 验收标准

满足以下条件才算完成：

1. 生成页 `世界观提示` 输入框旁存在两个辅助按钮
2. `使用 IP 默认` 可把当前 IP 的 `world_hint` 回填到文本框
3. `根据文案生成` 可在不触发正式生成的情况下回填一版草稿
4. 正式生成合同仍然只使用 `generation_world_hint`
5. `ip_profile_world_hint` 仍然保持前端辅助字段，不发到 API
6. `ContentWorldPlanner` 仍然是世界观理解的唯一后端语义源
7. 相关前后端测试通过
