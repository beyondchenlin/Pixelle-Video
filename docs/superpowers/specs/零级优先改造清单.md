# 零级优先改造清单 v2

## 文档状态

- 版本：v2
- 更新日期：2026-04-24
- 适用范围：`Quick Create -> Standard Pipeline -> 文案 -> 视觉规划 -> TTS/媒体 -> 成片合成`
- 依据：当前代码与文档巡检、`codex://threads/019dbca5-ffdf-7fe0-958c-1e7149bcd451` 的性能排查结论

这版文档修正 v1 的两个问题：

1. v1 的大方向仍然成立，但部分事项已经在当前代码中落地，不能继续当作待办从零执行。
2. 下一步优先级应从“泛泛提速”收敛到“可观测性 + Qwen LLM 链路减负 + 快速模式”，再基于数据推进媒体和渲染优化。

---

## 一句话结论

当前“快速制作 -> AI 创作”链路的慢，既有真实耗时，也有 UI 和日志粒度不足造成的卡住体感。

v2 的 P0 不应该先做大重构，而应该先补齐主链路测速和 LLM telemetry；v2 的 P1 再集中处理 Qwen fallback 下的 schema 重复、串行 LLM 调用和缺少缓存的问题。

---

## V2 核心修正

### 仍然成立的判断

- 默认 Quick Create 入口会使用标准流水线。
- 默认模板类型偏向 `image`，因此会进入视觉规划和媒体生成链路。
- 默认分镜规划开启时，视觉规划内部会多走一段 LLM 分镜规划。
- Qwen 当前走 OpenAI-compatible chat fallback，不走 OpenAI 原生 structured output。
- UI 进度只显示阶段和短 `extra_info`，长 LLM 调用期间没有心跳式耗时反馈。

### 需要修正的 v1 判断

- `style resolution` 缓存已经存在，不应再作为“新增缓存”从零实现；下一步应补 `cache_hit/cache_miss` 日志，并扩展缓存到 storyboard planning 和 prompt batch。
- TTS `auto` 默认策略已经部分调整：HyperFrames 路径走 `master_track`，legacy + ComfyUI TTS 在 `auto` 下也走 `master_track`，本地 TTS 仍走 `per_frame`。
- 资产生产层已经有基础执行模式：静态模板跳过媒体、selfhost image + ComfyUI TTS staged、纯 RunningHub 并发、普通串行。
- 标题和旁白的真实顺序是先 `generate_content`，再 `determine_title`；它们逻辑上独立，后续可以并行或合并。
- “减少 1 到 3 次 LLM 请求”只在重复生成、缓存命中或合并调用时成立；首次生成稳定可减少的主要是标题调用和重复 schema 负担。

## 当前真实主链路

### Web 入口

1. `web/pipelines/standard.py`
   - `StandardPipelineUI.name = "quick_create"`
   - 三栏布局：内容输入、风格/模板配置、生成与预览
2. `web/components/content_input.py`
   - 输入模式：`generate` 或 `fixed`
   - `generate` 输入主题，`fixed` 输入完整文案
3. `web/components/style_config.py`
   - 默认模板类型为 `image`
   - Quick Create 调用 `render_style_config(..., storyboard_default_enabled=True)`
   - `static` 模板会禁用分镜规划控件
4. `web/components/output_preview.py`
   - 点击生成后构建参数并调用 `pixelle_video.generate_video(...)`
   - UI progress 仅由 `ProgressEvent` 驱动

### 后端标准流水线

`pixelle_video/pipelines/linear.py` 定义标准生命周期：

1. `setup_environment`
2. `generate_content`
3. `determine_title`
4. `plan_visuals`
5. `initialize_storyboard`
6. `produce_assets`
7. `post_production`
8. `finalize`

`pixelle_video/pipelines/standard.py` 里的当前重点：

- `generate_content`
  - `generate`：调用 `generate_narrations_from_topic`
  - `fixed`：调用 `split_narration_script`
- `determine_title`
  - 用户传 title 则跳过
  - `generate` 模式下 `generate_title(..., strategy="auto")`
  - 短主题可直接返回，长主题会多一次 LLM 调用
- `plan_visuals`
  - `static` 模板跳过 prompt 和媒体生成
  - `image/video` 模板进入 `generate_styled_image_prompt_batch`
- `generate_styled_image_prompt_batch`
  - 风格解析：`resolve_style_spec`
  - 可选分镜规划：`plan_storyboard_batch`
  - 图片或视频提示词 batch：`generate_image_prompts` / `generate_video_prompts`
  - 最终组装 prompt 和 negative prompt
- `produce_assets`
  - HyperFrames image 路径
  - legacy master-track TTS 预处理
  - selfhost staged
  - RunningHub parallel
  - 普通串行
- `post_production`
  - legacy concat + BGM
  - 或 HyperFrames compiled render

| 能力 | 当前状态 | 说明 |
| --- | --- | --- |
| 风格解析 runtime cache | 已有 | `pixelle_video/utils/style_resolution.py` 中已有 LRU cache |
| 静态模板跳过媒体链路 | 已有 | `static` 模板不生成 image prompts，也不生成媒体 |
| selfhost image staged 模式 | 已有 | selfhost TTS + selfhost image 时按 TTS、media、compose、segment 分阶段 |
| RunningHub 并发 | 已有 | 纯 RunningHub 且并发配置大于 1 时并行处理分镜 |

| HyperFrames backend fallback 记录 | 已有 | metadata 中记录 requested/effective backend |
| 分镜规划快照 | 已有 | task metadata/storyboard 中可保存 planning snapshot |

这些能力后续只应增强，不应重复实现。

## 当前仍缺的关键能力

### 1. 缺少统一测速基线

当前代码有局部 `perf_counter()` 日志，但没有统一的阶段统计对象，也没有把完整阶段耗时落到任务 metadata。

缺口包括：

- LLM 总耗时
- 每次 LLM 调用耗时
- prompt 字符数
- structured output 模式
- cache hit/miss
- 内容规划耗时
- 视觉规划耗时
- TTS 耗时
- 媒体生成耗时
- HTML 合成耗时
- segment 生成耗时
- 最终合成耗时

### 2. Qwen fallback payload 偏重

当前 `LLMService` 对非 OpenAI provider 会把 JSON schema 拼进 prompt。

但 `style_resolution` 和 `storyboard_planning` 的 prompt builder 已经包含 `required_output` schema，导致这两类请求在 Qwen fallback 下重复带 schema。

### 3. LLM 串行仍然偏多

当前首次生成的主要串行点：

- 旁白生成后再生成标题
- 风格解析后再分镜规划
- 分镜规划后再生成 base prompts

其中标题和旁白逻辑上独立；风格解析与分镜规划也基本独立，分镜规划主要依赖 narrations、world preset、shot preset 和控制项。

### 4. 缓存边界还不完整

已有缓存仅覆盖风格解析。仍缺：

- storyboard planning cache
- base prompt batch cache
- 标题/旁白联合结果 cache
- cache key 的统一规范和可观测日志

### 5. UI 长调用缺少心跳

UI 只在阶段开始、batch 完成或 frame step 时更新。单次 Qwen 调用如果持续 10 到 30 秒，用户会看到同一句进度文案不动。

### 6. 文档和代码现状不同步

v1 文档把若干已落地能力仍列成待办，容易导致重复实现或错误排期。

## V2 优先级

## P0：主链路可观测性和测速基线

### 要做什么

建立统一阶段耗时和 LLM telemetry，先让“慢在哪里”可量化。

至少覆盖：

- `content_planning`
  - narration 生成或 fixed split
  - title 生成
- `visual_planning`
  - style resolution
  - storyboard planning
  - base prompt batch
  - prompt assembly
- `asset_synthesis`
  - TTS
  - media generation
  - media download
  - HTML compose
  - segment render
- `render_assembly`
  - legacy concat
  - BGM mix
  - HyperFrames project write
  - HyperFrames render

LLM telemetry 至少记录：

- `stage`
- `model`
- `base_url_host`
- `prompt_chars`
- `enhanced_prompt_chars`
- `response_type`
- `structured_output_mode`
- `elapsed_ms`
- `cache_hit`
- `attempt`
- `error_type`

`stage` 不能只在 `LLMService` 内部猜测。实现时必须选择一种明确传递方式：

- 显式参数：给 `LLMService.__call__` 增加 `stage` 或 `telemetry_context` 参数，并从 `generate_title`、`generate_narrations_from_topic`、`resolve_style_spec`、`plan_storyboard_batch`、prompt batch 等调用点传入。
- 上下文变量：在 `StandardPipeline` 阶段上下文里设置当前阶段，`LLMService` 读取 contextvar，并允许调用点覆盖更细的子阶段。

推荐的最小阶段命名：

- `content_planning.title`
- `content_planning.narration`
- `visual_planning.style_resolution`
- `visual_planning.storyboard_planning`
- `visual_planning.base_prompt_batch`

### 主要改动点

- 在 `LLMService.__call__` 和 structured output fallback 内统一打点。
- 给所有 LLM 调用点补 `stage` 传递或接入统一 contextvar，避免 telemetry 只能记录成 `unknown`。
- 在 `StandardPipeline` 生命周期阶段挂 `StageTiming` 或轻量上下文对象。
- 在 `FrameProcessor` 的四个步骤内记录单帧耗时。
- 将阶段统计写入 task metadata，并在 History 页面可读。
- UI 增加长阶段心跳，例如“规划分镜中，已用 12.3s”。在当前 Streamlit 同步等待结构下，心跳不能只靠页面层定时器；需要由长阶段包装器或 LLM wrapper 启动轮询任务，等待真实任务完成期间每 1 到 2 秒发一次 `ProgressEvent`，或改为后台任务状态驱动 UI 刷新。

### 验收标准

- 任意一次 Quick Create 完成后，metadata 中能看到阶段耗时树。
- 能区分慢在 LLM、TTS、媒体、HTML 合成、segment 或最终合成。
- 每次 Qwen 调用能看到 prompt 规模和耗时。
- 每次 LLM telemetry 都有具体 `stage`，不能长期停留在 `unknown` 或空值。
- UI 长调用期间至少每 1 到 2 秒刷新一次已用时间。

## P1：Qwen LLM 链路减负

### 要做什么

先做低风险、收益明确的 LLM 优化。

优先顺序：

1. 去掉 Qwen fallback 下的重复 schema。
2. 标题和旁白并行，或合并成同一轮结构化输出。
3. 风格解析和分镜规划并行。
4. 增加 storyboard planning cache。
5. 增加 base prompt batch cache。

### 建议实现方式

#### 1. schema 去重

可选方案：

- 在 `LLMService` fallback 拼 schema 前检测 prompt 是否已有 `required_output`。
- 或给结构化调用增加参数，例如 `schema_instruction_mode="append" | "skip"`。
- 更长期可以让 prompt builder 不再内嵌完整 schema，只保留任务说明，由 `LLMService` 统一负责 schema。

优先推荐第二种，边界更清楚。

#### 2. 标题与旁白并行或合并

短期低风险：

- `generate` 模式下，`generate_narrations_from_topic` 和 `generate_title` 可并行。
- 用户传 title 或短主题 direct shortcut 时自然跳过额外请求。

中期更优：

- 新增联合响应模型：`GeneratedContentPlan(title, narrations)`。
- 只对 `generate` 模式使用。
- `fixed` 模式仍保留现有 split + title 逻辑。

#### 3. 风格解析与分镜规划并行

`plan_storyboard_batch` 当前不直接依赖 `resolved_style`，主要依赖 narrations、预设和用户控制项，因此可以和 `resolve_style_spec` 并行。

需要注意：

- prompt assembly 仍然要等两者都结束。
- 如果后续 planner 需要读 style_profile，则并行策略要重新评估。

#### 4. cache key 规范

建议缓存键统一包含：

- 输入文本或 narrations hash
- scene count
- min/max words
- prompt prefix source identity
- world preset id
- shot preset id
- consistency/content/role/shot strategy
- frame overrides identity
- workflow/media type
- planner 或 prompt builder 版本

### 验收标准

- 默认 Quick Create 首次生成至少减少一个稳定 LLM 等待点，或同等请求数下总 LLM 耗时下降。
- Qwen fallback 的 style/storyboard prompt 字符数下降。
- 同配置重复生成时，visual planning 至少有一处稳定 cache hit。
- 所有优化都能从 P0 telemetry 中看到收益。

## P2：Web 快速模式

### 要做什么

给 Quick Create 增加面向“先出片，再精修”的快速模式，避免把标准模式直接改成低约束模式。

快速模式建议默认：

- 关闭 storyboard planning
- scene 数限制为较小值
- 使用 static 或轻量 image 模板
- 使用快模型或可配置轻量 LLM preset
- 标题与旁白并行或合并
- 优先本地 TTS
- 保留一键切回标准模式

### 设计原则

- 快速模式是独立用户意图，不替代标准模式。
- 标准模式继续优先质量、连贯性和可控性。
- 快速模式 UI 只暴露少量必要开关，不把所有高级配置平铺出来。

### 验收标准

- 用户能一键切换“快速 / 标准”。
- 快速模式下默认不会触发 storyboard planning。
- 同样主题下，快速模式的首屏等待和总耗时显著低于标准模式。
- 切回标准模式后不影响现有分镜规划和模板配置。

---

## P3：媒体生产和最终合成优化

### 前置条件

只有在 P0 数据证明媒体或最终合成是当前主要瓶颈后，才进入 P3。

### 可选方向

- 扩大 HyperFrames compiled 对常用 image 模板的覆盖。
- legacy 路线减少“每帧独立 mp4 再 concat”的重复编码成本。
- selfhost staged 增加保守并发上限，但必须尊重 GPU 显存和 ComfyUI 队列能力。
- 对已有素材或静态模板继续扩大跳过逻辑。

### 验收标准

- 同一组样本里，媒体或合成阶段耗时下降能从 metadata 直接看出。
- HyperFrames 与 legacy 输出时长、音频、尺寸一致性达标。
- selfhost 并发不会引入不稳定重试或显存错误。

---

## P4：轻量封层，不做大重构

### 要做什么

在当前 `StandardPipeline` 内部继续收敛阶段边界，而不是把所有 pipeline 合并成统一大框架。

建议阶段：

1. `ContentPlanning`
2. `VisualPlanning`
3. `AssetSynthesis`
4. `RenderAssembly`

### 实施方式

- 优先抽私有方法和轻量数据对象。
- 阶段边界挂测速、缓存和参数快照。
- 不在第一轮拆出大量新模块。

### 验收标准

- 新增一个测速点或缓存点，不需要横跨多处业务代码。
- 阶段输入输出清晰。
- 旧测试不需要大面积重写。

---

## 不建议做的事情

- 不要在没有 P0 基线前盲目调媒体并发。
- 不要把 storyboard planning 在标准模式里直接默认关闭，除非产品明确牺牲连贯性换速度。
- 不要重复实现已经存在的 style resolution cache。
- 不要重复实现已经存在的 staged asset path。
- 不要一上来重写 `digital_human / i2v / action_transfer`。
- 不要把所有 pipeline 合并成统一大框架。
- 不要只凭一次 5-scenes 样本判断所有场景瓶颈。
- 不要只优化后端日志，UI 体感也必须同步改善。

## 建议固定测速样本

至少固定 4 组样本，每组记录首次运行和重复运行：

1. `generate + image template + 5 scenes + storyboard on`
2. `generate + image template + 5 scenes + storyboard off`
3. `fixed + static template + 8 scenes`
4. `generate + image template + 12 scenes + comfyui tts`

每组记录：

- 总耗时
- LLM 总耗时
- LLM 请求数
- LLM prompt chars
- LLM cache hit 次数
- TTS 总耗时
- 媒体生成总耗时
- HTML 合成总耗时
- segment 生成总耗时
- 最终渲染总耗时
- UI 中最长无刷新等待时间

## V2 完成定义

本轮完成不以“改了多少代码”为标准，而以这些结果为准：

1. 主链路每层耗时可见。
2. 每次 Qwen 调用的规模、耗时和结构化模式可见。
3. 标准模式下至少一个稳定 LLM 等待点被减少或并行化。
4. 重复生成时至少一个视觉规划阶段能稳定命中缓存。
5. 快速模式可单独提供更短等待路径，不破坏标准模式质量。
6. 后续媒体和渲染优化有数据依据，而不是靠体感排序。

## 最终判断

v1 的方向是对的：主链路需要提速，日志和 UI 进度也确实不够细。

v2 的调整是：先承认当前代码已经具备一部分优化基础，然后把下一步集中到最有确定性的地方：

`可观测性 -> Qwen LLM 减负 -> 快速模式 -> 媒体/渲染数据驱动优化`

这样推进风险更低，收益也更容易被量化。
