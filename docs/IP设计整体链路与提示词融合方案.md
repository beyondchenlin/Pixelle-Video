# IP 设计整体链路与提示词融合方案

## 1. 文档目的

本文档用于沉淀当前关于 Pixelle IP 设计能力的讨论结论，作为下一阶段产品设计、技术设计和实现计划的共同依据。

这里的 IP 设计不是单纯创建一个角色，也不是把一段固定提示词追加到最终图片提示词末尾。真正需要解决的是：当用户上传一段长文案、选择高级分镜规划、选择风格提示词，并启用某个 IP 形象后，系统如何在每一帧里合理判断 IP 是否出现、以什么身份出现、如何变化，并最终生成一段流畅、可用于 Z-Image 文生图的综合提示词。

本文只讨论方案，不代表当前代码已经全部实现。

## 2. 当前共识

### 2.1 IP 创作不是核心难点

IP 的初始创作可以有多种入口：

- 用户自然语言描述生成 IP。
- 用户上传图片，由视觉模型反推形象提示词。
- 用户上传图片后再用自然语言二次创作。
- 用户从其他大模型生成好 IP 文本后复制进来。
- 用户在 AI Chat 里持续修改已有 IP。

这些能力对用户体验有价值，但不是当前最关键的系统难点。更关键的是 IP 被设计好之后，如何在用户长文案生成图片的主链路中被合理使用。

### 2.2 IP 使用才是主系统

用户可能输入几百字到几千字的长文案。系统会先把长文案拆成分镜，再结合高级分镜规划、风格前缀和图片生成模型要求，生成每一帧图片提示词。

IP 不应简单地覆盖每一帧，也不应无条件成为所有画面的主角。系统必须理解每一帧的语义，然后判断：

- 这一帧 IP 是否应该出现。
- IP 是主角、讲解员、观察者、背景符号，还是不出现。
- IP 是否会误替代原文案里的核心主体。
- IP 的固定身份应该保留哪些锚点。
- IP 的动作、表情、服装、道具、站位应该如何随语境变化。
- IP 与风格前缀、高级分镜、镜头规划如何融合成一段自然提示词。

## 3. 现有项目链路理解

当前项目中，生成图片前的文本链路大致是：

```text
用户主题或长文案
-> Script / narration
-> StoryboardPlan
-> FramePlan / 高级分镜规划
-> ImagePromptComposer
-> generate_image_prompts 生成 base prompt
-> style resolution / prompt prefix / storyboard prompt assembly
-> PromptPlan.final_prompt
-> 图片生成
```

当前代码已经有以下基础能力：

- `StoryboardPlan`：保存分镜事实源。
- `FramePlan`：保存每帧的镜头、主体、世界元素、连续性锚点等信息。
- `ImagePromptComposer`：从分镜计划生成图片提示词。
- `prompt_prefix` / style resolution：把风格前缀解析成结构化风格。
- `PromptPlan`：保存最终图片提示词，并预留 `character_ids`、`scene_id`、`prop_ids`、`style_id`。
- `AssetBible` / `SceneCast`：保存 IP、角色、场景、道具、风格和每帧资产引用。

当前缺口是：IP 还没有真正进入图片提示词生成主链路。现有 `SceneCast` 更偏向资产 ID 绑定，尚未自动生成“这一帧 IP 如何出现、如何动作、如何穿着、如何站位”的文本表达。

## 4. IP 信息分层

为了让大模型能稳定理解 IP，又不让 IP 约束压垮画面生成，IP 信息应该拆成四层。

### 4.1 硬锁定项

硬锁定项决定“这个角色是谁”，原则上不能被场景、风格或分镜改掉。

典型字段：

- 物种或角色类型，例如白色兔子。
- 主色和核心配色。
- 核心轮廓，例如长耳朵、圆脸、头身比例。
- 标志配件，例如蓝色领带。
- 固定结构，例如耳朵形状、脸型、身体比例。
- 禁止变化项，例如不能变成人、不能变成其他动物、不能丢掉蓝色领带。
- 语义边界，例如不能替代佛祖、历史人物、真实人物或文案中的核心主体。

硬锁定项应该在系统内部强约束，但最终 prompt 中每帧只写最关键的 2 到 4 个。

### 4.2 识别锚点

识别锚点是让观众一眼看出“还是同一个 IP”的核心要素。

示例：

- 白色兔体。
- 长耳朵轮廓。
- 蓝色领带。
- 圆脸。
- 固定眼睛或脸部结构。

每一帧不需要完整写出所有锚点，但如果 IP 出场，应至少保留 2 到 3 个强锚点可见。对于远景、背影、符号化出场等情况，可以降低锚点数量，但需要在连续性里补偿。

### 4.3 受控可变项

受控可变项决定 IP 如何融入具体画面。它们可以随用户文案、分镜和场景变化。

建议结构化为以下字段：

- `role_mode`：主角、讲解员、观察者、陪伴者、背景符号、不出场。
- `outfit_theme`：古代、现代、职业、贫寒、富贵、节日、旅行、课堂等。
- `outfit_condition`：整洁、破旧、战损、华丽、朴素、轻便。
- `accessories`：帽子、眼镜、披风、徽章、围巾、背包。
- `hand_prop`：书、卷轴、教鞭、灯笼、工具、地图、卡片。
- `body_action`：跑、跳、站、坐、蹲、指向、抬头、低头、靠近、后退。
- `gesture`：挥手、摊手、抱胸、托腮、翻书、举物、指路。
- `facial_expression`：开心、惊讶、困惑、严肃、悲伤、愤怒、专注、无奈。
- `gaze_target`：看天空、看道具、看对手、看镜头外、看观众。
- `body_orientation`：正面、侧身、背侧、半转身。
- `frame_position`：左侧、中央、右侧、前景、中景、背景。
- `interaction_target`：人物、动物、道具、文字板、天空、地面、场景元素。
- `era_mapping`：古代化、现代化、架空化、童话化、课堂化。
- `profession_mapping`：老师、旅人、士兵、商贩、讲解员、学生、助手。
- `continuity_state`：是否延续上一帧的服装、道具、情绪或动作结果。

可变项可以很多，但最终每帧 prompt 只应选择 3 到 5 个最有价值的变量写进去。

### 4.4 镜头归属项

镜头项主要归高级分镜系统负责，不应全部塞到 IP 本体里。

典型字段：

- 远景、中景、近景、特写。
- 平视、俯视、仰视、侧面。
- 全身、半身、脸部特写。
- 前景、中景、背景。
- 画面左侧、中央、右侧。
- 人物占比。
- 是否遮挡、是否留白。

IP 系统可以向镜头系统提出约束，例如“这帧必须看到蓝色领带”或“这帧需要全身显示长耳朵和动作”，但不应替代高级分镜系统。

## 5. 每帧 IP 出场模式

IP 是否出场，应按帧裁决，而不是全片统一硬塞。

建议使用以下模式：

### 5.1 `lead`

IP 是当前帧主角或主要行动者。

适用场景：

- 文案本身是围绕 IP 展开的。
- 科普、讲解、品牌短片需要 IP 强出场。
- 当前帧没有不可替代的原文核心主体。

约束强度：

- IP 相关内容可占 prompt 核心描述的 30% 到 40%。
- 必须保留多个识别锚点。
- 可以设计动作、表情、服装、道具。

### 5.2 `support`

IP 是讲解员、陪伴者、观察者或辅助角色。

适用场景：

- 原文案有明确主体，IP 不应替代主体。
- IP 适合解释、引导或陪伴观众。
- 知识类、历史类、故事类内容需要稳定讲解角色。

约束强度：

- IP 相关内容占 15% 到 25%。
- 保留 2 到 3 个识别锚点。
- 动作和站位应服务主画面，不抢主体。

### 5.3 `symbolic`

IP 只以符号形式出现。

形式包括：

- 徽章。
- 玩偶。
- 挂画。
- 贴纸。
- 招牌。
- 剪影。
- 角落小图标。

适用场景：

- 画面主体很强，不适合角色直接出现。
- 需要维持品牌存在感但不能打断叙事。
- 严肃、历史、宗教或纪实场景。

约束强度：

- IP 相关内容占 5% 到 10%。
- 只保留一个核心符号或配色锚点。

### 5.4 `ambient`

IP 作为世界观背景存在，不构成明确角色。

适用场景：

- 场景中自然出现少量 IP 视觉语言。
- 背景中有 IP 颜色、图案或轻量标识。

约束强度：

- 只保留一个轻量视觉提示。
- 不影响主画面语义。

### 5.5 `absent`

IP 不出现。

适用场景：

- 当前帧有不可替代的语义主体，例如佛祖、历史人物、真实人物、关键动物或关键事件。
- IP 出现会破坏氛围、逻辑或用户文案表达。
- 需要纯场景铺垫、情绪空镜或严肃画面。

## 6. 长文案场景中的 IP 占比原则

长文案生成图片时，不应该追求每一帧都出现 IP。应该按内容节奏做出场规划。

建议默认规则：

- 开头帧：可以让 IP 作为引导者或世界观入口出现。
- 解释帧：IP 适合做讲解员、指示者、观察者。
- 情节主体帧：IP 不应替代原文主体，可降为陪伴或不出现。
- 情绪空镜：IP 可以不出现，保留画面情绪。
- 总结帧：IP 可以回到画面中，作为收束角色。

对于几千字长文案，应避免 IP 高频主角化。更好的方式是形成节奏：

```text
出现 -> 弱化 -> 不出现 -> 观察 -> 符号化 -> 再出现
```

这样既能保留系列感，也不会破坏文案本身的画面表达。

## 7. 与风格前缀的关系

风格前缀和 IP 不是同一层。

风格前缀负责：

- 画风。
- 材质。
- 线条。
- 光影。
- 色彩氛围。
- 世界视觉语言。

IP 负责：

- 角色身份。
- 固定识别锚点。
- 可变动作、表情、服装、道具。
- 出场身份和语义边界。

因此需要遵守：

```text
风格是渲染层，IP 是身份层。
```

风格可以把白兔画成水墨、黏土、扁平卡通、童话插画或电影感 3D，但不能把白兔变成猫、变成人、变黑兔，不能丢掉蓝色领带这类身份锚点。

如果风格前缀本身带有强 IP 世界观，例如某种强品牌化世界，系统应先做冲突判断：

- 如果风格只是视觉风格，则可以正常渲染 IP。
- 如果风格会替换主体语义，则必须降级为视觉层，不允许覆盖 IP 身份。
- 如果风格与 IP 完全冲突，则 IP 可降级为 `symbolic` 或 `absent`。

## 8. 与高级分镜规划的关系

高级分镜规划已经负责以下内容：

- 每帧讲什么。
- 视觉目标是什么。
- 主体是谁。
- 镜头类型是什么。
- 镜头目的是什么。
- 世界元素是什么。
- 连续性锚点是什么。

IP 使用规划应插在高级分镜之后、最终提示词组装之前。

推荐链路：

```text
StoryboardPlan / FramePlan
-> IP Usage Planner
-> IP Frame Adaptation Package
-> Prompt Composer
-> PromptPlan.final_prompt
```

IP Usage Planner 不重新做分镜，而是读取每帧上下文，判断 IP 如何参与。

## 9. IP Frame Adaptation Package

每帧应生成一个结构化的 IP 适配包，而不是直接生成一段散乱提示词。

建议字段：

```text
frame_id
presence_mode
role_in_frame
semantic_reason
must_not_replace
identity_anchors_visible
identity_anchors_suppressed
outfit_theme
outfit_condition
accessories
hand_prop
body_action
gesture
facial_expression
gaze_target
body_orientation
frame_position
depth_layer
interaction_target
continuity_from_previous
shot_fit_notes
prompt_weight
negative_constraints
```

字段说明：

- `presence_mode`：lead、support、symbolic、ambient、absent。
- `role_in_frame`：主角、讲解员、观察者、旁白角色、背景符号等。
- `semantic_reason`：为什么这样安排。
- `must_not_replace`：不能替代的文案主体。
- `identity_anchors_visible`：本帧需要显式保留的识别锚点。
- `identity_anchors_suppressed`：由于镜头或场景原因暂时弱化的锚点。
- `prompt_weight`：IP 在最终 prompt 中的表达强度。
- `negative_constraints`：防止角色跑偏的负面约束。

这个结构化包是后续可测试、可追踪、可调试的关键。

## 10. 最终提示词融合原则

最终提示词不应是简单拼接：

```text
风格前缀 + 原文场景 + IP 提示词 + 镜头提示词
```

而应是先裁决、再重写：

```text
文案语义
+ 高级分镜
+ 风格规则
+ IP 适配包
-> 生成一段自然、流畅、可执行的 Z-Image prompt
```

推荐最终 prompt 结构：

```text
1. 场景与时间氛围
2. 原文核心主体和动作
3. IP 出场方式和身份锚点
4. IP 当前帧可变表现
5. 构图、镜头和站位
6. 风格、材质、光影、色彩
7. 连续性要求
8. 负面约束
```

如果 IP 不出场，最终 prompt 中不应强行写 IP，只需要在 trace 中记录 `presence_mode=absent` 和原因。

## 11. Z-Image 场景下的提示词策略

Z-Image 属于文生图模型，适合较详细的提示词，但详细不等于堆叠。

建议策略：

- 场景描述要完整。
- 主体关系要明确。
- IP 锚点要少而强。
- 可变项要挑关键项。
- 风格描述不要污染主体身份。
- 背景复杂度要受控。
- 人物位置和占比要明确。
- 负面约束要针对常见跑偏点。

不建议每帧重复所有 IP 档案。每帧应该只写最必要的识别锚点和当前变化。

一句话原则：

```text
内部结构化信息可以多，最终 prompt 表达要少而精。
```

## 12. 约束强度策略

IP 约束不是越多越好，也不是越少越好。

推荐策略：

- 对身份锁定项强约束。
- 对是否出现和出场身份强裁决。
- 对服装、动作、表情、道具中等约束。
- 对场景细节和画面氛围弱约束。
- 对最终 prompt 长度做控制，不让 IP 描述吞掉文案主体。

也就是：

```text
小硬核，大弹性。
```

硬核是身份锚点，弹性是情境表达。

## 13. 示例：小狗草地场景与兔子 IP

用户文案：

```text
清晨，阳光照在草地上，一只小狗正趴在花坛边晒太阳，有一个人从这里路过。
```

假设 IP 是白色兔子，固定蓝色领带。

### 13.1 不出场模式

适用于强调原文生活感，不希望 IP 干扰画面。

```text
清晨的草地被柔和阳光照亮，一只小狗安静地趴在花坛边晒太阳，远处有一个路人从小径经过，画面温暖、平静、生活化。中景构图，花坛和草地形成自然前景，路人保持弱化，不抢夺小狗主体。整体保持所选风格的线条、色彩和光影，画面干净自然。
```

### 13.2 陪伴观察者模式

适用于 IP 轻量融入，不替代小狗。

```text
清晨阳光洒在草地和花坛上，一只小狗趴在花坛边晒太阳，画面右侧有一个白色兔子 IP 角色安静路过，保留长耳朵和蓝色领带两个清晰识别锚点。兔子微微侧身看向小狗，表情温和好奇，手里不拿复杂道具，姿态放松。小狗仍是画面主要生活主体，兔子只是陪伴观察者。中景平视构图，背景简洁，整体遵循所选风格的材质、线条和光影。
```

### 13.3 符号化模式

适用于保留品牌存在感但不让 IP 角色入场。

```text
清晨的阳光照在草地和花坛上，一只小狗趴在花坛边晒太阳，一个路人从小径旁自然经过。花坛边有一个小小的白兔蓝领带图案木牌，作为轻量视觉符号出现，不影响小狗和路人的生活场景。中景构图，草地、花坛、小径形成清晰层次，氛围温暖安静，整体使用所选风格的画面语言。
```

### 13.4 IP 宇宙化主导模式

只适用于用户明确希望 IP 主导画面。

```text
清晨阳光洒在草地和花坛上，一只小狗趴在花坛边晒太阳，白色兔子 IP 角色作为画面主角从小径旁路过。兔子保持长耳朵、白色身体和蓝色领带，穿着轻便晨间外套，表情温柔，身体微微前倾看向小狗，像是在安静问候。小狗仍保留为原文关键主体，不被替换。中景平视构图，兔子占画面约三分之一，小狗和花坛形成前景，整体风格统一、温暖、干净。
```

这四种模式没有绝对好坏，选择取决于产品默认策略和用户是否希望 IP 强出场。默认更推荐 `support` 或 `symbolic`，避免 IP 过度干扰长文案原意。

## 14. 可参考的外部文档结论

用户提供的《已有 IP 形象的 Z-Image 文生图提示词反推与复用流程》有参考价值，但它主要解决的是已有 IP 标准图如何反推出稳定提示词体系。

值得吸收的部分：

- 不要只靠一句风格前缀。
- 提取轮廓锚点、结构锚点、配色锚点、线条锚点、气质锚点。
- 固定前缀不要写死动作、表情、场景和道具。
- 可变模块应拆成表情、动作、场景、人物位置、景别镜头、道具互动、光线氛围和输出用途。
- 纯文生图下，少量强锚点比复杂细节更稳定。
- 通过母版、表情动作、简单场景、用途图分阶段测试。

它的不足是没有解决长文案主链路中的每帧出场裁决，也没有解决和高级分镜、风格前缀、PromptPlan 的融合。因此它适合成为本系统中的 `IP Identity Profile / IP Prompt Bible` 子模块，而不是完整方案。

## 15. 推荐产品能力边界

### 15.1 IP 设计工作台

主要负责：

- 自然语言创建 IP。
- 图片反推 IP。
- AI Chat 修改 IP。
- 保存固定身份、识别锚点、可变模块和负面约束。
- 维护 IP 版本。
- 做母版和变量测试。

### 15.2 IP 使用规划

主要负责：

- 读取长文案生成后的分镜计划。
- 对每帧做 IP 出场裁决。
- 输出 IP Frame Adaptation Package。
- 记录为什么出现或不出现。
- 控制 IP 占比和提示词强度。

### 15.3 Prompt Composer

主要负责：

- 融合文案语义。
- 融合高级分镜。
- 融合风格前缀。
- 融合 IP 适配包。
- 生成最终 Z-Image prompt。
- 保存可追踪的 PromptPlan。

## 16. 后续实现方向

下一阶段不应先扩大手工表单，而应优先设计和实现以下能力：

1. 扩展 IP 数据结构，补充固定锚点、可变模块、负面约束和版本信息。
2. 新增 IP Usage Planner，在 StoryboardPlan 之后对每帧做出场裁决。
3. 新增 IP Frame Adaptation Package 的结构化模型。
4. 改造 Prompt Composer，让最终 prompt 从“拼接”变成“基于结构化输入重写”。
5. 保留现有 `AssetBible / SceneCast / PromptPlan` 的资产引用能力，但让它们服务于主生成链路，而不是只做手工 apply。
6. 建立测试样例，覆盖不出场、陪伴、符号化、主导四类 IP 使用方式。
7. 以 Z-Image 为目标优化最终 prompt 的详细度和约束强度。

## 17. 最终原则

当前 IP 系统的核心原则是：

```text
固定身份，变化情境。
先做出场裁决，再做提示词融合。
内部结构化要完整，最终 prompt 要少而精。
文案语义优先，IP 身份第二，镜头规划第三，风格作为渲染层。
```

只有这样，IP 才能真正融入用户长文案的视频生成链路，而不是成为一个孤立的角色提示词或风格前缀。
