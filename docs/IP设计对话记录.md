## 正定向导兔 IP 资产设计分析

### 一、JSON 字段结构评价

当前 `zhengding_guide_bible.json` 的字段设计核心逻辑是 **"结构化事实源 vs 说明性辅助文本"** 的分离，这来自 `2026-05-04-ipprofile-结构化事实源设计.md`：

| 层级 | 字段 | 用途 |
|------|------|------|
| **正式生成事实源** | `identity_lock`、`identity_anchors`、`semantic_boundary`、`negative_constraints`、`variable_slots` | 直接注入 Z-Image prompt |
| **人类参考辅助** | `logline`、`world_hint`、`style_hint` | 仅设计时参考，不进入生成链路 |

**这个设计逻辑本身是合理的**，解决了之前的核心 bug：UI 里填了"白色卡通兔子，蓝色领结"，但 `identity_lock=[]` / `identity_anchors=[]`，导致生成结果里 IP 静默退化。强制结构化字段非空后才允许生成（`ip_profile_readiness.py:17`），是正确的防御。

### 二、对照实际 prompt 看问题

你给的这条 prompt：

> 一对情侣在不同情境下的表情变化…minimal line art, elegant contour drawing…**白色卡通兔子, 古城文旅向导, 亲和好奇的表情, 温和陪伴式讲解者, 蓝色领结, 长耳朵, 浅粉色耳朵内侧, 圆润脸型, 清爽亲和的卡通造型, 它是陪伴式古城导游和文旅吉祥物, 不是历史人物, 不是宗教人物, 不是佛像, 不能替代正定古城城墙寺庙碑刻等真实主体，不是主角，不能占图片太多比例，要融入到图片中, 不要替代古城主体, 不要遮挡佛像寺庙城墙等核心内容, 不要出现错误文字, 不要出现乱码, 不要变成蓝色兔子, 不要变成真人玩偶…**

能看出几个关键问题：

#### 问题 1：内容域不匹配——最核心的设计缺陷

旁白讲的是 **"爱情/情侣/情感关系"**，但 IP 设定是 **"正定古城文旅向导兔"**。一个文旅导游兔子被塞进"情侣从开心到忧虑"的情感场景里，角色身份和画面内容没有天然关联。当前系统**没有"内容域兼容性检查"机制**——`IPUsagePlanner` 的 `_presence_type_for_frame()` 只判断画面是否有"佛像/宗教/严肃纪实"等敏感内容来降级 IP 存在感，但**从不判断"IP 是否根本就不该出现在这个主题里"**。

`ABSENT` 存在类型只能通过 scene_cast 手动配置才能触发，没有自动检测路径。

#### 问题 2：Prompt 膨胀与信号竞争

IP 相关术语占了整个 prompt 约 50% 的篇幅。这些信号在互相竞争：

- 场景要求：**单色极简线条画**，强调情感对比
- IP 要求：**白色卡通兔子**、**蓝色领结**、**浅粉色耳朵内侧**（需要色彩信息）
- 同时又说：**不是主角，不能占太多比例**

这三个要求之间存在张力——你让模型画一只具体的、带颜色细节的兔子，又让它不占太多画面，还要求单色处理。这在实际生图时容易产生不可预期的结果。

#### 问题 3：约束字段冗余

`semantic_boundary` 和 `negative_constraints` 之间存在语义重叠：

```
semantic_boundary[4]:  "不能替代正定古城城墙寺庙碑刻等真实主体"
negative_constraints[0]: "不要替代古城主体"
negative_constraints[1]: "不要遮挡佛像寺庙城墙等核心内容"
```

再加上 `IPUsagePlanner._negative_constraints()` 硬编码追加的 `"不能替代画面中的历史建筑或宗教人物"`，同一条约束以不同措辞出现了 4 次。对于文生图模型来说，重复强调可能有用，但从**数据建模**角度看，这说明字段职责边界不够清晰。

#### 问题 4：`variable_slots` 丰富但未充分落地

```json
"variable_slots": ["表情", "动作", "站位", "手持地图", "手持导览旗", "讲解姿势", "与游客或古城场景的距离", "出场强度"]
```

这个设计很好——定义了 IP 的"可变量"。但在你给的这个 prompt 里，这些 slot 并没有被动态填充为具体的画面描述（比如"手持导览旗指向远方"、"站在情侣身后不远处"）。当前 `IPUsagePlanner` 只用了 `action_for_presence` 和 `expression_for_presence` 两个静态值，没有利用 `variable_slots` 做逐帧变化。

---

### 三、总结判断

| 维度 | 评价 |
|------|------|
| 结构化事实源架构 | **合理**，解决了 IP 身份在生图中丢失的根因 |
| 字段语义拆分 | **基本合理**，但 `semantic_boundary` / `negative_constraints` / `suppression_rules` 三者边界有重叠 |
| 内容域兼容性 | **缺失**，系统无法判断 IP 是否适合当前视频主题 |
| Prompt 膨胀控制 | **不足**，IP 注入无节制，在无关场景中造成信号污染 |
| variable_slots 落地 | **未完成**，slot 定义了但没有被逐帧填充 |

**最需要优先解决的是问题 1**：让系统有能力判断"这个 IP 是否适合这段内容"，而不是在所有帧里无条件注入。这可以在 `IPUsagePlanner` 中增加一个内容域相关性评分，当旁白/画面主题与 `world_hint` 的相关性低于阈值时，自动走 `ABSENT` 或 `SYMBOLIC_ONLY`。

## 核心问题：角色身份 vs 角色职能被混为一谈

当前配置把"这只兔子长什么样"和"这只兔子在正定古城做什么工作"焊死在了一起。这导致了一个根本性的局限：**IP 只能在"古城文旅"这一个场景里当导游，出了正定古城就无处安放。**

### 逐字段诊断

**`identity_lock`（身份锁定）—— 混入了职能：**

| 条目 | 类型 | 问题 |
|------|------|------|
| 白色卡通兔子 | 身份（对） | ✓ 应该保留 |
| 古城文旅向导 | 职能（错） | ✗ 这是角色设定，不是视觉身份 |
| 亲和好奇的表情 | 职能（错） | ✗ 表情应该随场景变化 |
| 温和陪伴式讲解者 | 职能（错） | ✗ 这是行为模式，不是视觉特征 |

结果：`identity_lock` 里 4 条只有 1 条是真正的视觉身份。"古城文旅向导"一旦进入非文旅场景（比如你给的爱情主题），就和画面内容产生冲突。

**`semantic_boundary`（语义边界）—— 写成了职业说明书：**

```
"它是陪伴式古城导游和文旅吉祥物"  ← 这是正向职能断言，不是语义边界
"不能替代正定古城城墙寺庙碑刻等真实主体" ← 只在古城场景有意义
```

语义边界应该回答"这个角色是什么/不是什么"，而不是"它在哪个景区上班"。

**`variable_slots`（可变槽位）—— 一半是古城特供：**

```
手持地图、手持导览旗、讲解姿势、与游客或古城场景的距离
```
这四个 slot 离开旅游场景就报废了。

**`negative_constraints`（负约束）—— 大量无效噪音：**

```
不要替代古城主体、不要遮挡佛像寺庙城墙等核心内容
```
当画面是"一对情侣在咖啡馆"时，这两条约束毫无意义，但依然被注入 prompt，成为纯粹的 token 浪费。

**`world_hint` —— 过于具体：**

```
正定古城、城墙、古寺、青砖、历史文化旅游
```
这应该叫 `scene_hint` 而不是 `world_hint`，它描述的是一个具体景点，不是一个世界。

---

### 设计层面的根因

当前 `IPUsagePlanner` 的行为可以概括为：**IP 永远是导游，永远在介绍景点**。看代码：

```python
# ip_usage_planner.py:320-325
def _visible_anchors(presence_type, ip_profile):
    if presence_type is IPPresenceType.ABSENT:
        return ()
    if presence_type is IPPresenceType.SYMBOLIC_ONLY:
        return tuple(ip_profile.identity_anchors[:1])
    return tuple([*ip_profile.identity_lock, *ip_profile.identity_anchors])
    #                                              ^^^^^^^^^^^^^^
    #                                          "古城文旅向导" 永远被注入
```

几乎所有 presence_type 都把 `identity_lock` 完整注入，而 `identity_lock` 里塞了职能描述。这就解释了为什么每张图 IP 都是"导游"姿态、占比都很大——系统没有给 IP 分配**角色可变性**。

---

### 公允判断

**你的直觉完全正确。** 当前设计的问题不是个别字段取值不当，而是整体架构把"IP 角色"当成了"固定职能的吉祥物"而不是"可适配不同场景的演员"。

一个可通用化的 IP 配置应该做三层分离：

| 层级 | 内容 | 随场景变化？ | 示例 |
|------|------|------------|------|
| **视觉身份** | 它长什么样 | 不变 | 白色卡通兔子、蓝色领结、长耳朵、圆润脸型 |
| **角色职能** | 它在这场戏里做什么 | 可变 | 导游 / 路人 / 主角 / 旁观者 / 画外角色 |
| **出场规格** | 它占多大画面、什么距离 | 逐帧可变 | 全身 / 半身 / 局部 / 远景 / 只出现耳朵或领结 |

当前配置把三层全部压进了 `identity_lock + semantic_boundary` 且全部标记为"不变"，这才是根因。

**`variable_slots` 本来是为第三层设计的**，但它被填入了古城特供内容，且 `IPUsagePlanner` 实际上没有消费 `variable_slots` 做逐帧动态变化——它只用了 `action_for_presence()` / `expression_for_presence()` 两个硬编码的静态值。

---

### 如果要修正，关键改动方向

1. **`identity_lock` 改为纯视觉身份**：去掉"古城文旅向导""温和陪伴式讲解者"，只保留"白色卡通兔子"类视觉锚点
2. **新增 `role_presets`**（角色预设）：定义兔子在不同场景下可以扮演什么角色——导游、路人、画外解说、情感陪伴、主角等
3. **`semantic_boundary` 改为通用约束**：去掉古城特供内容，改为通用的"不是人类、不是写实动物、不替代画面真实主体"等
4. **`IPUsagePlanner` 增加角色指派逻辑**：根据用户文案的主题域，自动选择 IP 在当前视频中的角色职能，而不是永远当导游
5. **`variable_slots` 通用化 + 真正消费**：slot 应该是"构图位置、镜头距离、露出程度"等通用的画面参数，且每帧动态变化

这些改动不需要推翻现有结构化事实源的架构——三层分离可以完全兼容当前的 `IPProfile` dataclass 和 AssetBible schema，主要是**字段内容的重新定义**和 **Planner 的行为扩展**。

## 方案概要

### 问题根因

当前 `identity_lock` 把三件事焊死了：

```
白色卡通兔子（视觉） + 古城文旅向导（职能） + 亲和好奇的表情（行为）
```

导致 IP 离开古城就无处安放，且 `IPUsagePlanner` 对所有帧做无差别拼接。

### 解决方案：三层分离

| 层级 | 谁定义 | 谁决定 |
|------|--------|--------|
| **Layer 1** — 它长什么样（白色兔子、蓝色领结、长耳朵） | 用户在 IP 工作台定义 | 不变 |
| **Layer 2** — 它演什么角色（导游/陪伴/路人/主角/不出镜） | 用户在 `role_presets` 定义可选角色 | **LLM 按帧决定** |
| **Layer 3** — 它占多大画面（全身/半身/局部/远景） | 用户在 `presence_spectrum` 定义范围 | **LLM 按帧决定** |

LLM 为每一帧输出自然语言描述（如"画面边缘的咖啡馆角落，白色兔子的耳朵和蓝色领结隐约可见"），而不是机械拼接关键词。LLM 拿到的自由空间来自 `variable_slots`（服装配饰、手持道具、动作姿势、表情神态、互动对象），约束来自 `universal_constraints`（不能变成人类、不能丢耳朵和领结等）。

### 关键发现

`IPFrameAdaptationPackage` 模型**早已预留**了 `outfit_theme`、`accessories`、`pose`、`expression`、`continuity_from_previous` 等字段——只是 `IPUsagePlanner` 从未填充它们。所以数据结构不需要大改，改的是 Planner 的行为。

### 实施分两个批次

- **批次 A（Task 1-3）**：模型 + 预设 + API/UI 同步 — 新增 `role_presets` / `presence_spectrum` / `universal_constraints` 字段，重写 `zhengding_guide_bible.json`
- **批次 B（Task 4-5）**：Planner LLM 驱动改造 + Prompt 自然语言融合 — 新增 `IPFrameAppearancePlanner`，有 LLM 时用 LLM，没有时用规则检测内容域做基本变化

## 有参考价值的部分

**1. 多实体分离的方向是对的**

文档把 IP 拆成 CharacterProfile / AssetProfile / WorldProfile / StyleProfile，比当前系统以 `IPProfile` 为单一入口更合理。当前 Pixelle 的 AssetBible 虽然也有 `character_profiles` 和 `style_profiles` 字段，但 `IPProfile` 承担了太多东西——它既管角色视觉、又管约束、又管文字规则。文档里的 CharacterProfile 拆得更细：

```
CharacterProfile:
  visual_summary          ← 一个自然语言视觉摘要
  signature_traits        ← 核心识别特征
  outfit_traits           ← 服装
  fixed_colors            ← 固定用色
  props                   ← 道具
  personality_visuals     ← 性格视觉化
  must_include / must_avoid ← 正负约束
```

这比我们当前的 `identity_lock`（一条平列表塞所有东西）更结构化。

**2. `role` 枚举的方向对，但粒度错了**

```python
role: Literal["main", "support", "npc", "villain", "narrator"]
```

这个字段抓住了"角色在叙事中的位置"——正是我们讨论的"坑位"概念。但问题是：**它被定义成角色的静态属性，而不是每帧的动态决策**。

植物老师的 `role="main"`——那它在每一帧都是主角？显然不对。一集视频里第 1 帧可能是主角特写，第 5 帧植物老师可能只是背景里的一个影子，第 8 帧根本不出现。

**3. 参考文档里缺失的关键能力**

这份文档设计的是一个**角色数据库**，不是**角色出场调度系统**。它解决了"这个角色是谁"的存储问题，但没有解决：

| 缺失的能力 | 说明 |
|-----------|------|
| **逐帧角色坑位选择** | 角色扮演 main/support/npc 不是固定属性，是每帧的动态决策 |
| **坑位替换语义** | IP 不是追加到画面，而是替换画面中某一个已有角色 |

## 公允判断

这份文档作为一个**角色数据库 schema 设计**是及格甚至不错的——它知道要把角色拆成视觉摘要 + 特征 + 约束 + 道具，也知道要分 mode（prompt_only / reference_augmented）。

但它**不是**一个"如何让角色融入画面"的设计。它假设角色已经有了一个固定的叙事身份（`role`），然后所有帧都按这个身份出场。这正是我们当前系统的问题——正定向导兔永远被当成"导游"塞进每张图。

- **可以参考的**：CharacterProfile 的字段拆分思路（visual_summary / signature_traits / must_include / must_avoid），把它作为 IPProfile 重构后的角色定义层
- **不能照搬的**：把 `role` 当作角色静态属性。`role` 应该是**逐帧决策**，不是角色固有属性
- **它没覆盖的**：坑位替换策略、逐帧出场描述生成、IP 与场景融合的 meta-prompt 设计

## 如果我们重设计，合理的模型结构

结合这份文档的优点和我们讨论的结论，应该是两层：

**第一层：角色身份（静态，用户在设计工作台定义）**

```python
class CharacterProfile:
    character_id: str
    name: str
    visual_summary: str                # "白色卡通兔子，蓝色领结，长耳朵..."
    signature_traits: list[str]        # ["蓝色领结", "长耳朵", "圆润脸型"]
    outfit_base: str | None            # 基础服装描述（可为空，LLM自由发挥）

    must_avoid: list[str]              # 负向约束
    reference_images: list[str]        # 预留参考图
```

**第二层：出场调度（动态，LLM 逐帧决策）**

LLM 读取帧内容 + 角色身份后，输出：

class FrameCastingDecision:
    frame_id: str

```

## 核心概念：角色坑位替换

任何画面场景都隐含有"角色坑位"——画面里有人/有角色存在。IP 的工作不是往画面里多塞一个人，而是**顶替掉其中一个坑位**。

```
场景: 两个人在咖啡馆聊天，窗外有人走过
坑位:  [主角A]  [主角B]           [路人]
                                   ↑
                             IP顶替了这个坑位
```

---

## 系统设计

### 第一层：IP 角色身份证（静态，用户定义）

只描述"它长什么样"，不定义"它干什么"。

```
角色身份证:
  类型: 卡通动物 / 动漫人物 / 真人动漫脸 / 简笔画 / ...
  视觉摘要: 一段自然语言描述（"白色卡通兔子，蓝色领结，长耳朵，浅粉色耳朵内侧，圆润脸型"）
  固定锚点: ["蓝色领结", "长耳朵"]
  颜色规则: []
  负向约束: ["不能变成人类", "不能变成写实风格", "不能丢失固定锚点"]
```

不管什么类型的 IP——兔子、动漫少女、火柴人、真人和动漫脸结合——都是同一套结构，只有内容不同。

### 第二层：坑位策略（用户可选，全局默认）

用户在创建 IP 时选择一个默认策略，LLM 据此做逐帧决策：

| 策略 | 行为 |
|------|------|
| **优先配角/路人** | 默认。尽量选背景坑位，IP 低调融入，不抢主体 |
| **优先主角** | IP 成为画面核心角色，适合品牌 IP 视频 |
| **仅在必要时出现** | 大多数帧不出场，只在场景天然需要角色时才顶替 |
| **完全由 LLM 判断** | 无默认偏好，LLM 根据每帧内容自由决定 |

### 第三层：逐帧出场决策（LLM 动态执行）

对每一帧，LLM 做四件事：

```
Step 1: 理解场景
  输入: 帧的旁白文本、视觉目标、镜头类型
  输出: 这个画面里有哪些角色坑位？

Step 2: 选择坑位
  输入: 坑位列表 + 用户的坑位策略
  输出: 本帧选哪个坑位让 IP 顶替？（或者"不出场"）

Step 3: 生成出场描述
  输入: IP 视觉身份证 + 被顶替的角色原本在做什么
  输出: 一句自然语言，把 IP 放到那个位置上

Step 4: 融入最终提示词
  输入: 原场景描述 + IP 出场描述 + 负向约束
  输出: 完整的文生图 prompt
```

## 关键认知：高级分镜 ≠ 场景设计，是骨架 ≠ 血肉

```
┌──────────────────────────────────────────────────────────┐
│  高级分镜规划（Storyboard Planner）                        │
│  输出：画面的骨架                                          │
│  shot_type / primary_subject / visual_goal / world_elements│

│  它定义了"拍什么"，不含光线、色调、体态、情绪视觉化          │
└──────────────────────┬───────────────────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────────────────┐
│  场景转换（Scene Designer）                               │
│  骨架 + 文案情感 → 完整的画面描述                           │
│                                                          │
│  它定义了"怎么拍"：光线从哪打、人物什么体态、空间什么氛围     │
└──────────────────────┬───────────────────────────────────┘

                       ▼
┌──────────────────────────────────────────────────────────┐

│  画面里选一个角色坑位，让 IP 顶替                           │
└──────────────────────────────────────────────────────────┘

两者不冲突——分镜规划决定了**镜头怎么架**，场景转换决定了**架好镜头后画面里有什么**。

## 冲突点在哪，怎么解决

只有一个潜在的冲突：**分镜规划的 `primary_subject` 和 IP 替换的主角坑位如果重叠，谁优先？**

```
分镜规划: primary_subject = "一对情侣"
IP 融入:  大模型决定替换主角坑位 → 情侣中的一方被兔子替换

结果: "一只白色卡通兔子和一个人类女孩作为情侣" ← 没冲突
```

```
分镜规划: primary_subject = "一位老人在长乐门前讲述历史"
IP 融入:  大模型决定替换主角坑位 → 老人被兔子替换

结果: "一只白色卡通兔子站在长乐门前" ← 老人被替换了，可能不符合用户预期
```

**解决方式**：不是通过规则，而是让场景转换 LLM 自己去判断。分镜字段是输入不是命令。

## 1. 亚洲人物的默认约束放哪里

不放风格前缀。风格前缀是"怎么画"（笔触、色调、光影），不是"画什么"（人种、地域）。

应该放在**文生图 prompt 的生成规则**里，作为默认约束：

```

```

这条和风格无关，它和"不要出现乱码"、"不要出现错误文字"同级——是画面内容的生成规则。风格前缀保持它的职责单一。

---

## 2. 是否动态拼装 —— 你的想法完全正确

不开的功能，不应把参数传给大模型。理由是：

**第一，prompt 膨胀是真实的伤害。** 传空字段或者"本节不适用"意味着 LLM 需要额外消耗注意力去理解"哪些是有效的、哪些可以忽略"。你让它忽略的东西它未必真的会忽略。

**第二，条件分支不应该推给 LLM 做。** "如果开了 IP 就融入，没开就算了"——这个判断是系统逻辑，不是 LLM 的创作判断。系统应该在拼 prompt 之前就把不相关的节删掉，LLM 看到的 prompt 里压根没有"IP 角色"这个标题。

## 正确的 Meta-Prompt 拼装逻辑

```
def build_meta_prompt(
    narration: str,
    style_prefix: str,
    style_suffix: str,
    storyboard: StoryboardPlanFrame | None = None,   # None = 未开启高级分镜
    ip_identity: CharacterIdentity | None = None,      # None = 未开启IP
) -> str:
    sections = []
    
    # 风格段 —— 永远有
    sections.append(f"## 风格\n前缀：{style_prefix}\n后缀：{style_suffix}")
    
    # 分镜约束段 —— 只在开了高级分镜时才有
    if storyboard is not None:
        sections.append(build_storyboard_section(storyboard))
    
    # IP 融入段 —— 只在开了 IP 时才有
    if ip_identity is not None:
        sections.append(build_ip_section(ip_identity))
    
    # 默认约束 —— 永远有
    sections.append(build_default_constraints())
    
    # 用户文案 —— 永远有
    sections.append(f"## 用户文案\n{narration}")
    
    # 输出规则 —— 永远有
    sections.append(build_output_rules(storyboard, ip_identity))
    
    return "\n\n".join(sections)
```

## 分组设计

### 区块一：基础设定

| 字段 | 类型 | 说明 |
|------|------|------|
| IP 名称 | 文本 | 不变 |
| IP 类型 | 下拉 | `卡通动物` / `动漫人物` / `真人动漫混合` / `简笔画` / `3D卡通` |
| 视觉摘要 | 文本区 | 一段自然语言，描述 IP 整体长什么样。这是 LLM 写出场描述的**核心输入** |

**删除**：`world_hint`、`style_hint`——世界观是生成页的事，风格是 StyleProfile 的事，IP 设计工作台不需要。

---

### 区块二：视觉锚点

| 字段 | 类型 | 说明 |
|------|------|------|
| 固定锚点 | 逗号分隔 | **不可丢失的视觉特征**。如"蓝色领结, 长耳朵, 浅粉色耳朵内侧, 圆润脸型" |
| 颜色约束 | 逗号分隔 | 颜色必须/禁止。如"必须白色身体, 不可变成蓝色" |
| 最小可识别特征 | 逗号分隔 | 即使只露出这些也能认出 IP。如"蓝色领结一角, 长耳朵轮廓" |

**合并**：原 `identity_lock` 和 `identity_anchors` 合并为"固定锚点"——两者没有本质区别，都是视觉特征，都需要在 prompt 中携带。

**新增**："最小可识别特征"——当 LLM 选择局部细节或远景出场时，只携带这些。

---

### 区块三：可变项

| 字段 | 类型 | 说明 |
|------|------|------|
| 可变项 | 逗号分隔 | LLM 可以自由发挥的部分。如"服装配饰, 手持道具, 动作姿势, 表情神态, 与其他角色的互动方式" |

**重新定义**：原 `variable_slots` 塞了古城特供道具（手持地图、手持导览旗、讲解姿势），现在改为通用可变项，不再绑定任何场景。

---

### 区块四：替换策略

| 字段 | 类型 | 说明 |
|------|------|------|
| 默认替换偏好 | 下拉 | `优先配角或路人`（默认）/ `优先主角` / `完全由场景判断` / `仅在必要时出现` |
| 出场规格范围 | 逗号分隔 | 多选文本，如"全身出镜, 半身出镜, 局部细节, 远景融入, 完全不出镜" |

**新增**：这两个是 LLM 逐帧决策的**策略输入**。

---

### 区块五：角色能力

| 字段 | 类型 | 说明 |
|------|------|------|
| 角色预设 | 每条一行 | IP 可以在不同场景中扮演的角色。每行一条，如：|

情感陪伴者：安静的陪伴角色，与画面主体自然互动，不抢戏

画面主角：占据画面主体位置，面向镜头，成为画面焦点

**新增**：LLM 根据文案内容和替换策略，从角色预设中选一个。

### 区块六：约束

| 字段 | 类型 | 说明 |

| 通用负向约束 | 逗号分隔 | "不能变成人类, 不能变成写实风格, 不能变成真人玩偶, 不能丢失固定锚点, 不要出现错误文字和乱码" |

## 问题二：前端"IP与世界观提示"改版

当前这个区域有三样东西：

```
┌─────────────────────────────────┐
│ IP 与世界观提示                   │
│                                 │
│ [IP 开启] [选择 IP] [选择 Profile] │  ← 保留
│                                 │
│ ┌─────────────────────────┐     │
│ │ 世界观提示（文本区）       │     │  ← 删掉
│ └─────────────────────────┘     │
│                                 │
│ [使用IP默认世界观] [根据内容生成]   │  ← 删掉
└─────────────────────────────────┘
```

"世界观提示"的本意是告诉 LLM"这次内容的 IP 应该怎么融入场景"。这个目的本身没错，但放错地方了——它不该存在 IP 设计工作台里（那是 IP 的静态身份证），但作为**本次生成的上下文**是有意义的。

改版后：

```
┌──────────────────────────────────┐
│ IP 角色融入                       │
│                                  │
│ [IP 开启] [选择 IP] [选择 Profile] │  ← 保留
│                                  │
│ 本次替换偏好：[下拉] 本次出场强度：[下拉]│  ← 新增，覆盖 IP 默认策略
│                                  │
│ ┌──────────────────────────┐    │
│ │ 本次生成特殊说明（可选）    │    │  ← 改版后的文本区
│ │ 例：本次是美食内容，IP以    │    │
│ │ 食客身份出场，不要导游姿态   │    │
│ └──────────────────────────┘    │
│                                  │
│ ┌─ IP 能力预览（只读）────────┐   │  ← 新增
│ │ 视觉锚点：白色兔子, 蓝色领结...│   │
│ │ 可扮角色：导游/陪伴/路人/...  │   │
│ │ 出场范围：全身 ~ 不出镜       │   │
│ │ 状态：✅ 可用于生成            │   │
│ └────────────────────────────┘  │
└──────────────────────────────────┘
```

### 各模块说明

| 模块 | 作用 | 数据来源 |
|------|------|---------|
| **IP 开关 + 选择** | 不变 | IP 设计工作台保存的 AssetBible |
| **本次替换偏好** | 覆盖 IP 的默认替换策略，仅本次生效 | 下拉，默认取 IP 预设值 |
| **本次出场强度** | 拉杆或下拉：偏多 / 默认 / 偏少 / 极少。一个快捷方式，让用户一句话控制全局 | 新增 |
| **本次生成特殊说明** | 用户对本次内容域的自由描述。如"美食探店""历史知识""情感故事"。这会作为 meta-prompt 中 `## 用户文案` 之上的上下文前缀 | 用户输入，不存回 IP，仅本次请求携带 |
| **IP 能力预览** | 选中 IP 后自动展示：视觉锚点、角色预设、出场范围、生成状态。纯只读，作用是让用户确认"选的 IP 没问题" | 从选中的 IPProfile 读取 |
